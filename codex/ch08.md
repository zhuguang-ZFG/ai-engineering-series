# 第 8 章：沙箱限制的是执行能力

<!-- block: codex-ch08.b-opening -->
沙箱约束进程能够访问的文件与网络等能力；读写范围、审批和任务意图必须分别确认。

选择 workspace-write 之后，还要确认当前工作根、额外可写目录和临时目录的处理方式，以及网络限制和实际执行器。本章用两个临时文件设计实验，观察这些设置怎样影响一次具体读写。

## 8.1 三个名字不是完整安全说明

<!-- block: codex-ch08.b-term-sandbox -->
固定 CLI 的 `--sandbox` 帮助列出 `read-only`、`workspace-write`、`danger-full-access`。前两个表达受限运行方式，第三个意味着不使用相同的沙箱约束。它们适合快速选择模式，但完整行为仍由平台实现、配置要求与运行入口决定。

| 概念 | 回答的问题 |
| --- | --- |
| 工作目录 | 相对路径从哪里解析，项目说明从哪里查 |
| 可写范围 | 哪些位置可以产生文件修改 |
| 网络约束 | 哪类连接能够建立，是否有额外策略 |
| 审批策略 | 遇到需要决定的动作怎样询问或拒绝 |
| 任务授权 | 用户是否要求这个动作产生相应副作用 |

动作同时需要任务授权和执行能力；两项都满足后，仍可能因文件锁、磁盘空间或程序错误而失败。排查时用表中的问题逐项确认。

## 8.2 用哨兵文件设计边界实验

一个有价值的沙箱实验应准备两个临时目录：一个在预期允许范围内，一个在范围外。各放一个可识别的小文件。先验证允许范围中的读取与写入，再验证边界外动作的实际结果。否则，连内部操作都失败时，你无法判断是不是沙箱生效，还是命令本身写错了。

实验要记录实际执行入口、权限模式、平台、退出码和文件摘要。不要只根据错误文字判断，因为不同平台可能报告不同的系统错误。操作后重新计算文件摘要，才能确定是否真的没有修改。

本书的检查范围不启动会话、不使用账号，因此尚未运行这组 OS 边界实验。下面的设计供读者在独立测试环境复现，Windows、Linux 的沙箱结果需分别记录。

## 8.3 添加目录意味着扩大具体范围

`--add-dir` 的帮助描述是增加主工作区之外的可写目录。它适合确实需要改动多个仓库的任务，但应给出明确目录，避免为省事把整个用户目录都加入。目录选择还要注意符号链接、规范化路径和挂载点：你在终端看见的字符串未必等同于执行器最后判断的目标。

```powershell
# 教学用法：两个项目都属于此次明确任务时再添加。
codex.cmd -C . --sandbox workspace-write --add-dir ../shared-library
```

运行前先检查 `../shared-library` 实际解析到哪里。不要让脚本依赖偶然的启动目录，然后在另一个位置执行时扩大到错误路径。对自动化任务，使用由配置解析得到的绝对路径通常更清楚。

## 8.4 外部工具可能拥有自己的权限

MCP 服务、远程执行后端或另一个宿主进程可能运行在不同机器、容器或账号下。CLI 的本地文件范围不能自动约束远端服务的数据库或云资源。审批界面可以控制是否调用某个工具，但工具本身的权限由它的部署和凭据决定。

因此接入外部服务前应先确认它接受什么输入、能访问什么资源、日志保存在哪里。把生产凭据交给一个“只读描述”的工具，并不会因为说明文字写着只读就变成只读凭据。权限限制要落实在服务与账号层。

## 8.5 失败后不要立即切到完全访问

某条命令在沙箱内失败，可能是工具需要写缓存、编译器要创建临时文件、项目测试访问网络，或你选错了目录。先检查失败的具体资源，再决定是否增加一个目录、预装依赖或使用专门的测试环境。

完全访问模式同时改变多项限制，不利于确定最小权限需求。若在可信的外部容器内使用，也要记录容器的挂载和网络范围，其他仓库复用这份配置时仍需核对。

## 8.6 为运费项目列出实际写入需求

运行本章练习前，先列出文件写入，而不是直接选择最大权限。读取代码和解释失败只需要读源码。运行 `python -B -m unittest -v` 让解释器不写字节码缓存，测试自身也没有写文件。修改公式需要写 `parcel.py`。保存报告需要写明确的输出目录。Git 提交则还要修改仓库元数据。

这几项能力并不总在同一阶段需要。可以先用只读任务取得解释，确认后再运行修改任务。若某个客户端支持更细的权限范围，也可以把写入限制到目标工作区；不要把“有一份报告要保存”解释为必须允许整个用户目录写入。

这一分析还能改善测试设计。若测试为了验证一个纯函数，却启动浏览器、访问公网和下载依赖，沙箱问题会掩盖真正的边界错误。运费测试只导入本地函数，失败更容易归因。等基础流程跑通，再增加集成测试所需能力，每个新增访问都能对应到具体用例。

## 8.7 一个可以自己执行的文件状态探针

下面的脚本只是文件观察器，不模拟沙箱。保存为 `snapshot.py`，在实验环境的任意允许目录运行，给它两个明确路径：

```python
import hashlib
import json
import sys
from pathlib import Path

records = []
for value in sys.argv[1:]:
    path = Path(value).resolve()
    record = {"path": str(path), "exists": path.exists()}
    if path.is_file():
        raw = path.read_bytes()
        record.update(size=len(raw), sha256=hashlib.sha256(raw).hexdigest())
    records.append(record)
print(json.dumps(records, ensure_ascii=False, indent=2))
```

先手动建好实验内外两个普通文本文件，各写不同内容。运行探针保存 before；通过你要验证的真实宿主尝试约定的写入；退出宿主后，再由独立终端运行探针得到 after。比较内容哈希，能看出操作是否真的改变文件。这里“独立终端”很关键：若验证命令也在受限执行器内，读不到文件可能只是验证者权限不足。

观察器不能证明是谁修改了文件，也不能防止并发干扰。实验时使用独占临时目录，记录操作时间和进程入口；其他程序改了同一个文件时，本轮结果应重做。脚本使用绝对路径是为了输出明确位置，公开记录前应脱敏个人路径。

完成实验后，记录退出码和 before/after 哈希。本册尚未调用 Codex 宿主执行越界写入，此处没有实测结果可供填写。若遇到 Python 不存在、脚本语法错误或文件名拼错，先修复实验条件，再测试访问限制。

## 8.8 为什么路径字符串相同仍可能指向不同文件

`./parcel.py` 由 cwd 解释；`../shared` 由父目录关系解释；符号链接还会改变最终目标。远程执行环境中的 `C:/work/parcel` 与本机同名路径，也不是天然同一个文件系统对象。配置、Hook 输入和工具执行记录若没有说明所属环境，日志会留下歧义。

固定插件资源类型提供了一个参照：`PluginResourceLocator::Environment` 同时带 `environment_id` 和资源路径；构造已解析插件时会检查资源是否在插件根之下。环境身份使本地与远程的同名路径可以区分，这项资源定位检查的范围不涉及整个沙箱实现。

当你为任务增加 `--add-dir` 时，先在启动 shell 中解析目标，记录实际目录，再看执行器的有效范围。若工作目录后来改变，原先看似合理的相对目录可能不再指向同一个位置。对固定 CI 工作流，用确定的工作区根构造路径，比依赖上一条命令的 `cd` 更稳妥。

## 8.9 权限失败的最小复现怎么写

一份有用的错误报告应包括：执行器与平台、选用模式、目标资源、最小命令、退出结果，以及文件实际是否变化。例如“只读阶段运行纯函数测试失败，日志显示无法创建缓存目录；加 `-B` 后该命令通过”就能定位到缓存写入。它不需要贴出整份个人配置，更不需要附完整环境变量。

如果加 `-B` 仍失败，再检查测试是否写文件、导入时是否有副作用、临时目录是否可用。一次只改一个条件，才能知道哪一项解决了问题。直接切到完全访问后所有事情都能做，只能证明限制变化影响了结果，不能告诉你最少需要什么能力。

确认权限需求后，把测试命令、所需目录和网络要求写回项目说明。运费项目可以写成：单元测试不需要网络和第三方包，使用 `-B` 运行。下一次任务便能直接采用这个入口。

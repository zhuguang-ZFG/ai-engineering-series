# 第 9 章：跨平台不是换一个终端窗口

<!-- block: codex-ch09.b-opening -->
Windows、Linux 与 macOS 的命令、路径和进程约束不同；跨平台结论需要逐个平台留下执行证据。

同一个仓库在 Windows 上通过，在 Linux CI 失败，未必是代理“变笨了”。路径大小写、换行、shell、依赖安装、进程终止和权限机制都可能不同。把问题归结为模型波动，会错过能稳定复现的环境差异。

## 9.1 先拆开程序与 shell

`python` 是要运行的程序，PowerShell 或 Bash 是解释命令文本的 shell。某些命令不需要 shell 特性，直接传参数数组即可；管道和重定向才需要明确选择 shell。跨平台脚本应尽量把复杂逻辑写进 Python、Node 或项目已有脚本，减少在长命令字符串里拼接。

在 PowerShell 中调用 npm 入口时，`.ps1` 可能被本机执行策略拦截，而同目录 `.cmd` 可以正常运行。本书本机就是通过 `codex.cmd --version` 确认版本，再定位原生 exe 做检查。这是启动路径问题，不是模型认证问题。

## 9.2 路径字符串会改变规则匹配

第 10 章的实跑里，规则写的是 `git status`，输入 `C:/book/bin/git.exe status` 时没有匹配。这个结果说明默认检查不会把任意绝对路径自动当成同名程序。路径、扩展名和 basename 解析选项都需要明确核对。

相对路径也容易造成差异。Windows 盘符路径、UNC 路径、Unix 根路径和符号链接没有统一的字符串前缀语义。不要用简单的 `startsWith` 实现安全目录检查；应使用平台路径解析，并考虑链接解析后的目标。书中的临时脚本只写自己创建的实验目录，不拿字符串前缀当隔离证明。

## 9.3 平台沙箱实现有独立入口

上游为 Linux 和 Windows 提供各自组件，说明平台约束不是一份通用 shell 包装就能解决。研究一个平台时，应追到该平台执行器构造的能力与进程参数；不能从另一个平台的错误消息推断同样实现。

## 9.4 测试命令要表达相同目标

Windows 与 Linux 不一定需要完全相同的命令文本，但应该验证相同项目行为。例如两端都运行同一组 Python 单元测试，输出的测试数量与失败名称可比较；若一端只跑语法检查，另一端跑集成测试，就不能把两个绿色状态当作等价。

文件产物也要检查。有些代码只因大小写不一致而在一种文件系统上工作；某些脚本把 CRLF 当作内容写入摘要。文本摘要记录时应说明是原始字节还是规范化文本，本书实验的 SHA-256 使用文件原始字节。

## 9.5 为差异准备最小复现

遇到跨平台问题时，先从完整任务中抽出最小命令。只保留必要文件与配置，不带真实凭据。记录两端二进制版本、程序路径、cwd、参数数组和退出状态，再比较文件内容。这样往往能把“平台问题”缩小成一个引号、一处路径或一个依赖版本。

如果错误发生在受限环境，应保留权限模式，不要先在完全访问模式下重跑然后宣称问题消失。后者只能证明更宽的环境允许动作，并没有解释原边界为何拒绝。需要扩大能力时，写出新增范围与理由，再重新验证。

团队文档可以为每个平台写一小段差异说明，公共流程保持一致。读者会知道哪些命令可直接复制，哪些步骤需要选择对应平台，而不必从散落的报错中反推环境。

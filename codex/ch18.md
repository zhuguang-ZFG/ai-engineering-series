# 第 18 章：把一次修复做成可交付工作

<!-- block: codex-ch18.b-opening -->
完整工程任务把需求、基线、最小修改、实际检查和交付证据连起来；代理框架比较也应基于同一任务与明确边界。

这一章用一个很小的 Python 项目串起全书。它的规模刻意受控：一个函数、一组测试、一个明确缺陷。这样可以把注意力放在工作过程，观察代理是否先理解问题、是否只改必要内容、是否运行真实检查，而不是让大量框架代码掩盖执行边界。

## 18.1 准备一个有明确失败的项目

```python
# parcel.py：完整模板见 codex/examples/workshop/。
def fee_cents(grams):
    if type(grams) is not int:
        raise TypeError("grams must be an integer")
    if not 1 <= grams <= 30000:
        raise ValueError("grams must be between 1 and 30000")
    kilograms = grams // 1000
    return 600 + max(0, kilograms - 1) * 200
```

```python
# test_parcel.py：完整模板另含类型与范围用例。
import unittest
from parcel import fee_cents

class ParcelTests(unittest.TestCase):
    def test_prices(self):
        for grams, cents in ((1, 600), (1000, 600), (1001, 800),
                             (2000, 800), (2001, 1000), (30000, 6400)):
            with self.subTest(grams=grams):
                self.assertEqual(fee_cents(grams), cents)
```

沿用第 3 章复制的独立项目，运行 `python -B -m unittest -v`，确认失败确实来自跨千克边界。这里先列出核心用例，实际跟做使用随书完整模板，保留类型与范围检查。

这是读者练习，本书没有调用模型替你完成这一轮。正确实现很简单，但任务流程仍有研究价值：如果代理引入一个大依赖、重写测试目标或只改断言让它通过，就能直接看出问题。

## 18.2 把需求写成可判断的句子

```text
修复 fee_cents 在 1001 克与 2001 克的收费边界。
每个不足一千克的部分向上计费，金额保持整数分。
不要增加依赖。先复现失败，再做最小修改，运行测试并报告实际结果。
```

需求同时说明触发条件、预期行为和范围。输入是 1 至 30000 的整数克，布尔值、字符串和浮点数不在接口内；本轮不顺便实现单位转换、表单解析或外部价目表。

## 18.3 分阶段观察代理

先让代理读文件与复现测试，再允许必要写入。修改后检查差异，确认只是修正取整而没有删除测试。运行同一组测试，并把命令、退出码和结果留在交付记录中。

```mermaid

  A[明确需求] --> B[记录基线并复现失败]
  B --> C[最小修改]
  C --> D[运行相关检查]
  D --> E[阅读最终差异]
  E --> F[提交与审阅]
```

图 18-1：每一步都给下一步提供证据。没有验证的实现仍是一份候选修改。

如果运行环境拒绝写入，代理应报告约束或请求适当批准，而不是通过另一个工具绕开。若测试程序找不到 Python，应先修正环境或解释缺失，不能把“无法运行”改写成“预计通过”。

## 18.4 比较代理时保持任务条件一致

你可以用 Pi、OpenCode、DeepSeek Harness、Hermes 与 Codex 做同一修复，但要记录模型、版本、提示词、工具集和权限。不同默认能力会显著影响过程：某系统有自定义插件，另一系统可能依靠外部 MCP；某环境已经预装依赖，另一环境却需要下载。

比较重点可以是：需要多少人工介入、是否保留错误证据、失败后能否恢复、扩展是否容易维护。不要仅比较最后答案长度，也不要根据一次运行得出普遍的模型能力排名。

特别是沙箱与审批不能借用另一册的结论。Pi 的某个扩展事件、OpenCode 的 V1 Hook、Codex 的生命周期 Hook，名称都可能带“工具执行前”，但参数、返回值、异常与清理契约不同。迁移时先画接口表，再编写适配代码。

## 18.5 从练习走向真实仓库

真实任务会增加数据库、网络、生成文件和多人协作。不要一次把所有能力都开放；先选择一个边界清楚的模块，用项目已有测试建立反馈。任务拆分后，代理更容易给出可审阅差异，人也更容易判断是否偏离需求。

当多项任务并行，按第 16 章明确目录责任与工作树；当接入 CI，按第 14 章保存终态和检查证据；当需要扩展，按第 12、13 章分别处理技能、Hook、插件与服务。工具越多，越需要知道每项能力属于哪个层，而不是靠一段越来越长的提示词协调全部行为。

## 18.6 一本实现研究怎样保持有效

每次升级都检查本书的事实类型。源码路径变了，更新导航；协议字段变了，重新生成 schema；规则行为变了，复跑固定输入；模型行为变了，建立新的实际任务记录。没有证据时保留未验证状态，比把日期改新更诚实。

这本书交付的是一套可以继续验证的理解方式：看到命令时知道它还没等于执行，看到审批时知道它还没等于能力，看到回合结束时知道它还没等于工程正确。日常使用不需要每次都重读全部源码，但关键边界应始终能回到文件、命令和结果。

## 18.7 按章节走完一次小仓库修复

这一节把前面的材料连起来。先从书籍仓库复制 `codex/examples/workshop/` 到自己的空目录，进入副本并初始化 Git。保留模板里的 AGENTS.md、错误函数、测试和最终报告 schema。若要建立初始提交，按你自己的 Git 身份配置提交这些文件；本书脚本不会代替你创建或推送提交。

第一步只运行测试。记录 1001 克与 2001 克的失败，不急着改代码。第二步阅读项目说明，确认整数数据与依赖约束。第三步按第 12 章准备技能和 Hook fixture，在普通 Python 子进程中验证处理器。第四步运行固定 CLI 的 execpolicy 检查，只检查 token，不执行示例中的推送。

到这里已经有四种证据：项目失败可复现、说明内容明确、处理器输出可解析、规则判断来自真实二进制。它们彼此独立。你可以继续不使用模型，直接运行 `check_workshop.py` 观察临时副本从失败到通过；也可以在自己的模型环境中用第 14 章的任务入口进行真实修复，再保存事件和日志。

选择真实任务路径时，不要把离线 fixture 当作这次运行日志。真实 thread ID、测试输出和用量都应从本轮获取；教学数据中的 fixture-thread 和零 token 没有实际会话含义。比较时关心数据形状和完成判断方法，别要求模型输出与教材逐字相同。

## 18.8 读者能够判定的每个阶段

| 阶段 | 应看到什么 | 若看不到，停在哪里排查 |
| --- | --- | --- |
| 原错误测试 | 两个跨千克边界失败 | Python 环境、cwd、模板内容 |
| 修复公式 | 只有向上取整计算改变 | Git 差异与业务规则 |
| 再次测试 | 三个测试方法运行并通过 | 函数类型、范围和价格 |
| Hook 普通输入 | additionalContext | stdin 与 stdout 契约 |
| Hook 拒绝输入 | deny 加非空理由 | 精确命令文本和事件名 |
| 策略检查 | matchedRules 与 decision | token、规则文件、匹配选项 |
| 协议练习 | 正例通过，错误字段名失败 | 固定 schema 与消息字段 |
| 真实 exec | 进程状态、事件终态、实际差异可对应 | 第 17 章的故障层次 |

三项测试方法里使用 subTest 包含多组输入，所以“Ran 3 tests”不表示只检查了三个重量。读报告时应知道测试框架的计数方式，不能拿一个较大的数字装饰验证结果。重要的是边界、类型和范围这些独立行为都被检查。

离线驱动故意不修改教材模板。每次把文件复制到新的临时目录，运行错误版，再替换公式并运行修复版。因此重复执行不会把第一次修复后的状态误当作初始错误，也不会因为上一次已经绿了而跳过复现。它验证的是本书练习能否重复，不是对 Codex 模型能力的测评。

## 18.9 为交付写一个真正有内容的结果

运费任务的最终报告可以很短：

```json
{
  "summary": "按不足一千克向上计费，修复 1001 克与 2001 克边界。",
  "changed_files": ["parcel.py"],
  "checks": ["python -B -m unittest -v：退出 0", "git diff --check：退出 0"],
  "remaining": []
}
```

这是读者完成对应命令后可以填写的示例。没有运行 `git diff --check` 时，不能照抄第二项；没有模型实跑时，也不能把离线驱动结果写成“代理端到端通过”。报告格式越整齐，越需要确保每一项能找到实际记录。

审阅者先看业务变化：1001 克为何从 600 变成 800，1000 克为何仍是 600。然后看测试有没有被削弱，类型检查是否保留，是否增加无关依赖。最后看提交内容与测试时文件是否一致。这个顺序围绕问题本身，避免报告变成一串与结果无关的命令清单。

如果还有限制，也写具体对象。例如“尚未在项目实际接入方验证输入转换”，比“可能存在未知风险”更有用；它告诉下一位维护者应该检查哪里。我们的教材示例只定义了整数函数接口，没有假装覆盖 HTTP 表单、数据库或业务退款流程。

## 18.10 把失败演练纳入这次交付

完成正常路径后，再做三个小扰动。把正确公式暂时改回去，在自己的副本验证边界测试重新失败；给事件检查器传入缺少终态的 fixture，确认它拒绝宣布流完整；把 threadId 改成 thread_id，确认 schema 检查报错。最后恢复副本的正确公式，再运行测试。

这些扰动有明确观察值，能证明检查确实会抓到相关错误。只运行一次绿色结果，可能只是检查没有真正触达修改；能让同一检查对错误版失败、对修复版通过，证据更强。不要把无关错误也算进去，例如把 Python 路径写错获得 exit 1，并不能证明边界测试有效。

如果你继续接入真实 Hook 宿主，再增加发现、信任与取消实验。先记录列表里来源和状态，再触发测试命令，保存实际输入输出；修改处理器后检查是否要求重新审查。整个过程应使用独立项目，避免把教学 Hook 装到个人全局配置后影响其他仓库。

## 18.11 与其他代理比较时固定哪些条件

同一个运费仓库可以交给 OpenCode、Pi 或其他代理。固定起始提交、测试、任务文本与允许的动作，分别保存结果。比较它们如何发现项目说明、加载技能、表达工具状态和处理权限，比只问“哪个回答更像人”更能指导工程选型。

插件也要按契约比较。Codex 本章的技能文件、Hook 命令与插件资源清单，不应直接迁移成 OpenCode 的 Hooks 对象；相似事件名的参数、输出和生命周期可能不同。先把你的扩展需求写成具体行为：何时观察，能否阻止，失败如何呈现，状态放在哪里，再映射到目标系统。

本册最终交付的是可以回查源码、运行本地练习、构建整书的材料。模型任务、操作系统沙箱和完整插件宿主实验保留各自记录位置，读者补充时有明确入口。教材不需要把所有未做的组合都宣称成功，才能讲清一个完整工作流程；它需要让每个结论都知道从哪里来、下一步怎样亲自验证。

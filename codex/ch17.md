# 第 17 章：从失败现场恢复任务

<!-- block: codex-ch17.b-opening -->
排错先确定失败阶段与已发生副作用，再选择恢复、重试或开始新任务；保存证据比盲目重跑更有用。

一次代理任务可能在模型连接、命令启动、测试、审批或客户端显示处失败。用户看到的常常只有一句“出错了”。如果没有阶段信息，下一步容易变成重新发同一段提示词，既浪费时间，也可能重复产生副作用。

## 17.1 先确认最后一个可靠事实

把任务链倒着看：最后一个明确成功的事件是什么？文件已经写入了吗？进程已经启动了吗？审批是否收到回应？模型响应是否已经形成完整工具参数？先找到这一点，再看之后的缺口。

| 现象 | 首先检查 | 不应立刻推断 |
| --- | --- | --- |
| 参数被拒绝 | 固定版本帮助和配置 schema | 模型服务不可用 |
| 任务无输出 | 连接、进程状态、stderr | 任务从未开始 |
| 命令非零 | 程序契约和原始错误 | 所有修改都已回滚 |
| 会话恢复后结论过时 | Git 基线和现有文件 | 恢复功能没有保存历史 |
| Hook 没有执行 | 发现、启用、信任与事件条件 | 脚本内容一定错误 |

错误报告可以围绕这张表组织。不要只给一张终端截图，最好保留可复制的命令和脱敏文本；截图容易遗漏退出码、前置警告和参数转义。

## 17.2 把重试分为三类

第一类是无副作用查询，例如版本与显式规则检查，通常可以安全重复。第二类是可逆的本地修改，需要先检查部分结果，再决定是否重做。第三类是外部副作用，例如推送、发消息、提交业务任务，必须先查询是否已经发生。

这不是按工具名字分类。一条 shell 命令可能只读，也可能调用外部 API；一个看似查询的工具也可能触发刷新或写缓存。分类依据是具体动作的契约和状态，而不是“它叫 read，所以永远没有变化”。

对于模型请求，网络重试还要考虑运行时是否已经执行上一批工具。客户端断开与服务端停止并不同时发生。恢复前读取线程状态或检查文件，能减少重复执行。

## 17.3 日志应帮助定位，而不是收集一切

保存时间、版本、入口、任务 ID、命令摘要、退出状态和错误类别，通常比保存完整环境更有价值。敏感参数、账号令牌、个人文件正文应避免进入公开日志。需要原始数据复现时，在受控位置保存，并另外生成脱敏版本。

本书的规则实验没有启动会话，结果只含固定命令 token、匹配规则与二进制摘要。这样公开证据足够验证结论，同时不需要公布本机账号配置。其他实验也应从目的出发设计记录范围，而不是最后再对一大堆日志做仓促清洗。

## 17.4 用最小复现区分版本与环境

当一个复杂任务失败时，抽出最小输入，在同一版本运行。如果失败仍在，再比较另一版本；若最小输入不失败，逐步加回配置与文件。一次只改变一个因素，才能判断关键差异。

第 10 章的错误正例就是这种方法：只写一条规则，让它声称一个不匹配命令应匹配。固定 CLI 返回非零，因此我们知道加载器验证了例子，不需要启动整个模型会话来推断。

升级问题也可以用这种方式处理。先保持旧版本结果和输入，记录新版本的不同输出；不要立刻改测试让它通过。测试变更应说明契约为何改变，而不是把每个新行为自动接受为正确。

## 17.5 恢复记录应写给下一位接手者

```text
目标：修复空输入崩溃。
基线：提交与工作树状态已记录。
已完成：增加边界处理，相关单元测试通过。
未完成：集成测试因数据库未启动而未运行。
下一步：启动测试数据库后重跑指定命令，再检查最终差异。
```

这类记录无需重述整个对话。它应把已证实事实与仍需验证的假设分开，并给出能继续操作的下一步。长任务跨多个会话时，记录能避免后来的人反复重做已完成实验。

如果用户改变目标，也应更新记录中的当前目标，而不是把新旧计划并排保留，让后续代理自己猜哪一个有效。任务状态需要随事实变化，不能因为计划最初写了某项就永远继续执行。

## 17.6 故障结束之后留下可复用知识

值得保留的是触发条件、根因、修复与防止复发的方法。例如“PowerShell 选择了被策略阻止的 ps1，改用同包 cmd 入口”是可复用结论；“重试第三次就好了”只是现象。网络间歇错误若未确定根因，也应诚实写成暂时恢复，不要编一个确定解释。

遇到同类问题反复发生时，优先改工作流或检查工具。让脚本自动核对版本、规则输入和产物，比每次在聊天里提醒一次更能减少错误。这里的自动化服务于清楚的契约，而不只是增加更多日志。

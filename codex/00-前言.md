# 前言

<!-- block: codex-front.b-opening -->
这本书从命令、文件和会话的实际变化解释 Codex CLI，重点是让自动开发过程可检查、可恢复。

你让代理修一个测试，它改了三份文件，终端上出现绿色提示，然后回答“完成”。到这里还有几件事没有确定：测试是不是在当前工作树运行的；失败的命令有没有被误判成成功；为了安装依赖而批准的权限是否还在生效；重新打开会话时，代理看到的历史与磁盘上的内容是否一致。这些问题决定了一个演示能否变成日常工具。

Codex CLI 值得研究的地方，是它把终端界面、非交互执行、协议服务、工具与平台约束放进同一个开源 Rust 工程。你既可以把它当成终端助手，也可以把它接进自己的客户端。两种用法都要经过真实的进程、文件系统和网络，不能只看模型回答。

## 本书固定哪一版

本书使用 `rust-v0.167.0`，源码提交为 `086ccc833bc9cf01024ad2dd6af7dbd421b6bf9a`，上游许可证为 Apache-2.0。标签对象与提交不是同一种 Git 对象；引用正文实现时，链接固定到这个完整提交。当前官网会继续更新，书中提到官网说明时会标出其文档性质，不拿滚动页面替代钉版证据。

本机实际运行的是 `codex-cli 0.167.0` Windows x64 发布程序。没有登录新账号，没有向外部模型发送任务。已经完成的实验包括执行策略匹配、错误规则加载和 app-server 静态协议生成。它们经过真实二进制，既不是重写的教学匹配器，也不证明整条模型到工具的链路都已运行。完整清单在附录 C。

这一区分不会阻止我们讲完整机制。说明一个函数如何接收配置、如何构造审批请求，可以由钉版源码支持；说明某条命令在本机真的得到哪个结果，需要运行记录。书中会把这两类证据放在对应位置，而不是在每章末尾重复一份笼统声明。

## 从一个小仓库读起

建议另建一个临时 Git 仓库，里面只有一个纯函数、两项测试和一份简短的 `AGENTS.md`。先让代理解释失败，再允许它修改。任务规模小，反而容易看出命令、补丁、测试和最后答复之间是否相互对应。

学习期间也应给文件状态留一份独立证据。每次运行前记下分支、提交与 `git status --short`；结束后读差异，亲自运行项目要求的检查。会话历史有助于理解“为什么这样改”，Git 差异回答的是“究竟改了什么”。两者都保留，比把最后一段聊天当作全部交付可靠。

如果你只想先使用 CLI，读第 1、3、4、7、11、14 章。要把它接进现有系统，接着读第 5、6、13、15 章。第 8 至 10 章把审批、沙箱、命令规则分开；第 12 章讲技能、Hook 和插件，适合已经准备写扩展的读者。

## 怎样读代码例子

带实际文件名的原创示例都放在 `codex/examples/`。`review.rules` 可以直接交给固定 CLI 检查；`check-local-cli.py` 会核对版本并保存脱敏结果。正文中的 JSON-RPC 消息用于说明协议字段，有些方法需要启动会话，不能据此说本书已经调用模型验证。

命令默认从临时项目根目录运行。Windows 的 PowerShell 与 Bash 在引号、环境变量和命令拼接上不同，因此书中尽量把动态参数交给结构化数组。遇到较长提示词、JSON 或规则正文，先存文件，再传文件路径。少一层壳解析，就少一类“明明写对了却被改成另一条命令”的问题。

阅读中最应反复追问的是：这个动作由谁发起，由谁执行，失败被谁接住，留下了什么。掌握这四点之后，换一个模型或换一套终端界面，都不会让你失去判断依据。

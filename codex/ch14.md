# 第 14 章：把 exec 放进脚本，完成条件要自己写清楚

<!-- block: codex-ch14.b-opening -->
非交互任务应同时保存退出码、事件与最终输出，并用项目检查验证实际改动，不能只读取最后一句答复。

把交互命令放进 CI，不是简单地加一个 `--json`。终端里用户可以看到错误、拒绝审批或追问结果；脚本则需要明确的分支处理，否则一次失败可能变成空文件，一次超时可能被当作成功上传。

## 14.1 四种输出，各有用途

`exec` 的帮助列出 JSONL 事件输出、最终消息文件和输出 schema 等选项。它们解决不同问题：事件记录过程，最后消息面向读者，schema 限制最终结构，退出码表达进程结果。

```powershell
codex.cmd exec --json --output-last-message .scratch/result.md `
  --sandbox read-only "检查当前仓库的测试入口并列出缺少的验证"
```

这条命令需要读者自己的可用模型配置，未在本书真实运行。脚本应立即保存退出状态，再进行日志处理，避免后续命令覆盖原始结果。PowerShell 的 `$LASTEXITCODE` 与 Bash 的管道退出行为不同，应按所用 shell 实现。

钉版 exec 源码开头明确约定：`--json` 模式 stdout 必须是逐行合法 JSONL。不要向这个流里混入你自己的进度文字；诊断信息使用单独日志或 stderr。否则一个正常消息就可能把下游 JSON 解析器弄坏。

## 14.2 最终结构化输出不等于结构化全过程

```json
{
  "type": "object",
  "properties": {
    "summary": {"type": "string"},
    "checks_run": {"type": "array", "items": {"type": "string"}},
    "remaining_risks": {"type": "array", "items": {"type": "string"}}
  },
  "required": ["summary", "checks_run", "remaining_risks"],
  "additionalProperties": false
}
```

这是原创的最终报告 schema。`--output-schema` 可以用于约束模型最后回答的形状，但不能证明 `checks_run` 中每条命令真的执行过。要核实检查，仍应对照事件与实际测试日志。

字段设计应让不确定性有地方落下。如果只允许 `success: true` 和一段说明，失败时模型可能只能挤进不合适的结构。上面保留 `remaining_risks`，让未测项成为显式数据。业务系统也应允许失败状态，不能为了报表整齐把所有任务都改写成完成。

## 14.3 无人值守时处理审批

钉版 exec 通过进程内 app-server 客户端运行。其服务器请求处理函数会拒绝命令执行审批、文件变更审批与用户输入请求，MCP elicitation 则按取消处理；这些不是普通终端用户可随时点击的完整交互体验。把需要人工输入才能完成的工作流塞进普通 CI，会遇到明确的不支持路径。

正确做法是拆开阶段。前一阶段生成差异与报告，运行可自动完成的检查；后一个明确节点由有权限的人审阅，再触发发布或其他外部动作。这样批准对象是具体产物，而不是一段还没执行的泛泛计划。

## 14.4 失败不应被日志处理吞掉

钉版 exec 的事件循环给出了具体判断方法。它按主线程 ID 和当前回合 ID 筛选通知：当前回合收到不再重试的 `Error`，或结束状态是 `Failed`、`Interrupted`，就会设置 `error_seen`。关闭客户端之后，程序仍会调用 `print_final_output`，随后才根据这个标记以状态码 1 退出。程序写出了最后一段文字，仍可能以失败状态退出；脚本必须保留退出码。

中断也有明确对象。收到中断信号后，exec 发送带有当前 `thread_id` 和 `turn_id` 的 `turn/interrupt`，随后继续接收事件。用户按下 Ctrl-C 不是立即把当前任务的所有痕迹清空，已完成的文件修改仍要通过 Git 差异检查。

一个常见错误是 `command | tee log` 后只看最后一个程序的退出码。另一个是捕获异常后写出“请查看日志”，却让 CI 返回零。这样流水线会绿，但实际任务失败。

跨平台脚本可以使用结构化子进程调用，分别保存 returncode、stdout、stderr，然后决定退出码。即便需要上传失败日志，也应在上传之后保持失败状态。可观察性不应以隐藏错误为代价。

```python
# 教学框架：真实命令和凭据由使用者自己的 CI 配置提供。
import subprocess
from pathlib import Path

result = subprocess.run(command_args, capture_output=True, text=True)
Path("events.jsonl").write_text(result.stdout, encoding="utf-8")
Path("diagnostics.log").write_text(result.stderr, encoding="utf-8")
raise SystemExit(result.returncode)
```

`command_args` 在这里刻意留作调用者提供的参数数组，它不是可以原样运行的完整脚本。发布版脚本应加入超时、工作目录、编码和产物验证，并避免在异常中输出凭据。

## 14.5 任务完成的三道检查

第一道是运行完成：进程与回合到达明确终态。第二道是产物存在且可读：所要求的文件确实生成，内容不是空占位。第三道是行为正确：项目测试、构建或人工检查符合目标。

这三道检查互不替代。代理可以正确结束却没有实现需求；PDF 可以存在却打不开；测试可以通过却没有覆盖新分支。CI 应按任务风险选择证据，不能把某一个绿色标记扩大成所有结论。

对于修改代码的任务，还应在结束后保存差异摘要。必要时将产物、日志和基线提交关联，方便之后重现。不要把日志当成永久无限增长的存储；设置保留时间，并根据敏感程度控制访问。

## 14.6 固定输入，逐步扩大自动化

从只读分析开始，固定仓库版本和输入文件，比较多次运行是否输出结构正确、错误可见。再增加可逆文件修改，最后才考虑外部操作。这个顺序不是要求所有工作都手动完成，而是让每次扩大权限都能对应一组可检查行为。

对开放来源的仓库输入，要把内容视为数据。issue 正文、README 或日志中的句子可能看起来像指令，但它们不自动成为用户授权。工作流自身应说明哪些来源可以提供任务目标，哪些只用于分析。

# 第 13 章：上下文恢复与缓存

<!-- block: deepseek-ch13.b-opening -->
任务中断后继续对话，可能再次执行已经完成的操作。恢复时需要分别处理消息历史、运行状态和外部副作用。

## 13.1 恢复的是哪些东西

Session 日志可以重建模型历史、队列与投影，存储后端持有可写句柄，活跃 Agent 则有网络请求、计时器和当前取消信号。后者不能直接从 JSONL 复活，必须由新的运行实例重新建立。

所以恢复不是序列化整个进程。插件把一个 socket 放进内存 Map，重启后它不会因为会话存在就自动回来。应记录足够的业务标识重新取得资源，并明确资源不存在、已过期或已被别人占用时怎样处理。

## 13.2 不完整尾部需要语义判断

默认循环恢复时会通过持久化 write handle 取得历史，再补齐被中断 Turn 的关闭事件。存储层负责物理读取与写入排他，代理层负责“这一轮在语义上中断了”。把这两层分开，才能避免一个通用 JSONL 修复器凭空推断工具状态。

| 历史证据 | 可做的判断 | 不应自动推出的结论 |
| --- | --- | --- |
| 有请求，没有工具开始 | 调用可能尚未启动 | 外部系统必然没有副作用 |
| 有 tool/call，没有结果 | 结果尚未确认 | 可以安全重做 |
| 有完整 tool/result | 已提交一次结果 | 外部对象永远不会变化 |
| 有中断的 assistant 文本 | 用户已收到一部分内容 | 这是一条完整成功答复 |

“没有日志”有时只是日志尚未来得及写入，所以外部副作用最好拥有幂等键或查询接口。对于只读任务，可以较放心地重新读取；对于创建工单、付款或发布，则应先核对业务状态。

## 13.3 模型历史的投影不等于文件回滚

分支会话让模型从某个历史点继续，不会把工作区自动恢复到那一刻。模型看到旧代码片段，而磁盘已经是新版本，这种不一致必须由工具重新观察消除。读者可以准备一个文件，任务完成后修改它，再恢复旧会话询问当前内容；只有重新读文件的工具证据才代表现在。

纯消息投影也有相同边界。它能改变未来模型看到的表述，却不会撤销数据库事务或清除所有原始持久记录。需要遗忘或脱敏时，必须讨论实际存储、附件、备份与日志保留，而不是只在界面里隐藏一条消息。

## 13.4 缓存键为什么必须含身份

派生消息与请求冻结可以复用某些验证工作，但缓存不能只用文本内容判断。两个 Agent 的作用域、工具集合与路由可能不同；相同文字不代表相同请求。默认循环把冻结证据限制在同一 Agent 的消息身份内，避免跨实例错用。

应用层缓存也有各自的失效条件。README 内容可以用哈希或文件版本校验；审批结论则随策略、作用域和用户身份改变，不能永久缓存为 allow。

## 13.5 一份恢复演练记录

实用记录应至少包括原始版本、会话 id、停止位置、最后已提交事件、重启后的第一个请求和副作用计数。可以让一个工具在临时文件里追加唯一业务键，随后故意在返回前终止测试实例。恢复时先查询该键，再决定是否执行。这种实验能揭示“结果未知”的真正成本。

如果只测试正常关闭，再正常打开，验证的是保存与加载，不是崩溃恢复。两者都值得做，但报告应分开。并发恢复同一 sessionId 也应确认第二个写持有者被拒绝，避免两个合法实例互相破坏日志。

本册组件实验尚未覆盖完整 Session 持久化，这里给出的是固定实现的职责与复现设计。后续可先用本地模型替身和临时存储检查恢复过程，再加入真实供应商的差异，无需一开始就准备模型凭据。

## 13.6 从连续实例看“撤销入口”与“恢复状态”

提供者替换实验中，旧 ReviewTools.definitions 清空，新服务得到一张新表，reviewPlugin 重新注册。日志服务没有被移除，因此保留两次 plugin:load。这个结果来自明确的所有权：工具容器是可替换能力，记录属于另一个仍活跃提供者。

若连日志服务也移除，新 Journal 的数组会从空开始，因为它没有存储后端。重新激活可以重建服务能力，却不能恢复未持久保存的审查记录。

正式 Session 恢复需要历史、写句柄和新局部世界三个部分。读到历史不等于取得写权，取得写权也不等于模型和工具已装好。工厂在发布前组合它们，之后才释放输入。把恢复做成“读文件后直接 new Agent”，很容易漏掉排他与局部注册。

## 13.7 为副作用设计一个业务键

假设审查工具要创建远端问题单，可以使用项目、提交与规则标识组合出业务键。第一次请求发出之前就确定该键，服务端按键查询或去重。客户端断线后先查已有记录，再决定是否补发。这个键不依赖模型重复生成同一句话，也不依赖某次临时连接 id。

工具 callId 仍应保留，用来关联本次模型调用与结果；业务键用于识别外部操作是否已经完成。一次重试可以拥有新 callId，却继续使用同一业务键。反过来，用户有意创建第二张问题单时，应产生新的业务意图，不能因为正文相同就无条件去重。

外部服务若没有查询或幂等能力，结果未知就需要留待人工核对。本地日志无法替外部操作确认成功，恢复流程应在这里停下。

## 13.8 缓存失效可以用一张依赖表推演

审查结果依赖文本内容、规则版本与工具版本；执行授权还依赖用户身份、作用域和策略版本。只拿 text 的 hash 做所有缓存键，会在规则升级后复用旧判断，或把一个用户的批准借给另一个用户。

把可复用的纯计算与不可复用的执行决定分开。字符数只依赖文本和计数语义，可以缓存；这次是否允许读取某路径，则必须在当前授权条件下判断。返回旧字符数可能影响展示，复用旧权限可能改变实际可执行范围，两者风险与失效条件都不同。

消息身份、请求冻结与 scope 隔离都在限定复用范围。读缓存实现时，需要一起检查键的组成、值的所有者和撤销时机；身份字段缺失可能造成跨任务复用。

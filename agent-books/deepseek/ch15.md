# 第 15 章：安全、权限与执行环境

<!-- block: deepseek-ch15.b-opening -->
插件在 ctx 里取得的是服务，但插件文件本身仍然是可执行代码。一个工具受到审批，不代表加载它的 JavaScript 也被同一规则限制。理解这个差别，才能把权限配置放在真正有效的位置。

## 15.1 至少分四个边界

第一层是代码加载：你是否信任这个插件包及其依赖。第二层是模型可见性：模型是否会收到工具声明。第三层是运行策略：某次参数、身份和目标是否允许执行。第四层是执行环境：进程实际上能接触哪些文件、网络和凭据。

| 边界 | 主要问题 | 典型机制 |
| --- | --- | --- |
| 插件加载 | 是否运行这份代码 | 来源、版本、安装与激活 |
| 工具可见性 | 是否向模型公布能力 | scope、preset、schema 组装 |
| 调用审批 | 这次动作能否继续 | pre-execute、approval、guard |
| 系统隔离 | 被执行代码最多能做什么 | sandbox 后端、用户权限、容器 |

隐藏工具能减少模型误用，但恶意插件可以直接使用 Node API。审批能阻止某次工具主体，但已在初始化阶段发生的网络请求不在该次调用里。系统隔离限制最大权限，却不自动决定业务上“这次发布是否合理”。这些机制互相补充，不能用一个词替代所有边界。

## 15.2 审批与最终拒绝

工具管线的 pre-execute 可以产生 allow、deny 或 ask。ask 交给审批服务；没有可回答的通道、被拒绝或被取消时，不应继续执行。用户批准一次调用，也不应被解释成永久提升整个 Session 的权限模式。

普通协作策略之后还有 monotonic guards。它们可以拒绝或不表态，后来的监听器不能把已拒绝结论重新变成允许。这适合拥有者必须坚持的底线，例如工具只能处理某个目录，或者禁止某一类外发动作。

但是 guard 也不是操作系统沙箱。如果工具绕过已审查的参数读取别处，或者插件初始化直接访问文件，仍需执行环境约束。权限设计要先列出攻击者能控制什么：仓库文字、模型输出、工具参数、插件包，还是整个子进程；每种输入对应不同控制点。

## 15.3 插件管理会改变后续所有会话

本快照的 Plugin Manager 修改的是 profile，影响使用同一 profile 的会话。安装包、选择 bundle、启用 row 是不同状态。界面显示 enabled 表示保存的选择，不必然意味着插件成功加载；坏包可能仍被列出，并附上错误。

Host 插件在进程内执行，不能假定工作区沙箱也包住了新安装的 Host 代码。包管理器的构建脚本审批又是另一个边界。允许工具执行一次插件安装，并不等于已经审查所有依赖脚本。

开发插件时，先从本地包与无敏感环境开始。向宿主子进程传环境变量时只保留必要项；调试日志不要打印完整配置，因为代理、认证和服务地址可能包含凭据。可公开的证据应记录字段是否存在和来源，不需要公开值。

## 15.4 文件系统和进程要在同一执行世界

能力接口允许替换文件系统与子进程提供者。若文件读取发生在远程容器，shell 却仍运行在本机，同一个路径字符串可能指向两个不同文件。结果是模型先读 A 环境的代码，再在 B 环境运行测试，结论失去对应关系。

部署到远端时，要一起核对 fs、subprocess、shell、PTY 和语言服务的工作目录与路径映射。文件内容、命令输出和诊断位置必须属于同一工作世界。仅替换 shell 命令前缀不足以证明所有工具都已迁移。

## 15.5 哨兵文件实验

在允许目录内创建 inside.txt，在边界外创建只含无敏感标记的 outside.txt。分别请求读写、相对路径跳转和符号链接路径，再检查实际文件。网络则使用本地测试端点记录是否收到请求。这个实验应在临时隔离环境进行，避免拿真实秘密验证“能不能读”。

判定依据必须是实际读写与执行证据，不能只看模型说“我无法访问”。模型可能主动遵守提示词，却不代表底层确实拒绝；反过来，工具返回拒绝后模型仍可能猜出标记，所以也要查文件与服务端日志。

本册已运行的 Cordis realm 隔离只证明服务域独立，没有完成操作系统沙箱矩阵。Windows、Linux 与远程容器的支持情况需要逐平台记录，不能把一种平台的文档当成所有环境的实测结果。

## 15.6 用连续实例标出策略能管到哪里

policy veto 拒绝后，review_text 主体没有开始；但插件初始化早已执行，并向 Journal 写入 plugin:load。这个事实说明策略保护的是 book/execute 之后的那条调用路径。它既没有阻止插件文件被求值，也没有阻止插件主体安装监听器。

实验代码只做内存记录，但未知包的初始化可以调用任意同进程 API。即使 reject 始终返回 true，也不会撤销已发生的行为。审阅来源、决定是否加载插件、审批工具调用，分别发生在不同阶段。

如果希望“未经允许连读取文件都不能发生”，就要让限制落在真正的文件提供者或操作系统边界，并检查是否存在绕过提供者的直接 I/O。仅在模型工具入口加一个 if，能保护遵守该入口的代码，无法控制任意 JavaScript。

## 15.7 把审批对象保留到执行处

审批请求应包含足够具体的目标和操作。用户批准读取 A，执行器却在等待期间把路径变量改成 B，就出现检查与使用不一致。可以在接纳阶段取得参数快照，并在实际访问时再次确认解析目标仍满足约束；对可变化文件系统还要考虑符号链接和挂载变化。

本书 ReviewTools.call 使用 structuredClone 加顶层冻结，让普通调用者后续改原 args 不会改变这次 request。它只处理平面文本参数，因此没有完整路径问题。正式管线对执行身份与参数还建立更多快照和 token，目的正是让策略判断对应同一次实际动作。

授权说明还需要目标和范围。同一个工具名可能包含多个操作，参数才确定本次对象。复用批准时，应明确匹配目标、有效生命周期与策略版本；永久 allow 若范围不清，后来新增的能力也可能被放行。

## 15.8 日志本身也有访问边界

为了观察执行，记录者很容易把 args、result 和 error 全部序列化。这些字段可能同时包含代码、凭据、私人路径和远端响应。审查插件只需知道哪个调用完成、统计多少字符，就不必保存原文；将最少资料写入日志，可以减少后续传播范围。

错误文本也不能默认公开。底层请求异常可能包含 URL，URL 中又可能有认证参数。内部 reason、用户可读说明和模型 content 应分别处理；脱敏时保留错误类别与关联 id，避免把所有失败都擦成没有诊断意义的“发生错误”。

检查拒绝路径有没有读到边界外文件时，可使用前面的哨兵文件。已知的虚构标记便于判断读取结果，也避免暴露真实密钥，记录可以公开复核。

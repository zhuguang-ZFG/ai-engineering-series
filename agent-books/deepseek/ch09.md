# 第 9 章：模型适配器与流式协议

<!-- block: deepseek-ch09.b-opening -->
模型服务说“支持流式输出”，并没有说明工具参数怎样拼接、结束后是否还会补 token 用量、取消时已经显示的文字如何保存。Harness 需要一套比纯文本更精确的协议，才能让不同提供者进入同一条循环。

## 9.1 一个请求先绑定具体适配器

llm 服务提供统一消息与流词汇，适配器负责把某个 provider/model 路由转成供应商请求。prepareCall 解析适配器拥有的字段、默认值和能力，并绑定本次调用使用的具体适配器。后续插件卸载或路由更新，不应使已经准备好的同一调用突然落到另一个实现。

这与从全局 Map 每次重新查 provider 不同。前者让“我为哪个实现解析了参数”和“我实际调用哪个实现”一致；后者可能在热更新间隙拿到不同实现，导致已验证参数失效。排查版本问题时应记录绑定路由和实际 serving registration，而不只记录一个显示名称。

## 9.2 流有块边界

响应可能交错出现文字、推理内容和多个工具调用。StreamChunk 使用 index 关联增量块，block-end 给出组装完成的块。工具 arguments 在传输词汇里保留原始 JSON 字符串，不能在半个字符串阶段当成完整对象执行。

一个读文件调用的参数可能分两段到达：第一段只有 `{"path":"src/`，第二段才补上文件名与括号。UI 可以显示进度，但执行器必须等完整调用与 schema 校验。把“看起来像路径”当成可执行参数，会让截断流造成错误读写。

```text
块开始 → 多个 delta → block-end
多个块完成 → usage → finish
finish 后不再发送任何 chunk
```

这是阅读适配器的契约顺序，不是所有供应商网络 chunk 的原样形状。适配器需要把供应商特有的尾部 usage、终止标记和错误帧映射进统一协议；下游不应该再次猜测某一家 API 的细节。

## 9.3 失败信息与重试决定分开

LlmFailure 描述失败事实，例如网络故障、协议错误、取消、超时。是否重试由策略决定。供应商给出的 Retry-After 延迟是输入，不是授权无限重试的命令。

固定版本约定一次适配器调用代表一次供应商尝试，避免底层 SDK 和 Agent 两层同时重试。否则配置写着五次，实际网络请求可能远多于五次，日志也无法对应账单。代理层对 request-error 的恢复留下明确尝试与结束记录，失败尝试不应制造成功的 assistant message。

实现本地模型替身时，建议分别构造断流、正常结束却没有内容块、工具参数缺半边、usage 晚到以及取消与超时同时发生。固定版本的两个 DeepSeek 适配器会把无内容的 stop 结尾映射为 EMPTY_RESPONSE 错误，默认重试插件将其视为可重试；不能仅因网络协议正常结束就认定回答成功。每种输入只改变一个条件，并保存被规范化后的终止原因，不要只测字符串拼接成功路径。

## 9.4 取消是活的，历史是冻结的

默认循环冻结派生请求的历史与头部，但 AbortSignal 继续传播。冻结数据是为了防止发出后被插件篡改，取消信号则必须能让正在等待的网络 I/O 停下。把整个控制对象做成不可更新的快照，会使取消只改变界面按钮，却无法停止实际工作。

供应商流已经输出了一部分文字后断开，应保留那次尝试的状态与已交付文本。重试是否重复显示、是否进入模型历史，需要由结算规则解释，不能简单把两段文字连接起来假装是一条无中断回答。

## 9.5 重放状态不等于可随便换模型

适配器可以携带私有 replay metadata，用于重放供应商响应中的特殊状态。通用内容仍是权威；读取方无法使用私有状态时，应按契约退回通用转换并给出诊断，而不是认为历史损坏。

模型切换的实验应分别观察三类东西：通用消息是否保留，私有重放信息是否还能用，工具声明和能力是否改变。只比较最后回答文字，看不出协议边界。尤其不要把一个 provider 的私有 reasoning 标记直接转交另一个 provider。

本册没有运行远端适配器，也没有对供应商价格、速率或成功率给出结论。本章给出的顺序与失败职责来自固定快照，后续接入真实模型时，读者可以按这些边界设计小而明确的协议测试。

## 9.6 把同一块的增量放在一起看

StreamChunk 是按 type 区分的封闭联合。block-start 提供 index 与 blockType；text-delta 或 reasoning-delta 追加文字；tool-call-delta 还携带工具 id、可选 name 与 argumentsDelta；block-end 给出完整 ContentBlock。不同 index 可以交错到达，不能把网络收到顺序当成所有内容都属于同一块。

下面省略了供应商细节，展示本框架词汇中的一个参数流：

```text
block-start       index=1, blockType=tool-call
tool-call-delta   index=1, id=call-7, argumentsDelta={"text":"TO
tool-call-delta   index=1, id=call-7, argumentsDelta=DO"}
block-end         index=1, block=完整工具调用
usage             本次计量
finish            终止原因
```

这不是逐行可直接解析的 JSON，而是读协议的时序示意。工具执行需要完整 block 和后续校验；在第一段看见 TO 就提前调用，会把正常分片变成业务错误。与此同时，UI 可以显示模型正在组装工具参数，不必等全部完成才给用户反馈。

## 9.7 BlockAssembler 的丢弃决定影响两份数据

assembler 负责把增量重新组成 ContentBlock，同时收集 usage、finish 与 replayState。达到 max-tokens 结束时，工具调用可能被截断，固定契约会丢弃这些不安全调用；对应 replay envelope 的 per-block 项也必须一起删掉。只删内容、不删元数据，会让私有状态对错块。

replay metadata 与响应内容的排列和来源关联。后续请求只有在历史 provider 与目标 provider 注册到同一个适配器实例时，才按契约传回这些数据；显示名称或模型字符串相近并不足以判定兼容。

测试自定义提供者时，同时查看 blocks 与 replayState，才能发现误保留的工具块、usage 顺序错误或元数据错位。两个交错 index 的输入还可以检查实现是否错误地共用一个缓冲区。

## 9.8 错误对象、失败事实与策略分开

适配器可以抛异常，也可以用终止 finish 表达 error/aborted。LlmRuntime 规范化对外流，使消费者不必再为每家供应商写一套网络异常分支。原始错误对象和不可变失败事实仍需要保留，供日志与重试决策使用。

重试插件不应把任何抛错都归为网络抖动。请求准备、扩展中间件或工具结果处理失败可能表明插件代码本身有问题；默认循环将这些失败与适配器尝试失败区分。让“重试三次”包住整个任意插件链，可能重复执行已完成的副作用，也会把真正的程序错误隐藏成偶发连接失败。

连续实例中的 POLICY_DENIED、TEXT_REQUIRED 和 PLUGIN_UNLOADED 分别指向策略拒绝、参数类型错误和插件卸载。原因不变时，重试也不会改善结果；调用方需先根据失败类别决定是修改输入、调整策略，还是等待可用实例。

# 第 4 章：配置变更与故障隔离

<!-- block: deepseek-ch04.b-opening -->
插件出错后应用能否继续，要看错误发生在哪里。缺少依赖、配置不合法、初始化抛错和运行中的监听器抛错，各有不同的处理路径。

## 4.1 缺依赖与初始化失败是两条路

声明了必需服务而服务不存在，fiber 等在 PENDING；主体已经执行后抛错，则进入 FAILED。本书实验先验证这两个结果，避免把“没有执行”误判为“悄悄执行成功”。

初始化失败的插件先做三件事：写一条不受管记录、打开受管 effect、注册事件监听，然后抛异常。等待 fiber.await 会重新抛出原始错误；框架清理 effect 与监听器。随后挂一个健康插件，事件仍能被健康插件接收。

```javascript
const bad = root.plugin(ctx => {
  records.push('unmanaged:written');
  ctx.effect(() => {
    records.push('managed:open');
    return () => records.push('managed:closed');
  });
  ctx.on('book/probe', () => records.push('unexpected'));
  throw new Error('BOOK_INIT_FAILURE');
});
await assert.rejects(bad.await(), /BOOK_INIT_FAILURE/);
```

实际留下的记录是 unmanaged:written、managed:open、managed:closed，没有 unexpected。它证明了受管注册的失败回收，也说明已发生的外部效果不会自动倒带。

## 4.2 应用是否启动，另有一层决策

Cordis 能让某个 fiber 失败，不等于 dsh 会把缺失这项能力的应用宣布为就绪。启动组合里有必需能力，应用引导代码还要判断 readiness、错误报告和退出。Web 服务端口能监听，也不能证明创建 Agent 的工厂、持久化或模型路由已经可用。

检查启动失败时，先记录错误属于哪一层。模块找不到时连插件主体都没到；config schema 拒绝时不应继续用坏配置；服务依赖缺失时需要修补组合；网络连接失败时可能需要应用级重试。不同处理不能被一个 catch 后继续启动替代。

| 现象 | 应先保留的证据 | 常见误处理 |
| --- | --- | --- |
| 找不到插件模块 | 完整 specifier、解析位置 | 在别的目录装同名包 |
| 配置校验失败 | row id、字段和类型错误 | 删除校验后继续跑 |
| fiber 长期 PENDING | inject 与有效服务域 | 强行读取未提供服务 |
| 初始化进入 FAILED | 原始异常和清理记录 | 只打印“插件不可用” |
| 热更新后失去能力 | 更新前后组合与状态 | 把重启当成已修复 |

## 4.3 配置覆盖要看最终树

profile、home 和命令行 patch 形成有序层。补丁针对 row id 修改，可能替换整份 config，而非逐字段合并。要删除一项高层覆盖，通常应修改拥有它的层；在底层补更多值可能仍然被覆盖。

建议为每次配置实验保留两份 dump：改动前与改动后。比较插件 id、name、inject 相关配置和服务隔离信息。不要把包含 token 的完整配置提交到仓库；公开记录可以保留字段名、来源层和脱敏值。若 dump schema 会导入插件声明，也应按加载代码的信任要求对待，不能当成完全被动的文本查看。

## 4.4 热重载的旧配置与新配置

配置更新不应该造成“旧能力被撤掉，新能力却没能装上”的无人值守状态。dsh 的 app-boot 和 HMR 协调层处理更新、就绪和失败报告，具体保留哪些旧状态取决于该路径。本册读过固定版本文档与代码入口，但没有运行完整配置 HMR，所以不把“更新必然原子”写成保证。

练习可以使用一个不向外部发送数据的插件：配置只接受正整数 interval，每次触发记录序号。依次给它合法值、错误类型、合法值，观察拒绝发生在撤旧前还是撤旧后、旧监听是否仍工作，以及恢复后有没有双订阅。

运行期的异常也要另外测。事件 emit 是同步分发，不会自动等待返回的 Promise；异步监听器若忘了把错误交回有等待语义的链，可能成为未处理拒绝。waterfall 里的异常则会沿调用返回链传播。初始化失败回收的测试不能替代这些运行期测试。

恢复动作需要由能处理该错误的层执行：参数错误交给校验，暂时断线保留原因并有限重试，永久配置错误则停止相关能力。自动重启也要限制次数，否则持续错误会让插件反复注册、清理。

## 4.5 rawConfig 与 effectiveConfig 不总相同

fiber.ts 保存原始 config，也保存 `_effectiveConfig`。rawConfig 是下一轮激活会使用的原始输入；effectiveConfig 是已经交给插件主体，或最近一次成功保留实例的更新结果。候选配置经过求值和校验，并不立即发布成当前有效值。

假设运行中的 interval 是整数 5，用户提交字符串 wrong。活动 fiber 的 update 会先 resolveConfig；schema 拒绝时，不能把这个坏值当成已经生效的配置展示。读取界面若只显示用户刚保存的文本，就会让人以为程序已经采用了它；诊断应分别给出保存候选、有效实例和失败原因。

pending fiber 尚未取得必要注入，配置求值可能依赖那些服务，所以候选解析会推迟到激活。由此也能理解为什么“编辑配置成功”与“插件初始化成功”不能合成一个状态。一个配置值可能直到所需提供者出现后，才进入完整检查。

## 4.6 update 通过 waterfall 决定是否重启

更新流程保留 config 修订号、旧 epoch 和 committed 引用，再调用 internal/update。默认 next 会 restart；监听器可以不调用 next，自己处理可原位更新的值。发布 effectiveConfig 前还要确认修订号、epoch 和 committed 没被另一轮更新改变，防止晚到的 Promise 把新状态覆盖回旧状态。

如果第一次更新读取远端资料较慢，第二次更新很快完成，只有比较“这还是不是我准备的那一轮”才能避免倒写。单纯把最后 resolve 的结果当成最新配置，会让网络完成顺序替代用户操作顺序。源码中的修订检查就是为这种异步交错保留身份。

配置更新监听器若自行消费新值，便承担了实际更新正确性的责任。省掉 next 不只是“性能优化”，也意味着不执行默认卸载和重新激活。一个需要重建连接的配置却只改了显示字段，effectiveConfig 看起来新了，连接仍用旧值；这种错误应通过实际连接行为定位。

## 4.7 app-boot 的失败分类要落到具体行

固定文档给出了比“容错”更精细的表。启动时可选插件失败会警告并保留成功兄弟；启用的必需条目失败会清理应用并非零退出。条目根本不在 profile，或显式禁用，并不会仅因名字出现在全局 required 列表就使启动失败。

后续配置 HMR 不重新执行同一套启动审计，也不回滚整个更新。已有条目的配置 schema 被拒绝时，可以保留原实例与配置；新条目校验失败则保持不活跃。其他已成功兄弟的变化不因这件事自动撤回，因此不能把这项局部保护称为全配置事务。

脱离 apply 返回 Promise 的未处理异步拒绝，以及定时器等回调中的未捕获异常，会越过插件初始化的错误边界。app-boot 的 fail-loud 处理会尝试有时限的释放并退出，不再返回原操作。后台工作若纳入插件的 Promise 与 disposer，错误和清理就仍有明确的接收者。

# 附录 C：证据边界与复现

<!-- block: cursor-apxc.b-opening -->
闭源产品没有源码可查，能写稳的只有两类东西：文档声明，以及你能在自己机器上重复出来的行为。

## C.1 本书采用的口径

| 写法 | 依据 | 例子 |
| --- | --- | --- |
| 「文档说……」 | 官方文档页面，标注访问日期 | 权限令牌语法、配置字段表 |
| 「本次没有运行」 | 写作机器未安装该 CLI | 安装脚本、`agent --help` 的真实输出 |
| 「在你的机器上测」 | 需要账号与网络环境 | CLI 拒绝审批后的退出码、团队策略报错文本 |

不写的东西：内部实现、版本号、未经文档声明的默认值、把沙箱说成硬安全边界。

## C.2 文档自己划出的边界

团队管理员可以关掉 CLI 无头模式，让 `agent -p` 在发出提示词之前报错退出。文档同时写明：这个开关由成员机器上的 CLI 执行，服务端不校验，改过的客户端可以跳过它，CLI 读不到团队设置时运行照常继续。它是使用政策，不是安全边界。同一段还指出它管不到 Cursor SDK 这类其他无界面入口。

这类自我限定要单独记：读到「管理员可以禁止」时，先问一句由谁执行。

## C.3 每个结论都该带的三样东西

日期、来源、是否实测。缺任何一样，半年后都无法判断结论是否仍然成立。本书正文的每条引用都带访问日期（2026-11-13），实测的只有 Python 示例与本机可复现的命令形态。

## C.4 复现顺序

1. `command -v agent` 确认入口。
2. `agent about` 记录版本与账号。
3. 在一次性目录里跑 `agent -p "不要修改任何文件，列出目录"`，看默认是否只读。
4. 再测一次 `agent -p --force "创建 hello.txt"`，用 `git status --porcelain` 核对落点。
5. 把结果连同日期写进你的笔记，而不是记「这个工具有个 bug」。

## C.5 论坛才是报缺陷的地方

查 Cursor 的问题，第一反应通常是去 GitHub。`github.com/cursor/cursor` 确实存在，Issues 也开着，但打开 Issues 页显示的是「No results」；README 把渠道指得很清楚：

> Creating new posts on [our forum](https://forum.cursor.com/) for bugs or feature requests is much appreciated!

所以这个仓库更像门牌，不是追踪器。真正在动的讨论在论坛：下面四条都是 2026-11-13 打开核对过的主题，其中三条有 Cursor 员工（Colin）的回复。

版本变化看两处：`https://cursor.com/docs/cli/changelog` 是 CLI 的变更页，`https://cursor.com/changelog` 是产品级变更页。两者都不带可引用的版本号锚点，所以本书只记日期。

一条经验：有员工回复不等于已修复。看到回复时，去 changelog 里找对应条目；找不到就当作「已知问题，尚未确认修复」。判断依据是 changelog，帖子只是线索。

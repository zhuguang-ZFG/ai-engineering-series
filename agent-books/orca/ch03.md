# 第 3 章：配置、规则与技能落在磁盘哪里

<!-- block: orca-ch03.b-opening -->
Orca 不把配置收进一个总文件。安装包、用户数据目录、运行时档案、家目录、每个仓库根，五处各有归属；写错一处，效果为零，而且多半不报错。本章把五处认清楚，再分「规则」与「技能」各自落在哪一层。

第 1 章认程序，第 2 章认登记，这一章认落位。2.1 实测过的 `hookSettings` 字段在这里落位：它登记的脚本写在仓库根的 `orca.yaml`，它登记的策略来自机器上的 Settings——两条线索在 3.3 汇合。

本章的实测全部只读：目录列表、随包清单文件、三条 `skills` 子命令。写配置的效果（`orca.yaml` 是否真被照办）没有实测，3.6 逐条列出。

| 家 | 放什么 | 谁写它 | 本章证据 |

| 安装目录 `%LOCALAPPDATA%\Programs\orca` | 只读的程序与随包资源，更新时整包换 | 安装器 | 第 1 章实测；`resources/skills/` 见 3.5 |
| 用户数据目录 `%APPDATA%\orca` | 桌面设置、登记数据库、会话、日志 | 桌面应用与运行时 | 本机目录列表（3.2） |
| 运行时档案 `%LOCALAPPDATA%\orca\daemon-host-profiles` | 物化的 orcad 运行体 | 按版本物化 | 本机目录列表（3.2） |
| 家目录 `~/.orca` 与 `~/orca` | agent 钩子 shim、自定义键位；工作树基址 | Orca 与你 | 本机列表（3.2、3.4）；基址见第 2 章 |
| 你的项目仓库根 | `orca.yaml`、`.worktreeinclude`（提交进库）；`.orca/issue-command`（主 checkout 的本地覆盖，不进库） | 你 | 按文档（3.3） |

五个家有三条判别线。其一，安装目录是只读的：把它当配置目录，改的东西会在下次更新时消失。其二，用户数据目录是机器的：换一台机器不跟着走；仓库根的规则才跟着 git 走。其三，别被同名文件骗：附录 B 警告过 `stablyai/orca` 源码仓库根的 `.mcp.json` 与 `orca.yaml` 是仓库自用文件；本节说的 `orca.yaml` 是**你自己的项目**根上的同名文件，两处都真实存在，服务的对象不同。

## 3.2 机器上的规则：Settings 与用户数据目录

Settings 的官方说明把它分成若干面板：General、Appearance、Git、Terminal、Quick Commands、Agents、AI Provider Accounts、Chat、Browser、Artifacts、Integrations、Notifications、Voice、SSH、Remote Orca Servers、Shortcuts，另有 Repository 与 Floating Workspace（`docs/site/content/docs/settings.mdx`，按文档）。这些是「这台机器怎么用」的规则。

它们落在 `%APPDATA%\orca`——Electron 的 userData 目录。本机一次列表共 80 个条目（目录内容随使用变化），分两类看：

- Electron 常规件：`Preferences`、`Local State`、`Cache`、`Code Cache`、`GPUCache`、`IndexedDB`、`Local Storage`、`Network`、`Session Storage` 等，任何 Electron 应用都有。
- Orca 命名的：`agent-session-domain.db`、`agent-model-catalog.db`、`orchestration.db`、`mobile-notification-dismissals.db` 四个数据库（各带 `-shm`/`-wal` 的 WAL 伴生文件），`agent-hooks/`、`agent-session-authority.key`、`agent-session-runtimes/`、`agent-session-attachments/`、`codex-hook-trust.json`、`codex-runtime-home/`、`daemon/`、`logs/`、`plugins/`、`plugins-data/`、`profiles/`、`terminal-history/`、`ai-vault/`、`orca-runtime.json`、`orca-e2ee-keypair.json`、`host-installation.json`、`wsl-*.json` 一类。名字与功能对得上：会话域、编排、模型目录各有其库。

两条线索值得停一下。其一，`%APPDATA%\orca\agent-hooks\` 里本机有 `endpoint.cmd`、`agent-identities.db`、`last-status.db`（含 WAL 伴生）；文档说钩子端点就写在这里、每次钩子调用时重新读取，让长命的 agent 会话在应用重启后仍能找到活的服务器（`docs/site/content/docs/agents/hooks-memory.mdx`，按文档）。其二，自定义快捷键按文档存在 `~/.orca/keybindings.json`；本机没有改过键位，所以 `~/.orca` 下只有 `agent-hooks/` 一个目录——空缺与文档不冲突。

运行时档案在第三个位置：`%LOCALAPPDATA%\orca\daemon-host-profiles\<host 哈希>\<版本>\build-<构建号>\`。本机这一层下物化了一份运行体，顶层六项：`Orca.exe`、`icudtl.dat`、`snapshot_blob.bin`、`v8_context_snapshot.bin`、`resources/` 与 `.materialized.json`。目录名里的哈希与构建号是本机当次的标识，书上写占位；结构与第 1 章认过的 `orcad` 对得上（附录 B.2）。

## 3.3 提交进库的规则：两份共享配置与一个本地覆盖

仓库根放两份共享配置：`orca.yaml` 供项目默认值，`.worktreeinclude` 列要带进新工作树的已忽略文件。文档要求把**这两份**提交进库，团队共用；机密留在被引用的已忽略文件里。另有一个本地覆盖 `.orca/issue-command`：读的是**主 checkout** 的这一份，非空则胜过 `orca.yaml` 的模板；它按用户自己写的命令处理，不触发共享命令的那道确认（`docs/site/content/docs/model/orca-yaml.mdx`，按文档）。

`orca.yaml` 的键全部可选：

| 键 | 管什么 | 省缺时 |
| --- | --- | --- |
| `scripts.setup` / `scripts.archive` | 新工作树创建后、归档前跑的脚本 | 无项目脚本 |
| `setupAgentStartupPolicy` | `start-immediately` 或 `wait-for-setup` | `start-immediately` |
| `issueCommand` | 关联 GitHub/GitLab 条目的命令模板 | 无项目模板 |
| `defaultTabs` | 新工作树的首批终端页 | 常规初始行为 |
| `worktree.sharedDirectories` | 主 checkout 里共享进新树的已忽略目录 | 只用 Settings 的共享路径 |
| `environmentRecipes` | 每工作区环境配方 | 无 |

解析有纪律（按文档）：非法 YAML 或任何重复键，整文件拒绝——Orca 不取「最后一个重复值」；整文件上限 256 KiB（UTF-8 字节与 UTF-16 码元双双封顶），单字符串 64 KiB；`defaultTabs` 最多 256 条，`sharedDirectories` 只取前 100 条。一个 YAML 校验器接受重复键，不能证明 Orca 会接受这份文件。

哪份 checkout 供哪条规则，文档给了一张对照表，摘引如下：setup 脚本、启动策略与 `defaultTabs` 读**新工作树自己的** `orca.yaml`；共享目录规则与来源目录、复制规则、归档脚本读**主 checkout 的** `orca.yaml` 与 `.worktreeinclude`；`issueCommand` 读**主 checkout 的** `.orca/issue-command`，非空则胜过主 checkout `orca.yaml` 里的模板；清空该文件就回到 YAML 模板。改了特性分支里的清单不会更新主 checkout——建下一棵树之前先回主 checkout 确认。

Setup 与 archive 脚本还有一个「命令来源」三选（Settings → Repository，按文档）：

| Settings 选择 | 生效脚本 |
| --- | --- |
| `orca.yaml only`（shared-only） | 只跑 YAML 钩子 |
| `Local only`（local-only） | 只跑本机钩子 |
| `Run both`（run-both） | YAML 先、本机后，串成一条 |

2.1 实测的 `hookSettings` 就是这套选择落在登记表里的样子：`setupRunPolicy: run-by-default` 对应「新仓库默认跑 setup」，`commandSourcePolicy: local-only` 对应三选里的 Local only（E8 与同一份文档对照）。CLI 的 `--setup run\|skip\|inherit` 里，`inherit` 跟随的就是这个 Settings 策略。

Runner 侧还有一组变量（按文档）：`ORCA_ROOT_PATH`（主 checkout 路径）、`ORCA_WORKTREE_PATH`（新树路径）、`ORCA_WORKSPACE_NAME`（目录名而非显示名），另有 `CONDUCTOR_ROOT_PATH`、`GHOSTX_ROOT_PATH` 两个兼容别名。Windows 上 runner 用 `.cmd` 语法逐行调用、失败即停；把终端选成 PowerShell 不会让 setup 脚本变成 PowerShell 代码。

`.worktreeinclude` 是行式清单：一行一条字面路径，`#` 开头是注释；含 `*`/`?` 的通配与 `!` 取反被跳过；文件本体上限 256 KiB、至多 1 000 条候选；只复制已 gitignore 且现存的条目；复制预算 2 GiB 字节、50 000 个文件系统项。共享与复制是三种机制（按文档）：

| 机制 | 来源 | 进新树的结果 |
| --- | --- | --- |
| Settings → Repository → Worktree Shared Paths | 本机偏好 | 链接；macOS 有 APFS 克隆时克隆 |
| `worktree.sharedDirectories` | 主树的 `orca.yaml` | 链接/junction，改动双向可见 |
| `.worktreeinclude` | 主树的清单 | 私有副本，绝不回退成链接 |

## 3.4 agent 的规则文件归谁

Orca 尊重 agent 生态自己的约定（`docs/site/content/docs/agents/hooks-memory.mdx`，按文档）：每个 repo 的 `.claude/` 与 `.codex/` 配置由 Orca 读取，在 worktree 里启动 agent 时照跑；`CLAUDE.md` 与 `AGENTS.md`（仓库根或嵌套）属于 agent，Orca 不动它们，只在文件树里照常显示、可内联编辑。

Orca 自己管的钩子分两处写，都叫 `agent-hooks`，别混：

- `%APPDATA%\orca\agent-hooks\` 是服务器侧：`endpoint.cmd` 加两个数据库（3.2 已实测）。
- `~/.orca/agent-hooks/` 是 agent CLI 侧的 shim。本机八个文件：`claude-hook.cmd`、`claude-hook-impl.cmd`、`claude-statusline.cmd`、`claude-statusline.installed`、`codex-hook.cmd`、`cursor-hook.cmd`、`qoder-hook.cmd`、`orca-agent-hook.exe`——文件名对应它挂钩的那个 agent。

想改 agent 的行为，写 `CLAUDE.md`/`AGENTS.md`，读它的是 agent；想改工作树的生命周期，写 `orca.yaml`，读它的是 Orca；想改这台机器的默认，走 Settings，落在 userData。写错读者，同样一句都不会生效。

## 3.5 技能：随包清单、指南与全局安装

命令面在帮助文本的 Skills 组（摘引）：

```
Skills:
  skills installed          List installed skill selectors
  skills share              Publish selected skills behind one unlisted link
  skills list               List version-matched skill guides bundled with this Orca CLI
  skills get                Print a version-matched skill guide as Markdown
  skills install            Install bundled Orca skills globally via the community skills CLI
  skills update             Update Orca skills to the version this Orca build ships
```

随包的清单在安装目录：`resources/skills/current-manifest.json`。本机读到 `schemaVersion: 3` 与 11 条技能，每条形如 `{name, sourcePath, packageDigest, files}`；`sourcePath` 形如 `skills/<名字>`，与钉住提交 `c354ab3` 树上 `skills/` 的 11 个目录一一对应（按路径指认）。`files` 里每条记 `path`（技能是一个 `SKILL.md`）、`size`、`executable`、`classification`，外加三种 sha256：`exactSha256`、`textNormalizedSha256`、`identitySha256`——正文、规范化文本、身份各有各的摘要。旁边另有 `released-digests.json`，与一个不在 11 条清单里的 `agent-browser/` 目录；后者从哪来，本章未核对。第 1 章说过的「11 个技能只确认清单存在」到这里补齐了字段的形状，摘要仍未逐字节校验。

指南与桩在源码树的另两个目录（按路径指认）：`skill-guides/` 有 11 个与技能同名的 `.md`（最大 `orca-cli.md` 约 45 KB）与 4 个同名子目录，`skill-stubs/` 是小体量的同名桩加 `_shared/`。帮助文本说 `list`/`get` 给的是「bundled with this Orca CLI」的版本匹配指南——名字与这两个目录对得上。

三条只读子命令本机跑过：

- `skills list`：11 行「名字: 描述」，与清单的 11 个名字一致；`linear-tickets` 的描述自述是 `orca-linear` 的旧名、为存量安装保留。
- `skills get orca-cli`：打印该技能指南的 Markdown，frontmatter 的 `name`/`description` 与 `list` 里那条一致。
- `skills installed`：列的是**这台机器全局装了哪些**，按宿主家分组——本机输出的分组标签有 Cursor bundled、Claude Code home、Agent skills home、Codex home；每条三行：技能名 (短哈希)、一段描述、一行归属。名字与哈希因机器而异，书上不引具体值。

`installed` 与随包清单是两回事：前者是本机全局装了什么（`install` 说「via the community skills CLI」，装到全局），后者是这一版安装包带了什么。`install`、`update`、`share` 都会改状态，本章未执行。

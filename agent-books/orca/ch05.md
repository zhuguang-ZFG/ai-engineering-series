# 第 5 章：编排——协调者、worker 与消息体

<!-- block: orca-ch05.b-opening -->
第 4 章量的是并行的下限：两棵树互不踩文件。编排要的是下限之上的东西——多棵树各自有人干活、有人回报，结果落进同一本账。本章先立结论：Orca 的编排没有新造进程模型，它在第 2 章的两层登记之上加了一层记账与一个收件箱。Run 是命名空间，不是调度器（帮助文本）；协调者不轮询，它结束回合、等 Orca 叫醒（内置指南）；worker 由 `worker-start` 带着自己的工作树进场；一来一回都走消息，而消息体是任意文本，所以发送与消费各有严格语义。

第 2 章问一棵树怎样落地，这一章问多棵树怎样被组织成一支队伍。队伍里的协调者与 worker 本身都是 agent，分工不靠进程树，靠收件箱里的类型与去向。

本章实测九项（E22–E30），2026-11-23 在本机 1.4.269 上完成，全部只读，可按附录 C.2 复现。观测目录刻意选在没有绑定 Run 的地方，所以看到的多是负观测与空账本——形状是真的，账是空的。另有两类文本依据：本机 `orca orchestration --help` 与各子命令帮助（下文标「帮助文本」），以及随包的内置技能指南 `skills get orchestration --full`（下文标「内置指南」）。一个真实的编排闭环没有执行，5.5 逐条列出。

## 5.1 编排的单位是一个 Run

`run-create` 的帮助把 Run 的职责划得很干净（帮助文本）：「A Run is a namespace and home inbox. It never schedules or places workers. worker-start --spec creates one when none is bound; use run-create for Task graphs or a new goal.」——命名空间与家收件箱，从不调度、不放置 worker；`worker-start --spec` 在没有绑定 Run 时自己建一个，要画 Task 图或立新目标才用 `run-create`。它的用法行要求一句 `--objective <text>`：每个 Run 出生时带一个目标。

编排里的几个名词先说清：

### 术语

| 名词 | 在这里指什么 | 出处 |
| --- | --- | --- |
| Run | 一次编排的命名空间，带一个家收件箱；不调度 | 帮助文本 |
| 协调者 | 绑定某个 Run 的 agent；`run-use` 恢复它的账，worker 不用这条 | 帮助文本 |
| Dispatch | 一次派发的记录，也是远端 worker 的通信地址 | 帮助文本、内置指南 |
| worker | 被派出去干活的 agent，带自己的工作树与终端 | 内置指南 |
| Task | Run 里的活件，六种状态 | 帮助文本 |
| 消息 | 收件箱里的一条记录，九种类型之一（5.4） | 帮助文本 |

Run 记什么账：`run-list` 在本机只列出一条 legacy 行（实测 E22）：

```
$ orca orchestration run-list --json
{
  "ok": true,
  "result": {
    "runs": [
      {
        "id": "run_legacy_local",
        "objective": "Legacy orchestration state (inspect only)",
        "legacy": true
      }
    ]
  }
}
```

`run-show` 给出这条记录的账本细目，其中 `removedWork` 一段说明被清走的工作也留着账（实测 E26；只摘该字段，记录的其他字段从略）：

```
$ orca orchestration run-show --id run_legacy_local --json
{
  "coverage": "complete",
  "recordedSince": "<时间戳>",
  "tasks": 0,
  "dispatches": 0,
  "workers": 0,
  "terminals": 0,
  "activeWorkersAtRemoval": 0,
  "lastRemovedAt": null
}
```

任务数、派发数、worker 数、终端数、清走时还活着的 worker 数——一本账该有的科目都在。`recordedSince` 是当次安装的时间戳，书里只保留字段名。账本落在第 3 章确认过的 `%APPDATA%\orca` 数据目录，`orchestration.db` 是目录条目之一（只见过名字，内容未打开）。

记账之外，还有三组「空」的实测：`run-current` 问调用者自己绑了哪个 Run，返回 `{"runId": null}`（E23，退出码 `0`）——有账本不等于有协调者；`worker-list` 在没有 worker 的机器上返回空数组加 `scope: {source: "all"}`（E30，退出码 `0`）；`inbox` 列全机邮箱，空（E25）。不报错、只报「这里没有」，这是记账面的常态。

命令面：`orca orchestration --help` 列出 31 条子命令，其中 `coordinator-start` 与 `coordinator-stop` 标为「Retired: load the current orchestration skill」（帮助文本）——旧的常驻协调者退役，协调者就是当前这个 agent，配合 `run-create` 与 `run-use` 使用。

## 5.2 协调者：结束回合，等叫醒

绑定是协调者的身份来源。`run-use` 的一句「Resume coordinating a Run (workers never use this)」（帮助文本）把两边分开：恢复一个 Run 的协调权，worker 永远不用这条。`--takeover-legacy` 则「must run in the live coordinator agent terminal it binds; it preserves existing worker assignments」——接管旧账必须发生在它要绑定的、活着的协调者终端里，既有 worker 指派保留。

没绑定就调 Run 级动词，Orca 用一条错误把话说全（实测 E24）：

```
$ orca orchestration task-list --json
{
  "ok": false,
  "error": {
    "code": "run_required",
    "message": "No Run is bound. A coordinator creates one with `orchestration run-create`, or resumes its own with `orchestration run-use --id <run_id>`. No effects were applied."
  }
}
$ echo $?
1
```

三件事值得记：退出码 `1`；错误码 `run_required`，`task-*` 与 `gate-*`（E29）共用；响应里 `effectsApplied` 为 `false`——「No effects were applied」，报错不动账。错误体还带一条指向 `skills get orchestration --full` 的指引，修法就在里面。负观测比正观测更能说明边界：绑定不是可选的装饰，是 Run 级动词的准入。

协调者的核心纪律是不轮询。`ask` 的帮助一行（帮助文本）：「Ask the coordinator a question; Orca wakes you with the answer」——问出去就结束回合，答案以信件叫醒你，不是循环查询。收件箱的消费语义由 `check` 承担（帮助文本）：

- 默认：「return the bound Run's oldest unread FIFO batch and mark it handled.」——最旧的一批未读，整批取走并标记；
- `--peek` 只返回未读、不标记；`--all` 返回最近的、也不标记；
- 「A consuming check marks the batch it returns as handled, so the next check returns newer mail; no --ack is needed.」「A script that only watches the inbox must use --peek … and must never --ack, or it takes mail the agent never sees. Consuming checks belong to the agent itself.」——旁观用 `--peek`，消费只属于 agent 自己；脚本替它消费就是把信偷走（E28 实测 `check --peek` 在未绑定 Run 时也返回空批，退出码 `0`）；
- `check` 的响应丢了，用响应里打印的 `--retry-request <id>` 重取同一批（帮助文本）；写路径的结果不确定时，`request-show` 按请求号回答「已生效没有」（帮助文本）。

内置指南把同一件事写成操作纪律：一次叫醒拿到一整批，处理完整批再下一次 `check`；每次叫醒先把 `task-list --ready` 的 Task 起掉（「On every wake, start the Tasks `task-list --ready` shows.」）；不要 poll、不要 watch。

安全线一句（内置指南）：「Silence, a timeout, or `unverifiable` liveness alone never proves exit or authorizes autonomous recovery.」——沉默、超时、无法验证的活性，单独都不证明对方退出了；这条在 5.3 的 worker 观测里会用上。

## 5.3 worker：被派发的那一侧

worker 进场时自带身份。内置指南第一句：「If your prompt has a preamble with Task and Dispatch IDs, you are a worker: follow the preamble.」——prompt 里带 Task 与 Dispatch 编号的序言，你就是 worker，照序言做；有问题 `ask`，然后结束回合。

派发的入口是 `worker-start`。用法行（帮助文本，原为一行，这里按段断开）：

```
Usage: orca orchestration worker-start (--task <task_id> | --spec <text> | --spec-file <path|->)
  [--keep-open] [--on <saved-environment>] [--worktree <current|selector|new-child|new-top-level>]
  (--agent <agent> | --terminal <handle>) [--model <id>] [--effort <level>] [--name <name>]
  [--repo <selector>] [--retry-of <dispatch_id>] [--run <run_id>] [--json] [--full]
```

退出码的语义也写在帮助里：「The call exits 0 for ready, and in the concise view for a start whose turn was not yet observed (--full exits 1 for anything but ready). Failed or outcome_unknown exits 1 and JSON includes stage/failedStage, setup, effects, residualResources, and recovery commands when needed.」——`0` 有两种来路：ready，以及 concise 视图下「启动回合尚未观测到」的请求；后者既不能证明就绪，也不能证明已经启动。`--full` 视图里非 ready 一律 `1`（「--full exits 1 for anything but ready」）。`failed` 与 `outcome_unknown` 是 `1`，JSON 里带失败阶段、已做的设置、副作用、残留资源与恢复命令。

工作树由它开，指南把反着做列进「不要」：「Make checkouts yourself; let `worker-start` create a worker's workspace.」放置三选（内置指南）：`--worktree current` 用你自己的工作区；`new-child --name <short-name>` 嵌在你的下面；`new-top-level --repo id:<repoId> --name <short-name>` 是独立顶层。文件夹工作区也合法，但「`new-child` and `new-top-level` make Git worktrees, never in a folder project; never `git init` a user's folder.」（内置指南）

第 2 章的两条入口在这里合流：`--terminal <handle>` 复用既有终端，等于「已有 agent 就挂上去」；如果这批活根本不需要回报——用户会在那些会话里自己工作——就不起 worker，按工作区跑 `ORCA worktree create --name <name> --no-parent --agent <agent> --prompt "<brief>" --json`，然后结束回合（内置指南）。

并发有口径：「Start independent workers at the same time, up to about 4 at once, and start the rest as those return.」——一次 shell 命令里并发起，约 4 个为度，回一批再起下一批；分开的工具调用常常一个接一个跑，POSIX 与 PowerShell 两种写法在指南附带的 `references/parallel-start.md`；起完结束回合。跨服务器的口径是 `--on`（帮助文本）：「--on selects only the worker server; the Run and this command remain on the current Orca server.」——挑的只是 worker 落在哪台，Run 与这条命令留在本机；远端 worker 只按 Dispatch ID 寻址（内置指南）。

effort 有个坑，指南专门提醒（内置指南）：「take it from the dispatch's `--effort` or your process argv, not from a numeric `reasoning_effort`: that number is not on a 0–100 scale (claude-opus-5-5: low=5, medium=10, high=15, xhigh=40).」——进程参数里的数字不是百分制。

worker 的观测有诚实的记号。`worker-show` 的 `observation.agentWait`（帮助文本）：「Null means Orca looked and found no wait. An absent field means it never looked — an older host, an unverifiable worker identity, an unreadable pane, or an agent probe that did not answer in time — and never means the worker is not waiting. A waiting worker is healthy, not failed.」——`null` 是看过了、没在等；字段缺席是从没看过，**绝不等于**没在等。`worker-read` 取 `--source auto` 或 `--source transcript` 总能读（「Not every worker has a terminal.」）；`worker-stop` 会连带停掉它启动的每个 helper，但「Never deletes the worktree, setup terminal, configured tabs, or unrelated processes.」，停的结果说不清时 `stop_unknown`、退出码 `1`。配合 5.2 的安全线：可观测的「没动静」不等于「退出了」。

失败与恢复的规则集中在指南里，只摘主干（内置指南）：重试只在原因变了之后；`--retry-of <dispatch_id>` 指向最新的一次失败尝试；「After three failed starts in one `--retry-of` chain, the Dispatch circuit-breaks and the Task fails.」「Report the failure and stop automatic retries; never route around the breaker with a new Run or Task, or reset its count, including on restart.」；用户明确要求重开时，`task-update --id <task_id> --status ready --run <owning_run_id>` 把同一个 Task 放回，再 `worker-start --task <task_id> --run <owning_run_id> --worktree <placement> --agent <agent>` 起新链、计数器重来；可回收的失败启动终端用 `worker-release`（「Release the terminal of one settled supervised worker」），`worker-keep-open` 让完成的 worker 保持打开（帮助文本）。

## 5.4 消息体：类型、去向与消费

`send` 的用法行（帮助文本，只摘地址与正文相关部分）：

```
Usage: orca orchestration send --subject <text> [--to <run:id|dispatch:id|bot:name|legacy_handle>] …
       [--body <text> | --body-file <path|->] [--type <type>] … [--json] [--full]
```

`--type` 九种：「Valid --type values: status, dispatch, worker_done, merge_ready, escalation, handoff, decision_gate, question, heartbeat.」`--to` 四种地址之外有群发（帮助文本）：「Group addresses (@all, @idle, @codex, ...) reach the live Dispatches of your own Run; a sender in no Run must use run:\<id\> or dispatch:\<id\>. @worktree:\<id\> names one workspace.」——不在任何 Run 里的发送者必须点名叫 `run:<id>` 或 `dispatch:<id>`。worker 省略 `--to` 时默认回它的协调者，而且「mail sent after finishing, worker_done included, leaves the finished task unchanged」（帮助文本）。

消息体是任意文本，于是发送侧有两条规矩：

- 引号别自己扛。「For a long or multi-line body, write it to a file and pass --body-file \<path\> (or - for stdin); the CLI reads it on this computer, so no shell quoting applies.」——正文里有换行、反引号、引号都安全。
- 也别走 `orca.cmd`。第 1 章实测过的启动器护栏：`orca.cmd` 遇到 `orchestration send` 与 `orchestration reply` 以退出码 `2` 拒绝转发（`resources/win32/bin/orca.cmd:11-21`），理由正是 cmd.exe 会重新解析 `%*`，而消息体不该被 shell 二次解释。

类型约束还有细则（内置指南）：`worker_done` 必须带 `--outcome succeeded|failed`；`escalation`、`decision_gate`、`worker_done`、`heartbeat` 归 Dispatch 的精确信号，只对单个 Dispatch 发，不走群发地址。决策门是 Task 的闸：`gate-create`「Create a decision gate blocking a task」、`gate-resolve`、`gate-list`（帮助文本）；E29 显示未绑定 Run 时它们和 `task-*` 一样被 `run_required` 挡住。

收件箱的读法有三种视角（帮助文本）：「Without --terminal or --run it lists every mailbox on this Orca. --run \<run_id\> keeps all mail in that Run, including mail to its workers; --terminal run:\<run_id\> keeps only the coordinator mailbox.」每行正文预览 200 字符（「Rows preview each body in 200 characters」）。实测的三个空（E25 全机邮箱、E27 Run 视角、E28 `check --peek`）形状一致：`{"ok": true, "result": {"messages": []}}`，退出码都是 `0`。

## 5.5 这一章的边界

九项实测（E22–E30），2026-11-23 在本机 1.4.269 上完成，全部只读，可按附录 C.2 复现。它们共同的前提是**没有绑定 Run**：看到的 `run_required` 是准入边界，看到的空账本是空状态，不是编排运转的样本。legacy 行的 `recordedSince` 是当次安装时间戳，书里只留字段名。

没有做的事：

- 完整的编排闭环一次都没有跑：`run-create`、`task-create`、`worker-start`、`send`、`reply`、`worker-read` 无一执行；worker 的终端与 transcript 没有样本。
- `deny`、`worker-abandon`、`worker-release`、`worker-keep-open`、`dispatch --inject`、`task-update` 的状态迁移与 `reset` 未执行；`reset` 会删协调状态，只在用户放弃时跑（帮助文本）。
- 内置指南的行为描述按原文陈述、未实测：约 4 个的并发口径、三次失败熔断、`--retry-of` 链、effort 档位数字、worktree 放置决策树、远端按 Dispatch ID 寻址。
- `--on` 远端服务器、`ORCA_ENVIRONMENT` 与配对码未设置、未验证；`coordinator-start`/`coordinator-stop` 已 Retired，没有旧式常驻协调者的观测。
- `orchestration.db` 只确认存在（第 3 章的目录清单），内容未打开。
- 源码只按钉住提交 `c354ab3` 指认了四份规格文件——`src/cli/specs/orchestration.ts`、`orchestration-worker-specs.ts`、`orchestration-gate-specs.ts`、`orchestration-full-record-flag.ts`（GitHub API 目录清单），未逐行读实现。

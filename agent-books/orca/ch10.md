# 第 10 章：受控地动一次手——开一棵树，关一棵树

<!-- block: orca-ch10.b-opening -->
第 7 到 9 章不动任何东西。这一章第一次动，但动的方式只有一种：**做完即还原**。开一棵探针工作树，看清它登记成什么样，再关掉并核验零残留；把清理在规则全关时跑一遍，读它记什么账；把钩子开关拨下去、立刻拨回来，末态与基线逐字段比对。每笔动作拆成三步：先存基线，动一步核一步，收尾比对。第三部的方法论一句话：动词的答案只覆盖动词的字段——rm 说删了树，不说删了分支；分支删没删，要到管分支的那一层去问。

## 10.1 先读两层：repo 的行与 worktree 的行

动手前先把两层清单各读一遍。`repo list --json`（E79）的 `result` 只有 `repos` 一个键，本机当次 12 行。行键不齐是这条命令的第一个事实：11 个打底键（`addedAt`、`badgeColor`、`displayName`、`externalWorktreeVisibility`、`externalWorktreeVisibilityLegacy`、`gitRemoteIdentity`、`gitUsername`、`hookSettings`、`id`、`kind`、`path`）12 行全有；`upstream`、`repoIcon`、`projectHostSetupMethod` 出现在 11 行，`projectGroupId` 与 `projectGroupOrder` 出现在 7 行，`folderUpgradeGitRootPath` 与 `sourceControlAi` 各 1 行。条件键在场与否本身就是登记状态的旁证——12 行里恰有一行没有 `upstream`。树级字段一个都不在行上：没有 `repoId`、没有 `isMainWorktree`，`kind` 全部 `"git"`。`path` 两种形态并存（1 行反斜杠、11 行正斜杠），登记存的是什么形态，列表就报什么形态。

`worktree list --json`（E80）的 `result` 四键 `hostScope`/`totalCount`/`truncated`/`worktrees`，本机当次 18 行——12 棵主检出加 6 棵链接树，行数随登记的工作树数目走，别把行数当信息。每行 38 键，`id` 是复合格 `<repoId>::<path>`：仓库层发 GUID，树层拿它拼路径。`isMainWorktree` 12 行 `true`、6 行 `false`，主检出全在 `D:`，链接树全在 `C:/Users/zhugu/orca/workspaces/` 下，五个仓库挂着链接树。列表行里没有 `baseRef`、没有 `cliProvenance`——这两个键只在单记录里出现。

第三个观测定下本章探针的走法（E81）：本书的写作目录 `barreleye` 本身是一棵 git 工作树，但不在 Orca 登记里——在它里面问 `worktree current --json`，退出码 `1`，`selector_not_found`，消息「No Orca workspace contains the current directory: <路径>」。第 4 章在临时仓库里见过的同一条（E19），在本书自己的目录上同样成立。所以本章每个动词都显式给 `--repo`，不赌目录推断。

四种行形状收成一张表（键数是本机当次实测）：

| 视图 | 命令 | 键数 | 独有处 |
| --- | --- | --- | --- |
| 仓库行 | `repo list` | 11 打底 + 7 条件 | 无树级字段；行键不齐 |
| 树列表行 | `worktree list` | 38 | 有 `linkedItems`；无 `baseRef`、`cliProvenance` |
| create 记录 | `worktree create` 的 `result.worktree` | 42 | 比列表行多 `baseRef`、`cliProvenance`、`createdAt`、`creatorProvenance`、`workspaceLineage` |
| current 记录 | `worktree current` | 46 | create 记录的严格超集，多 `address`、`environment`、`linkedItems`、`parent` |

## 10.2 开一棵：两个拒绝与一张 42 键的登记

`worktree create` 先收两条拒绝（均退出码 `1`、`invalid_argument`、`_meta.runtimeId: null`——拒绝发生在 CLI 内，没到运行时）：缺 `--name`，消息只有一句「Missing required --name」（E82）；在未登记目录里不带 `--repo`，消息「Missing repo selector. Pass --repo or run from inside an Orca-managed worktree.」（E83）。两条都把修法写在消息里，且先校验、后动手。

真实的一次（E84）：`--repo id:<GUID>` 显式点名仓库，`--name` 与 `--branch` 同叫一个可回收的探针名，`--no-parent` 把谱系置空——不挂到任何调用上下文；`--setup skip` 不跑仓库钩子——第 3 章挂起的 `orca.yaml` 生效链路继续挂起，探针不背这个变量。退出码 `0`，`result` 五键：`worktree` 一张 42 键的登记，加 `lineage`、`workspaceLineage`、`warnings: []`（空）与 `catalogVersion`。登记里值得点名的：复合格 `id`、`identity.key` 形如 `wt2:local:<uuid>`、`projectId: "github:zhuguang-ZFG/ai-engineering-series"`、`hostId: "local"`、`path` 落在 `C:/Users/zhugu/orca/workspaces/ai-engineering-series/<探针名>`；`baseRef: "refs/remotes/origin/main"`——基点写的是远端跟踪分支的引用，不随本机哪份检出的当前状态走；`cliProvenance` 是 `{kind: "created-by-cli", createdAt, callerTerminalHandle: "term_<uuid>"}`——谁开的树，连调用方终端句柄都记进登记；`parentWorktreeId: null`、`lineage: null`——`--no-parent` 的效果直接可读；`sortOrder`、`lastActivityAt`、`createdAt` 三值同源（epoch 毫秒）；`catalogVersion` 带 `epoch` 与单调 `sequence`（当次 534）——注册表每次登记变动都有账。

git 侧同一时刻的交叉证：`git branch --list` 多出带 `+` 号的探针行（`+` 表示该分支已被另一棵树检出占用），`git worktree list` 多出探针一行——两层各记各的，层间不串。耗时 15.14 秒（当次值，含全量检出）。

## 10.3 关一棵：rm 的拒绝、极简答案与独立核验

关之前先进树里问一声（E85）：探针目录里 `worktree current --json` 退出码 `0`，46 键记录——刚开出来的树立刻可以被 `current` 寻址，登记不等你。46 与 42 的差集是四个键：`address`、`environment`、`linkedItems`、`parent`——单读视角比创建登记多出来的，都是「以现有树为对象」的字段。

`worktree rm` 不收 `current`（E86）：退出码 `1`，`invalid_argument`，消息原文「orca worktree rm needs an explicit workspace; --worktree current is not accepted for removal. Here, current is --worktree <复合格>; pass that instead.」，`data.current` 里 `resolution: "resolved"`、解析出的 `selectors` 数组、`nextSteps` 一应俱全——拒绝你的同时把解析结果和修法都递过来。删除必须点名，防止「我在哪就删哪」。

点名之后（E87）：`--worktree <复合格>` 加 `--delete-branch`，退出码 `0`，`result` 只有两键——`removed: true` 与 `catalogVersion`（序号已从创建时的 534 前进到 542，其间每次登记变动记一步）。没有分支证据。第 2 章引过的帮助原文在这里应验：「A removal result without branch evidence does not confirm branch deletion」——删树和删分支是两件事，rm 只对前一件背书。

所以分支删没删，去问管分支的那一层（E88）：`git branch --list <探针名>` 在两处检出里都是 0 行，`git worktree list` 回到两行（主检出加本书的 barreleye），探针目录从磁盘消失，`worktree list --json` 回到 18 行且无探针行。四路核验全过——`--delete-branch` 确实把分支删了，但这个事实是 git 侧证明的，rm 的答案里没有它。耗时 10.17 秒（当次值）。

## 10.4 清扫面：preview 的沙盘与 run 的账本

`workspace cleanup preview`（E89）的 `result` 两键 `evaluatedAt`/`rows`，本机当次 18 行，行 7 键（`worktreeId`/`repoId`/`repoName`/`displayName`/`branch`/`path`/`evaluation`），`evaluation` 全部 `{action: "keep", cause: "rules-off"}`。第 7 章观测时是 16 行、11 行 `not-removable` 加 5 行 `rules-off`——行数与 cause 分布都漂了，本书在两次观测之间没有执行过任何规则命令，`cause` 仍只当当次值记，不猜原因。第 7 章钉过的帮助原文在这里兑现：preview「Removes nothing.」——18 行全部 keep，一行都不动。

`workspace cleanup run`（E90）退出码 `0`，`result` 直接是一份运行记录，八键：`id`、`trigger: "cli"`、`startedAt`/`finishedAt`（相等）、`counts`（`removed`/`archived`/`kept`/`failed` 四个 0）、`freedBytes: 0`、`rows: []`。和 preview 的 18 行对照着读：沙盘列了 18 行、全部标 `rules-off`，run 的 `rows` 却是空——run 只记它实际考虑过的树，规则全关时一棵都不进账，`kept` 是 0 不是 18。规则不在命令面（第 7 章钉过：「Rules are set in Orca settings; these commands never change them.」），所以这次跑完机器上什么都没少——预览与执行对得上。

路由对照两条（E91、E92）：`workspace cleanup run --environment local` 放行，`result` 与不带旗标同八键同形；`workspace cleanup report` 的 `result` 三键 `running`/`nextRunAt`/`runs`，`runs` 已有两条——都是 CLI 触发的运行记录，条目形状与 E90 的 `result` 完全一致。第 7 章见过的空数组（E48）被今天的两次执行填上。

## 10.5 钩子开关：拨下去，拨回来，比对基线

`agent hooks` 管的是本机配置，它对 `--environment` 的态度与 `account list` 同款（E93）：退出码 `1`、`invalid_argument`、`_meta.runtimeId: null`，消息原文「`--environment` does not retarget agent hooks; run this command on the machine whose hooks you want to manage.」——改哪台机器的钩子，就在哪台机器上跑，连「问别处」都不给。第 7 章的 `agent hooks status` 不提供这条旗标，本章的 off/on 收下旗标却拒收——同一族命令，两种姿态拼成完整的「本机配置不路由」。

开关闭环（E94）压在一个调用里完成，让 off 的窗口只有几秒。基线（与第 7 章 E45 同形）：`enabled: true`、`appliedBy: "runtime"`、`settingsPath` 指向 `profiles\local-default\profile-state.db`、`statuses` 23 行（4 行 `installed`）。`agent hooks off` 退出码 `0`：`enabled: false`，23 行全部翻成 `not_installed`，claude 那行的 `managedHooksPresent` 翻成 `false`。紧接着 `agent hooks on` 退出码 `0`：`enabled: true`，回到 4 行 `installed`、19 行 `not_installed`。末次 `agent hooks status` 与基线逐字段比对：`statuses` 23 行逐行一致，其余字段一致，`appliedBy` 全程 `"runtime"`。拨下去有痕迹、拨回来无残留。「拨回来」拨的是基线，不是 `on`——本机基线恰好是 `on`，基线为 `off` 的机器收尾那步是再拨一次 `off`；「做完即还原」在配置面上就是这个样子。

## 10.6 这一章的边界

十六项实测（E79–E94），2026-11-23 在本机 1.4.269 上完成。与前九章不同，本章动过真状态：探针树的创建与删除、两次 cleanup run、一次 hooks off/on——全部做完即还原，复现命令连同 rm 之后的核验尾巴在附录 C.2。数值都是当次值：18 行树、`catalogVersion` 的序号、15.14 与 10.17 秒、23 行钩子、12 行仓库——可比的是字段形状、拒绝消息与还原核验的方法，不是数字。

没有做的事：

- `worktree create` 的默认谱系（不传 `--no-parent` 时挂到调用上下文）未观测；`--setup` 默认链（跑仓库钩子与 `orca.yaml`）未执行——第 3 章的生效链路继续挂起；`--issue`/`--pr` 挂接、`--copy-paths` 等其余旗标一条没碰。
- `worktree rm` 只测了 `--delete-branch` 且探针分支零提交：删树留分支（preserved branches）、有未合并提交时的保留判定、`--force` 均无样本；`worktree activate`、`worktree set`、`ports --all` 未执行。
- `workspace cleanup` 只在规则全关时跑过：开规则后的实际删除、`archived` 与 `failed` 计数、`freedBytes` 非零的行均无样本；`cause` 分布与第 7 章不同（全 `rules-off` 对 11+5 混合）只记观测，未查原因。
- `agent hooks` 只动了本机 4 行 `installed` 的状态：19 行 `not_installed` 在开关间的变化无样本（本机未装它们的钩子）；off 窗口里若有 agent 启动，钩子行为未观测。
- `--environment` 只验证了 `local`（cleanup 放行、hooks 拒绝）：未知名在这两组上的报错未测。
- 远端 host 上的 create/rm 未测；`callerTerminalHandle` 的 `term_<uuid>` 只记形状，未核它指向哪个终端。
- 引句逐字取自本机 1.4.269：三条拒绝消息原文照抄（E83、E86、E93），帮助文本只复用第 2、7 章已钉住的三句（rm 的「without branch evidence」、preview 的「Removes nothing.」与「Rules are set in Orca settings」），未新增逐字帮助引文。

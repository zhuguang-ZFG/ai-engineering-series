# 第 1 章：先确认跑的是哪个程序

<!-- block: orca-ch01.b-opening -->
`Orca.exe`、`orca`、`orcad` 是三个不同的东西。把它们对齐之前，任何关于配置、工作树或编排的判断都可能在跟错的对象说话。

装好 Orca 之后，你手上有四个可以各自回答问题的程序：桌面应用（你点开的那扇窗）、命令行启动器（Agent 在终端里调用的 `orca`）、本机运行时（会话与工作树真正跑在里面的服务），以及可以被配对到另一台机器的远端运行时。它们在同一个版本号体系下发布，却不是同一个进程。

这一章只做一件事：让你能说出「我刚刚确认的是哪一个」。所有命令都在写作机器上跑过，输出原样引用。

## 1.1 桌面安装目录里装了什么

<!-- block: orca-ch01.b-desktop -->
先认桌面包。桌面应用在 Windows 上装在用户目录下，不在 `Program Files`；注册表里的卸载项给出安装根：

```
DisplayName      Orca
DisplayVersion   1.4.269
DisplayIcon      C:\Users\<user>\AppData\Local\Programs\orca\Orca.exe,0
URLInfoAbout     https://github.com/stablyai/orca
```

这段取自 `HKCU\SOFTWARE\Microsoft\Windows\CurrentVersion\Uninstall\{GUID}`，`{GUID}` 是安装器分配的卸载键。路径里的用户名不要写进笔记：同一台机器上不同账号装出来的是不同副本。

安装根下 `resources/` 是承重墙，其余是 Electron 的常规件（`chrome_100_percent.pak`、`icudtl.dat`、`ffmpeg.dll` 一类）。`resources/` 里值得先认的几项：

| 路径 | 是什么 | 为什么先看它 |
| --- | --- | --- |
| `app.asar` | 桌面端打包后的应用代码 | 版本号与入口在这里 |
| `app-update.yml` | 更新来源声明 | 说明你装的是哪条发布通道 |
| `bin/orca.exe` | 原生命令行启动器 | 第 1.3 节的主角 |
| `orcad-template/daemon-entry.js` | 运行时守护进程的模板 | 第 1.4 节的主角 |
| `skills/current-manifest.json` | 随包技能清单与摘要 | 判断技能是否被换过 |

## 1.2 版本号有三个来源，对不上不是装错了

先看 `resources/app.asar` 里的 `package.json`。asar 是带头部 JSON 的归档，读出头部再定位文件即可：

```
name         orca
version      1.4.269
description  Next-gen IDE for parallel agentic development
main         ./out/main/index.js
```

`version` 与注册表的 `DisplayVersion` 一致，都是 `1.4.269`。`main` 指向 `./out/main/index.js`，说明 Electron 的主进程入口在打包目录 `out/` 下，不在源码的 `src/`。

再看仓库。公开提交 `c354ab3` 的根 `package.json` 写的是另一组数字：

```json
"name": "orca",
"version": "1.4.214",
```

以上两行分别在 `package.json:2` 与 `package.json:3`。同一棵树的 `main` 是 `./out/main/index.js`（`package.json:11`），包管理器固定在 `pnpm@12.18.0`（`package.json:421`）。

而 GitHub 上的发布页给出 `v1.4.269`，发布于 2026-11-21，与安装到本机的版本一致。三个数字的关系因此是：

| 来源 | 数字 | 指什么 |
| --- | --- | --- |
| 已安装的 `app.asar` | 1.4.269 | 你正在跑的这一份 |
| 发布 tag `v1.4.269` | 1.4.269 | 发布流水线打出来的那一份 |
| 公开提交的 `package.json` | 1.4.214 | 主干上最后一次可见的版本字段 |

结论不要说得比证据多：`package.json:3` 落后于发布 tag，说明主干上的版本字段不是在每次发布时提交的，把它当作「当前版本」会得出错误判断。要判断你手上这份是什么，读 `app.asar` 或跑 `orca --version`，不要读仓库的 `package.json`。

## 1.3 命令行是另一个可执行文件

<!-- block: orca-ch01.b-cli -->
命令行启动器也在同一个安装目录里。`resources/bin/` 下有五个文件，其中两个与 `orca` 命令直接相关：

```
journal-file-lock.exe
orca-administrator-restart.exe
orca-agent-hook.exe
orca.cmd
orca.exe
```

`orca.cmd` 是一层薄包装，只有 21 行。它把参数原样转给同目录的原生启动器，但为两个子命令留了护栏：

```bat
REM Why: cmd.exe reparses %%* and can execute/truncate embedded newlines. The
REM native launcher is the supported path for orchestration message bodies.
if /I "%~1"=="orchestration" if /I "%~2"=="send" goto :unsafe_body
if /I "%~1"=="orchestration" if /I "%~2"=="reply" goto :unsafe_body

"%LAUNCHER%" %*
exit /b %ERRORLEVEL%

:unsafe_body
echo orca.cmd cannot safely forward orchestration message bodies. Use "%LAUNCHER%" instead. 1>&2
exit /b 2
```

这段位于 `resources/win32/bin/orca.cmd:11-21`。注释里写明了理由：`cmd.exe` 会重新解析 `%*`，把编排消息体里的换行当成命令分隔符，轻则截断、重则执行。所以 `.cmd` 只转普通子命令，遇到 `orchestration send` 与 `orchestration reply` 直接以退出码 `2` 拒绝。

这条护栏本身就是一条结论：编排消息体不是普通的命令行参数，它可能包含任意文本。第 5 章讲编排时会回到这里。

## 1.4 运行时是第三个程序

`orca --help` 把命令分成若干组，其中「Startup」一组直接暴露了运行时：

```
Startup:
  open     Launch Orca and wait for the runtime to be reachable
  serve    Start a headless Orca runtime server
  status   Show app/runtime/graph readiness
```

`open` 是「启动并等到可用」，`serve` 是无界面的运行时服务，`status` 是自检。三者都围绕运行时转，而运行时不是 Electron 主进程：`serve` 能在没有窗口的情况下单独跑。

<!-- block: orca-ch01.b-runtime -->
守护进程就是运行时的实体：安装目录的 `orcad-template/` 里是它的入口，源码里这一段叫 `orcad`。入口是 `daemon-entry.js`，旁边是若干 worker 入口（`agent-identity-worker-entry.js`、`bots-db-worker-entry.js`、`claude-conversation-fork-worker-entry.js`、`computer-sidecar.js` 等）。名字已经说明了分工：身份、bot 数据库、会话分叉、计算机操作各自一个 worker。

源码里 `orcad` 的实现集中在 `src/main/orcad/`（`orcad-connector.ts`、`orcad-relay.ts`、`orcad-served-profile.ts`、`orcad-orca-account.ts`），WSL 一侧另有 `src/main/wsl/orcad/`（`wsl-orcad-watch.ts`、`wsl-orcad-deploy.ts`）。本机安装目录里 `relay/wsl/` 的存在与源码这一层对得上。

## 1.5 两条自检命令

判断这台机器上的 Orca 是否活着，只需要两条命令，都不改工程：

```powershell
$orca = "$env:LOCALAPPDATA\Programs\orca\resources\bin\orca.exe"
& $orca --version
& $orca status
```

第一条在写作机器上的输出是一行 `1.4.269`，退出码 `0`。第二条输出八行键值，退出码同样是 `0`：

```
appRunning: true
pid: <本机进程号，见文>
desktopWindowStatus: available
runtimeState: ready
runtimeReachable: true
runtimeConnectionState: connected
runtimeId: <运行时标识，见文>
graphState: ready
```

<!-- block: orca-ch01.b-worktree -->
这一次是在桌面应用已经运行的情况下取的，所以 `appRunning` 为 `true`；`pid` 是应用进程号、`runtimeId` 是运行时标识，两行都是本机这一次运行的值，不要抄进笔记当作配置。要读的是四个状态字段，其中 `graphState` 说的是工作树（worktree）与依赖图是否就绪，其余三个说的是进程与连接：`appRunning` 说应用在不在，`runtimeReachable` 说运行时能不能连上，`runtimeConnectionState` 说这条连接现在的状态，`graphState` 说工作树与依赖图是否就绪。

四个字段里只要有一个不是就绪值，后面章节的一切现象都要先怀疑这一层，而不是先怀疑模型或提示词。

## 1.6 这一章的边界

本章的证据分两类。安装目录的清单、`app.asar` 的 `package.json`、`orca --version` 与 `orca status` 的输出，都是写作机器上的实测，可以按第 1.5 节复现。源码层面的结论只到「文件与行能指认」为止：`package.json:3` 写着 `1.4.214`，发布 tag 是 `v1.4.269`，两者为什么不一致，本章只陈述现象，不推断发布流程。

没有验证的部分要列清：macOS 与 Linux 的安装目录结构没有实测；`orca serve` 没有在本机单独启动过；`orcad` 的 worker 分工是读文件名与源码目录得出的，没有逐个跑起来观察。`skills/current-manifest.json` 里共 11 个技能，本章只确认清单存在与摘要字段的形状，没有校验摘要是否与文件逐字节相符。

要确认这些，需要在对应平台上安装并保留输出。读到任何一条与本章不符的结果，先按第 1.5 节重跑，再往下判断。

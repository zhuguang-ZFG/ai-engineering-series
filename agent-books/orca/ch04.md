# 第 4 章：并行工作树的隔离边界

<!-- block: orca-ch04.b-opening -->
官方文档用一句话担保并行的安全：Orca 是 worktree-native 的，每个任务一棵自己的树——「这正是并行 agent 安全的原因：它们永远不会踩到彼此的文件」（`docs/site/content/docs/model/worktrees.mdx`，按文档）。本章把这句担保拆开核对，先立结论：两棵树并行时，HEAD、索引与 Orca 的窗口各归各的，对象库共享；边界只在三处打开——共享链接、复制副本、提交进库的内容。

第 3 章认的是「东西落在哪」，这一章认「并行时谁看不见谁」。git 层给事实：4.2 实测每棵树一份的状态与共享的对象库，外加 git 自己的一条硬约束。Orca 层给归属：4.3 实测登记的边界与跨树总览。被刻意打开的通道在 4.4。

本章的实测对 Orca 与你的仓库全部只读：git 的指针与管理目录、两棵树的 HEAD 与对象库路径、`worktree current` 在一棵未登记 git 工作树里的负观测、`worktree ps` 的输出形状，外加一个用完即删的临时仓库验证 git 的一条报错。`worktree create`、`rm`、`activate` 与 sleep/archive 一个都没有执行，4.5 逐条列出。

## 4.1 隔离的单位是一棵树

文档的模型（按文档）：每个仓库一个基 ref（通常 `origin/main`，2.1 的 `set-base-ref` 管它）；每棵工作树一个 start-from ref、自己的分支、磁盘上自己的文件、自己的 agent 终端。第 2 章实测过的 `baseRef` 与 `startFrom` 对上前两条，本章看后面几条。

生命周期把「圈进」写得更具体（按文档）：**Work** 步里「agent 终端、编辑器页签、浏览器页签、终端窗格都圈在这棵工作树里」；Review 步对着 start-from ref 看差异，Ship 步提交、推送、开 PR——用的都是这棵树自己的分支。删除把这棵树的目录与分支一起删掉（带确认）。

单位认清了，隔离才有处可查：git 层看状态（4.2），Orca 层看归属（4.3），被打开的边界单列（4.4）。

## 4.2 git 层：每棵树一份 HEAD 与索引

第 2 章的 `git rev-parse --git-dir` 说过：工作树不是独立克隆，元数据在主仓库 `.git/worktrees/<id>` 下。本章走进这个管理目录（实测）：

```
$ cat .git                                        # 工作树根
gitdir: <主仓库>/.git/worktrees/<id>

$ ls <主仓库>/.git/worktrees/<id>
COMMIT_EDITMSG  FETCH_HEAD  HEAD  ORIG_HEAD  commondir  gitdir  index  logs  refs

$ cat <主仓库>/.git/worktrees/<id>/commondir
../..

$ cat <主仓库>/.git/worktrees/<id>/HEAD
ref: refs/heads/<这棵树的分支>
```

两个指针对指：工作树根的 `.git` 文件一行 `gitdir:` 指向管理目录，管理目录里的 `gitdir` 文件一行指回工作树根的 `.git` 文件。`commondir` 的内容是 `../..`——从管理目录往上两级，共享区就是主仓库的 `.git` 本体。

每棵树一份的，是管理目录里的这些：`HEAD`（指向这棵树自己的分支）、`index`（这棵树自己的暂存区）、`logs/`（只有 `logs/HEAD`，记这棵树的 HEAD 走向）、`FETCH_HEAD`、`ORIG_HEAD`、`COMMIT_EDITMSG`。管理目录里的 `refs/` 本机当次是空的，按 git 的设计只放这棵树的私有引用；**分支本身在共享区**——`<主仓库>/.git/refs/heads/` 下（实测）。

两棵树并行时（实测，同一仓库的主检出与一棵工作树）：

```
$ git rev-parse HEAD                        # 工作树里
<工作树的提交号>
$ git -C <主仓库> rev-parse HEAD
<主检出的提交号>                             # 两个 40 位提交号不同

$ git rev-parse --git-path objects          # 工作树里
<主仓库>/.git/objects                        # 对象库只有一份
```

`git status --short` 也各报各的：工作树里未提交的改动，主检出看不见，反之亦然。这就是「不会踩到彼此的文件」的 git 侧事实——隔离不靠拷贝仓库，靠每树一份的 HEAD 与索引，加上一个共享的对象库。

分支共享还带出一条 git 的默认约束（实测，用完即删的临时仓库）：同一分支默认不允许两棵工作树同时 checkout——

```
$ git worktree add <路径一> w1
Preparing worktree (checking out 'w1')
$ git worktree add <路径二> w1
fatal: 'w1' is already used by worktree at <路径一>

$ git worktree add --detach <路径二> w1
HEAD is now at <提交号>            # git worktree list 显示 (detached HEAD)

$ git worktree add --force --force <路径三> w1
HEAD is now at <提交号>            # 强行越过拒绝，同一分支进了两棵树
```

拒绝是默认，不是必然：`--detach` 建出的树不挂分支，`--force` 给两次强行越过拒绝（两条路径都在同一临时仓库里实测，本机 git 2.54）。所以并行的树**通常**各占各的分支。Orca 侧的对应做法按文档：新树的分支名默认从工作区名派生，从挂接的 PR/议题/MR 建的则从条目派生（`docs/site/content/docs/model/worktrees.mdx` 的 Naming the branch），一棵工作区一个分支，把这条默认约束变成常态。

## 4.3 Orca 层：窗口圈进一棵树，登记是第二层

文档把两层关系说直了（按文档，「Using plain git」一节）：每棵 Orca 工作树都是真 git 工作树，你在里面照常 `git status`、`git rebase`、`git cherry-pick`，Orca 下次渲染就接上；反过来，你自己用 `git worktree add` 开的树是**外部的**，直到在 Orca 里把它 show 出来才登记。

「外部」意味着什么，本机有一次负观测（实测）：在一棵 git 工作树里跑 `worktree current --json`，这棵树没有登记为 Orca 工作区——

```
$ orca worktree current --json
{
  "id": "local",
  "ok": false,
  "error": {
    "code": "selector_not_found",
    "message": "No Orca workspace contains the current directory: <本目录>"
  },
  "_meta": { "runtimeId": null }
}
$ echo $?
1
```

git 层说「这是棵工作树」，Orca 层答「这里没有工作区」，退出码 `1`。第 2 章的两层登记在这里从反方向对上：登记是 Orca 自己的一层，不是 git 的事实。

登记过的工作区进跨树总览。`worktree ps` 的帮助一行：「Show a compact orchestration summary across worktrees」（帮助文本）。实测的输出形状：每个工作区一小段——名字与活跃时间一行、`--worktree id:<id>::<路径>` 一行、`environment` 与 `address`（`--environment <环境> --worktree identity:<identity>`）各一行、agent 与它的 `--terminal term_<id>` 一行、分支与 PR 状态一行、`live`/`pty`/`unread` 三个旗标一行、preview 一行收尾。名字、identity、terminal id、PR 号是本机当次的值，书上只固定形状；`ps` 不挑当前目录，一次列全 host 范围内的并行状态——「并行」在这里是最直接的观测面。

把登记过的树调回前台用 `worktree activate`——「Open a worktree on its host, waking a sleeping recipe VM」（帮助文本）：唤的就是 Work 步圈进去的那组窗口。`repo set` 的 non-Orca worktree visibility（第 2 章 2.1 摘引）管的则是外部树在界面里显不显。

## 4.4 被打开的边界：三条通道与一条天然通道

新树是干净 checkout（按文档）：依赖、缓存、gitignore 里的本地机密都不在，直到你重建。边界不会自己留缝，Orca 刻意打开的通道就是 3.3 的三条机制，这里只看隔离含义：

| 通道 | 边界状态 | 隔离含义 |
| --- | --- | --- |
| Settings → Repository → Worktree Shared Paths | 链接；文件系统支持克隆时（如 APFS）为克隆 | 链接=双向，改动互通；克隆=各改各的 |
| `worktree.sharedDirectories`（orca.yaml） | 链接（Windows 先 junction 后 symlink） | 双向：谁改共享目录，另一边立刻看得见 |
| `.worktreeinclude`（orca.yaml） | 私有副本，绝不回退成链接 | 各树各改各的，边界保持 |

第二条要停一下：链接把这一块边界**永久打通**。两棵并行树里各有一个 agent 时，谁动了共享目录，另一边立刻可见——并行安全在链接的路径上不成立。哪些目录进 `sharedDirectories`，就是在选哪些路径放弃隔离，这是 3.3 表里第三列「进新树的结果」的代价面。

天然通道是提交进库的内容：`CLAUDE.md`、`AGENTS.md`、提交了的 `.claude/`、`.codex/` 配置随 checkout 进每棵新树，各带一份（读它们的是谁，3.4 已分）。没提交的本地文件一条也不跟过去——三条通道补的正是这个缺口。

`ports` 的帮助一行「List the listening ports Orca detected for a workspace」：按工作区报端口，未执行。

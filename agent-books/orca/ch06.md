# 第 6 章：远端——把树送出去，还是把运行时送出去

<!-- block: orca-ch06.b-opening -->
第 5 章把 worker 派到别的机器时只用了一个开关：`--on <saved-environment>`。这个「saved environment」从哪里来、和 `--host ssh:<id>` 有什么区别，当时留在了边界里。这一章补上：远端不是一层，是两条路。一条把工作树与终端送出去，运行时仍在本机（SSH）；另一条把整个运行时送出去，本机只剩客户端（Remote Orca Server）。命令行用两套地址把它们分开——`--host ssh:<id>` 与 `--environment <name>`；`host list` 用一张表回答「我能目标谁、该传什么」；配对存储（pairing store）是后一套地址的登记处。读这一章最重要的收获不是记住命令，而是知道每个读命令只回答一台机器：地址是选择器，不是重定向开关。

## 6.1 两条路：树出去，还是运行时出去

官方文档把运行方式排成四种：本机、SSH 目标、Remote Orca Server、按工作区起的 Cloud VM（`docs/site/content/docs/ways-to-run.mdx`）。前两种与后两种的分界不在网络，而在**运行时属主**。

SSH 那条路，Orca 仍在你手上跑。文档的原话（`ways-to-run.mdx`）：「When you create a worktree, pick that host under **Run on**. Agents and `git worktree` run on the remote; the editor, diff, and UI stay on your laptop.」第一次连接时远端要装东西，装的是什么也写明了（`docs/site/content/docs/ssh.mdx:44`）：「On the first connect, Orca installs itself on the host over your own SSH connection; Settings lists these under **Orca on your SSH hosts**. Your code and files stay where they are. Only Orca's list of projects, tabs and terminals moves to the host.」——代码与文件不动，动的是一份项目、标签与终端的清单。

Remote Orca Server 那条路反过来（`docs/site/content/docs/remote-servers.mdx:8`）：「A Remote Orca Server lets one computer do the work while another computer provides the UI. The server keeps the projects, worktrees, terminals, tabs, provider accounts, and agent sessions. Your laptop connects to that running Orca instance.」——服务器拥有项目、工作树、终端、标签、账号与会话，本机只是界面。

两条路的差别可以排成一张表（`ways-to-run.mdx` 的对比表与 `remote-servers.mdx`）：

| | SSH 工作树 | Remote Orca Server |
| --- | --- | --- |
| 运行时属主 | 本机的 Orca | 远端机器（桌面应用或 `orca serve`） |
| 断线之后 | 远端的 agent 继续跑，本机重连后接回 | 完整会话状态都在服务器上 |
| 多客户端 | 一台笔记本驱动那台主机 | 桌面、网页、手机与自动化可以共享同一运行时 |
| 典型搭法 | 导入 SSH 配置，在工作树里选 **Run on** | 共享服务器应用或跑 `orca serve`，再用链接配对 |

配对链接的性质，文档说得比帮助更重（`remote-servers.mdx:79`）：「The pairing URL grants access to this Orca runtime. Treat it like a password and send it only to the client you intend to pair.」权限按客户端分（`remote-servers.mdx:122`）：「Orca creates a separate, revocable token for each paired client.」换链接只顶掉没用的那张（`remote-servers.mdx:125`）：「Generating another link replaces the previous **unused** link. Clients that already paired keep their own grants until you revoke them.」——已经配过的客户端不会被新链接挤掉，要收回得逐个撤销。

还有一个第 1 章式的坑：Linux 上这个程序不叫 `orca`（`remote-servers.mdx:137`）：「The Linux CLI is named `orca-ide`, because GNOME Orca's screen reader already owns `/usr/bin/orca`.」同名不同物，正是第 1 章「先确认你在跟哪个进程说话」的远端版本。

服务器侧的配对入口是 `orca pair`（帮助文本）：「Asks the Orca running for this profile (desktop app, `orca serve`, or its service) for a pairing offer. Nothing restarts and existing clients stay connected.」不带 `--mobile` 时打印一条给另一台 Orca 的访问链接，带 `--mobile` 时打印手机用的二维码与链接（`src/cli/specs/pair.ts:20-21`）。这条命令本章没有执行——它是写操作，会生成配对要约。

## 6.2 三种地址：一张表回答「该传什么」

`host list` 的帮助把它的职责写成了一句话（帮助文本）：「Answers "what can I target and what do I pass" in one place: this machine, the SSH targets registered on it, and the Orca servers paired with it.」紧接着是最容易踩的那条（`src/cli/specs/environment.ts:24`）：「The three kinds are reached differently. A paired Orca server is a connection, selected with `--environment <name>`. An SSH target is a machine the connected Orca host reaches, selected with `--host ssh:<id>`. Passing one where the other belongs is the most common way to get an empty or missing-host answer.」——把服务器地址塞给 `--host`、或把 SSH 目标塞给 `--environment`，得到的是「空」或「找不到主机」，而不是一条解释。

本机实测（E32）：一次 `host list --json` 返回 8 行，1 条 `kind: local` 加 7 条 `kind: ssh`；local 行带 `name`、`id`、`selector`、`machineName`、`platform: win32`，ssh 行带 `name`、`id`、`selector` 与 `connected: false`，没有 `platform`。行数与目标名是当次值，书里不引；形状与帮助的说明对得上——SSH 行「include the detected remote platform after that target has connected」，没连过的就报 `platform unknown`（帮助文本）。

三个 kind 的对号入座：

| kind | 怎么寻址 | 谁回答 | 本章观测 |
| --- | --- | --- | --- |
| `local` | `--host local`（也接受 `this machine` 这类打印出的名字） | 本机的 Orca 运行时 | E32 一条；E33 的 `host name` 报 `machineName` 与 `platform: win32` |
| `ssh` | `--host ssh:<target-id>` | 本机运行时里登记的 SSH 目标 | E32 七条，全部 `connected: false` |
| 已配对服务器 | `--environment <name>` | 本机的配对存储 | 本机为空（E31），未观测到行；字段按帮助与源码陈述 |

`host name` 是另一个小工具（E33）：不带 `--name` 时「prints the name and platform the answering runtime reports」，带 `--name` 时「updates the answering runtime over its authenticated connection」（帮助文本）。实测输出只有 `machineName` 与 `platform` 两个字段，退出码 `0`；`_meta.runtimeId` 是当次的运行时标识，和 `host list` 里那条 `"runtimeId": "local"` 不是同一种东西——前者是这次进程的编号，后者是「本机」这个固定别名，不能互相替代。

命令面还有一处表面差异值得记：本机 `orca --help` 的 Hosts 组只列 `host list` 与 `host rm` 两条，`orca host --help` 却列三条——`host name` 只在组帮助里出现；Environments 组同样如此，主帮助列 4 条，组帮助列 11 条。主帮助是摘要，组帮助才是全集；排查时别拿摘要当清单。

## 6.3 配对存储：`environment` 组

`environment add` 的用法把配对码的形态写死在例子里（`src/cli/specs/environment.ts:54-56`）：

```
Usage: orca environment add --name <name> --pairing-code <code> [--json]
  $ orca environment add --name work-laptop --pairing-code orca://pair?code=...
```

`orca://pair?code=...` 就是服务器上那条访问链接的协议头。存下来之后，`environment list` 回答的是本机账本（帮助文本）：「Answers from this machine's pairing store. `--environment` and `--pairing-code` are rejected rather than ignored, because there is no other host that could answer.」——`list` 拒收这两个参数不是疏忽，是因为「没有另一台主机能回答」。

本机实测（E31）：配对存储为空。

```
$ orca environment list --json
{
  "id": "local",
  "ok": true,
  "result": { "environments": [] },
  "_meta": { "runtimeId": "local" }
}
$ echo $?
0
```

空账本之外，四条负观测把「选择器不是路由」演示得很干净（E34–E38）：

```
$ orca environment show --environment no-such-env --json
{ "ok": false, "error": { "code": "invalid_argument", "message": "Unknown environment: no-such-env" } }
$ echo $?
1
```

```
$ orca environment status --environment local --json
{ "ok": false, "error": { "code": "invalid_argument",
  "message": "--environment local names this machine's own Orca, not a saved environment, so `orca environment status` cannot act on it.",
  "data": { "nextSteps": [ "Run `orca environment list` to see saved environments." ] } } }
$ echo $?
1
```

`environment list`、`environment show`、`environment status` 三条对 `--environment local` 的拒绝是同一句式：`local` 指「本机自己的 Orca」，不是一条保存的环境。选项说明里那句「or `local` for this machine's own Orca over `ORCA_ENVIRONMENT`/`ORCA_PAIRING_CODE`」是通用措辞，落到 environment 这组读命令上并不放行——实测三次都退出 `1`。`host list --environment local` 的拒绝理由更直接（E37）：

```
$ orca host list --environment local --json
{ "ok": false, "error": { "code": "invalid_argument",
  "message": "`--environment` does not retarget `orca host list`. It answers from this machine's own pairing store, so a routed answer would name servers paired with a different machine.",
  "data": { "nextSteps": [ "Run `orca host list` on that machine to see the SSH targets registered there.",
                          "Drop the flag to answer for this machine." ] } } }
$ echo $?
1
```

理由一句话：一份答案只能描述一台机器。要看另一台，就在那台上跑同一条命令——帮助里也这么写（`environment.ts:29`）：「SSH targets are read from this machine's own Orca runtime, so this lists that machine's targets and not another server's. Run `orca host list` on the other machine to see the targets registered there.」

`environment add` 缺参数时只报一行（E39）：`Missing required --name`，退出码 `1`。它没有走到配对那一步——真正配对需要一条有效的 `orca://pair?code=...`，本章没有执行。

## 6.4 托管服务器：版本与退役

`environment` 组里另外七条动词管的是「本机通过 SSH 部署出去的 Orca 服务器」：`status`、`update`、`rollback`、`recover`、`stop`、`forget`、`cancel-stop`。帮助给它们加了两条共同的注脚（`src/cli/specs/managed-server.ts:5-8`）：

- 「`--environment` names a managed Orca server this machine deployed over SSH (see `orca environment list`); it is a selector here, not a routing flag.」——选择器，不是路由；
- 「Runs on this machine's Orca desktop app, the same action as Settings > Orca on your SSH hosts. A runtime without the SSH registry (headless `orca serve`) refuses it.」——要求本机的 SSH 登记；无图形界面的 `orca serve` 没有这份登记，会被拒。

版本动作有分寸（帮助文本）：`update` 不带 `--force` 时，「an update that would restart over running terminals is deferred and reported, not applied.」——有终端在跑就推迟，只报告不执行；`recover` 遇到「a rejected build changed profile state」时「refuses rather than restart the previous build over it」，要 `--accept-changed-state --yes` 才恢复到启动前快照，代价是被拒构建改过的东西全部丢弃（`managed-server.ts:45`）。

退役动作把「证据」写进了语义（`managed-server.ts:61-62`）：

- `stop`：「Stops orcad on the SSH host and, once the host proves it exited, removes the server from this machine and disconnects the host. Its terminals end. Connecting the host again sets up a new server. Requires `--yes`.」
- 「If the host cannot prove orcad exited, the server stays linked and the refusal says why; nothing is removed on a guess. For a host that is gone for good, use `orca environment forget`.」

——停不掉就不删，账上留着并说明原因；主机永远回不来才用 `forget`。`forget` 只摘本机的登记（`managed-server.ts:77-78`）：「Nothing on the host is stopped: if it comes back, orcad may still be running there.」「The SSH host is left disconnected, since no Orca server serves it any more.」`cancel-stop` 则撤回一条 `orcad` 还没执行的停止。

这组语义和第 5 章的安全线是同一个思路：可观测的「没动静」不证明退出，所以删除必须等主机给出证据。

## 6.5 这一章的边界

九项实测（E31–E39），2026-11-23 在本机 1.4.269 上完成，全部只读，可按附录 C.2 复现。它们的前提是**本机没有保存任何配对服务器**：看到的空数组是空状态，看到的 `invalid_argument` 是选择器的准入边界，不是远端连通的样本。`host list` 的 8 行、`_meta.runtimeId` 的 UUID 与各目标名都是当次值，书里只保留字段形状与计数方式。

没有做的事：

- 配对一次都没有完成：`environment add` 只跑到缺参校验（E39），没有带真实 `orca://pair?code=...` 执行；`orca pair` 没有运行（它会生成配对要约），`environment rm` 也没有执行。
- SSH 连接没有建立：七条 `ssh` 行全部 `connected: false`，`platform` 因此缺席；`host rm` 未执行。
- `orca serve` 没有单独启动，`Environment Recipes`（`vm recipe doctor`、`vm env doctor`）与 Cloud VM 的 `orca.yaml` 配方没有运行；这部分只按文档陈述。
- 托管服务器没有对任何真实的已保存服务器执行过：`status` 只跑到 `--environment local` 的拒绝（E35），`update`、`rollback`、`recover`、`stop`、`forget`、`cancel-stop` 六条未运行。它们是写操作，且需要一台真实的 SSH 主机；语义按帮助文本与 `src/cli/specs/managed-server.ts` 陈述。
- 远端服务器上的项目、终端、会话与权限撤销没有观测；`remote-servers.mdx` 的「separate, revocable token」与「Shared Server Access」是文档口径，未在界面上核对。
- 平台只覆盖 Windows；Linux 的 `orca-ide` 命名、`--pairing-address` 与 `--bind` 按 `remote-servers.mdx` 陈述，未在 Linux 上跑过。
- 源码只按钉住提交 `c354ab3` 指认了三份规格文件——`src/cli/specs/environment.ts`、`src/cli/specs/managed-server.ts`、`src/cli/specs/pair.ts`，未逐行读实现；文档引用均为钉住提交下的 `docs/site/content/docs/` 路径。

读到与本章不符的结果，先按附录 C.2 重跑那几项观测，再往下判断。

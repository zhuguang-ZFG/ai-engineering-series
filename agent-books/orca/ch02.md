# 第 2 章：一次请求怎样落到 worktree 上

<!-- block: orca-ch02.b-opening -->
`git worktree` 只回答「目录从哪切出来」；Orca 在这层之上又记了一层：谁创建的、从哪个基点切、推到哪个远端、关联哪个条目。把两层分开看，每一层都有一条只读命令可以核对。

第 1 章的 `graphState` 只说工作树与依赖图是否就绪，没有说一个工作树是怎么来的。它的来历就是本章的题目：一次 `worktree create` 请求由 Orca 收下并协调，git 负责物化目录；两层各留一份记录。要判断「我的请求落到了哪」，先分清你在问哪一层。

本章的实测全部只读：`repo list`、`worktree current`、`worktree list`，加上 git 自带的 `worktree list`。创建与删除的完整闭环没有在本机执行，2.6 逐条列出。

## 2.1 先认登记方

worktree 不是凭空创建的，它挂在某个已登记的 repo 上。`orca --help` 的 Repos 组是这一层的入口（摘引）：

```
  repo list                 List repos registered in Orca
  repo add                  Add a project to Orca by filesystem path
  repo show                 Show one registered repo
  repo set                  Set a repo's non-Orca worktree visibility or browser profile
  repo hide                 Hide a project from Orca's sidebar
  repo unhide               Show a hidden project in Orca's sidebar again
  repo set-base-ref         Set the repo's default base ref for future worktrees
  repo search-refs          Search branch/tag refs within a repo
```

`repo add` 按路径登记，`repo set-base-ref` 定的是「以后的新工作树从哪切」——基点是仓库的属性，不是每次 create 时才决定的。本机 `repo list --json` 的一条 git 型记录（占位后）：

```json
{
  "path": "D:/…/<repo>",
  "kind": "git",
  "upstream": { "owner": "<owner>", "repo": "<repo>", "host": "github.com" },
  "gitRemoteIdentity": {
    "canonicalKey": "github.com/<owner>/<repo>",
    "remoteName": "upstream"
  },
  "projectHostSetupMethod": "imported-existing-folder",
  "hookSettings": {
    "mode": "auto",
    "setupRunPolicy": "run-by-default",
    "scripts": { "setup": "<安装命令>", "archive": "" },
    "commandSourcePolicy": "local-only"
  }
}
```

两个细节值得停一下。`kind` 只有 `git` 与 `folder` 两值，`folder` 型仓库只登记目录、没有 git 事实。`hookSettings.scripts.setup` 记的是一条设置命令，`worktree create` 的 `--setup run|skip|inherit`（帮助文本）决定它怎么被对待；具体何时执行，本章未实测。

## 2.2 一次 create 请求的参数面

帮助文本里 `worktree create` 的完整用法：

```
orca worktree create --name <name> [--repo <selector>|--project <id-or-name> [--host <host>]|--project-host-setup <id>] [--agent <id>] [--prompt <text>] [--model <id>] [--effort <level>] [--setup run|skip|inherit] [--base-branch <ref>] [--issue <number>] [--pr <number>] [--linear-issue <identifier-or-url>] [--gitlab-issue <number-or-url>] [--gitlab-mr <number-or-url>] [--comment <text>] [--parent-worktree <selector> [--parent-environment <environment>]] [--no-parent] [--run-hooks] [--activate] [--json]
```

按去向把参数分五类：

| 参数 | 去向 | 本章依据 |
| --- | --- | --- |
| `--repo` / `--project` / `--host` | 选登记方：哪个仓库、哪台机器 | 帮助文本；`repo list` 字段见 2.1 |
| `--name` / `--base-branch` | 落盘：目录名、从哪个基点切 | 帮助文本；布局见 2.5 |
| `--issue` / `--pr` / `--linear-issue` / `--gitlab-*` / `--comment` | 登记：关联条目与备注 | 帮助文本；字段见 2.3 |
| `--agent` / `--prompt` / `--model` / `--effort` | 建好之后启动 agent | 帮助文本；见 2.4 |
| `--setup run\|skip\|inherit` | 决定仓库登记的设置命令怎么跑 | 帮助文本；登记字段见 2.1 |

这条命令在源码里的说明文件是 `src/cli/specs/worktree-create.ts`，处理入口是 `src/cli/workspaces/worktree.ts`（钉住提交 `c354ab3`，按文件路径指认）。

帮助文本自带的示例里，有三条示范选择器怎么写：

```
$ orca worktree create --name agent-task --agent codex --prompt "hi"
$ orca worktree create --repo name:orca --name cli-test-1 --issue 273
$ orca worktree create --name linear-task --linear-issue STA-335
```

第一条 `--repo` 省略，后两条用 `name:` 选择器并挂外部条目号。`--repo` 省略时选谁、各条目类参数的接受格式，本章未实测，2.6 有交代。

## 2.3 落盘后的对齐

git 层最先能对上。在任一 Orca 工作树目录里跑 git 自己的命令：

```
$ git rev-parse --git-dir
D:/…/<repo>/.git/worktrees/<id>

$ git worktree list
D:/…/<repo>                                     <sha> [<branch>]
C:/Users/<user>/orca/workspaces/<repo>/<name>    <sha> [<branch>]
…
```

第一行输出说明：这个目录不是独立克隆，git 元数据在主仓库的 `.git/worktrees/<id>` 下。`worktree list` 的第一行是主工作树，其余行是工作树，可以带分支，也可以是 `(detached HEAD)`。

按钉住的源码，创建流程先完成 `addWorktree`，再调 `resolveCreatedWorktree`（`src/main/runtime/workspaces/creation/runtime-local-git-worktree-create.ts:187-238`）；215 行的注释写着此时「New worktree is now listable」。本章因此只对齐两层的记录，不把「谁先登记」当作结论。

Orca 层用 `worktree current --json` 对齐——在同一个目录里：

| 字段 | 本机当次值（形状） | 指什么 |
| --- | --- | --- |
| `id` | `<repoId>::<path>` | 登记主键：仓库 id 加工作树路径 |
| `identity.key` | `wt2:local:<instanceId>` | 选择器 `identity:` 后面那串 |
| `projectId` / `hostId` | `github:<owner>/<repo>`；`local` | 挂在哪个项目、哪台机器 |
| `path` / `branch` / `head` | 目录、`refs/heads/<branch>`、40 位提交号 | 与 git 层同一组事实 |
| `isMainWorktree` | `false` | 主工作树为 `true` |
| `baseRef` | `refs/remotes/<remote>/main` | 创建时从哪个基点切 |
| `pushTarget` | `{remoteName, branchName, remoteUrl, remoteCreated}` | 推送目标；`remoteCreated: true` 表示这个远端是 Orca 建的 |
| `createdWithAgent` | `<agent>` | 关联的 agent；类型注释说用于给补位终端做种子（`src/shared/worktree/types.ts:150`） |
| `workspaceStatus` | `in-progress` | 工作区状态 |
| `linkedWorkItem` | `{provider, type, number, url}` | 关联的条目 |

两个命令读的是同一个目录：一个报 git 的事实，一个报 Orca 的登记。路径、分支、提交号一致，两层才算对齐。这一对字段在源码里各有出处：登记表的读取实现集中在 `src/main/git/worktrees/catalog/`，推送目标另有 `src/main/git/remotes/worktree-push-target-setup.ts`（均按钉住提交 `c354ab3` 的文件路径指认）。

列表层是 `worktree list --json`：返回 `hostScope`、`totalCount`、`truncated` 与 `worktrees` 数组，主工作树也在数组里，`isMainWorktree` 为 `true`。

## 2.4 agent 从哪一步进来

帮助文本的行为段直接回答了这个问题：

```
Start agents with `worktree create --agent` (new checkout) or `agent launch`
(existing worktree). Both open a chat or a terminal per your Chat | CLI choice,
and take --model/--effort.
```

两条路：`worktree create --agent` 是「新切一棵树并启动」，`agent launch --worktree` 是「树已在，只启动」（后者在 Agents 组的说明是「Start an agent in a worktree」，帮助文本）。`createdWithAgent` 记着该工作树关联的 agent，但类型注释写明它的用途是给补位终端做种子，不能当作「从哪条路启动」的判据。第一条路在源码里分两侧：CLI 侧 `src/cli/workspaces/worktree-create-agent-launch.ts` 的 `createWorktreeWithAgent` 发出 `target.kind: 'create-worktree'`，主进程侧 `src/main/agent-launch/startup-agent-worktree-create.ts` 的 `createWorktreeWithStartupAgent` 调 `runtime.createManagedWorktree`（钉住提交 `c354ab3`）。`agent launch`（已存在的工作树）的对应实现本章未核对。

官方文档把工作树的一生排成五步：Create（建）、Work（终端与编辑器都圈在这棵树里）、Review（对着基点看差异）、Ship（提交、推送、开 PR）、Archive or delete（`docs/site/content/docs/model/worktrees.mdx`，按文档）。本章实测到的是第一步；后四步只引文档，第 5 章讲编排时会回到这两条入口。

## 2.5 基址、基点与清理

工作树落在哪由基址决定。本机布局是 `<基址>/<仓库名>/<工作树名>`：

```
C:/Users/<user>/orca/workspaces/<repo>/<name>
```

帮助文本的示例用同一布局：`--worktree path:/Users/me/orca/workspaces/orca/cli-test-1`。基址是项目登记的属性（`project setup-create --worktree-base-path <path>`，帮助文本），本机没有改过它。

基点决定从哪切。文档说每个仓库有一个基 ref（通常是 `origin/main`），每棵工作树另有自己的 start-from ref（同上文档）；2.3 实测的 `baseRef: refs/remotes/<remote>/main` 与之对得上。

删除是两层的合动作。帮助文本对 `worktree rm` 的说明只有一句：「Remove a worktree from Orca and git」——登记与目录一起删；文档补充删的还包括分支（同上文档）。两条本章都未实测。

命令面的其余部分（帮助文本摘引）：

```
  worktree show             Show one worktree
  worktree activate         Open a worktree on its host, waking a sleeping recipe VM
  worktree set              Update Orca metadata for a worktree
  worktree ps               Show a compact orchestration summary across worktrees
```

这些命令共用一套选择器语法（帮助文本摘引）：`--worktree` 接受 `identity:<identity>`、`id:<repo-id>::<path>`、`folder:<id>`（folder 型工作区才可用）、`name:<displayName>`、`branch:<branch>`、`issue:<number>`、`path:<path>`、`active` 或 `current`——2.3 的 `id` 与 `identity.key` 两个字段，正好对应前两种写法。

`worktree ps` 与 `workspace cleanup preview`（「Show what the cleanup rules would remove now」，帮助文本）都是只读，本章没有执行，2.6 列入未实测。

## 2.6 这一章的边界

实测是四项只读观测，共五条命令，全部在本机 1.4.269 上跑过，可按附录 C.2 复现：`repo list --json`、`worktree current --json`、`worktree list --json`（在任一 Orca 工作树目录里）与 git 的 `worktree list`、`rev-parse --git-dir`。帮助文本的引用出自同一次 `orca --help` 全文。

没有做的事要列清：

- `worktree create` 与 `worktree rm` 的完整闭环没有在本机执行，本章只在已登记的仓库上做只读观测。create 之后目录、分支与各字段是否如 2.2 的参数表所料，未验证；文档所说「创建在后台进行（git fetch 与 git worktree add 后台跑）」也未实测（`docs/site/content/docs/model/worktrees.mdx`）。
- `--issue` / `--pr` 挂接后 `linkedWorkItem` 怎么被填、hooks（`--setup run`）执行什么、`--repo` 省略时的默认仓库，未实测。
- 远端 host 上的 worktree（`--host`）与 parent/child lineage（`--parent-worktree`）未实测。
- 参数面在两棵树上不同步：本机帮助文本的 create 用法没有 `--surface chat|terminal`、`--branch <name>`、`--reference`、`--reference-site <id>`、`--retry-launch <operationId>` 这五个参数，钉住提交 `c354ab3` 的 `src/cli/specs/worktree-create.ts:8-9` 的 usage 字段有。引用参数时先说明出处是哪棵树。

# 第 11 章：链真跑，闸真拦——setup 链、rm 的闸门与 --delete-branch 的去留

<!-- block: orca-ch11.b-opening -->
第 10 章开树、关树、拨开关，全挑最安全的旗标组合走。这一章把挂起的事各补一遍：第 3 章挂起的生效链路真的跑一次——母树里提交一个六行哨兵 `orca.yaml`，按 `--setup` 四档各建一棵探针树，看谁跑了链、守护进程多开哪条会话；rm 的三道闸门各撞一次——旗标配对在 CLI 层、脏树在运行时层、分支去留在 `--delete-branch` 自己的判据里，两棵对照树把判据钉死：建点同头删，树内进头留。方法不变：先搭观测条件，动一步核一步，做完即还原，末态四路核验。

## 11.1 母树与哨兵：先把观测条件造出来

这一批先造一棵母树再谈观测（E95）：`worktree create` 带 `--setup skip`——母树自己不当实验对象，链这批不跑；基点落成默认的 `refs/remotes/origin/main`、head `65279cd`。回执与第 10 章 E84 同形：`result` 里 `worktree` 一张 42 键的登记，加 `lineage`、`workspaceLineage`、`warnings: []` 与 `catalogVersion`（当次序号 398；epoch 只记形状，序号跨批不可比）。谱系三键 `parentWorktreeId`、`lineage`、`workspaceLineage` 全空——第 10 章 E84 用 `--no-parent` 显式置空得到过同样的空，两种空在回执上不可分辨。

哨兵落进母树（E95b）：树内写六行 `orca.yaml`——setup 一条脚本、archive 一条——提交为 `464856b`（1 file changed, 6 insertions）。setup 那条的产物是 `.orca-setup-marker`，内容为工作树名；archive 那条备着，本批没观察到它的行为。从这一刻起，凡从 `ch11-ybase` 建出来的树，git 层都带着这份哨兵。

然后补第 10 章挂起的另一半（E95c、E95d）：不带 `--delete-branch` 的 `worktree rm` 回执 `{"removed":true}`，`result` 只有一键；git 侧 `git branch --list` 里 `ch11-ybase` 仍站在 `464856b`。删树留分支——第 10 章 E87 用 `--delete-branch` 补过「删」的那半，这里补上「留」的这半。另记一个形状漂移：第 10 章 E87 的 rm 回执是 `removed` 加 `catalogVersion` 两键，本批八次成功 rm 的 `result` 都只有 `removed`（E104b 多一个 `preservedBranch`）——同一安装上的漂移，只记观测不猜因。

## 11.2 四棵探针：--setup 的四档

矩阵一次跑四棵（E96–E99），全部从 `ch11-ybase` 建：`baseRef` 是 `refs/heads/ch11-ybase`、head `464856b`——哨兵随树检出，四棵的 `warnings` 都是空数组，`result` 的键集与母树同五个。四档分野一表收齐（时间与命令长度都是当次值）：

| 探针 | --setup | 标记文件 | 守护进程会话 |
| --- | --- | --- | --- |
| ch11-mdef | 默认 | t=7s 出现，内容=树名 | 两条 |
| ch11-minh | inherit | t=6s，内容=树名 | 两条 |
| ch11-mrun | run | t=6s，内容=树名 | 两条 |
| ch11-mskp | skip | 15s 无 | 一条 |

跑链的三棵，守护进程日志各记两条会话行：第一条 `startup-command-delivery` 不带命令——`hasCommand:false`、`commandLength:0`、`viaShellArgs:false`；第二条不到半秒后建立，`hasCommand:true`、`commandLength:97`、`viaShellArgs:true`——带一条 97 字符的启动命令，内容未记录。97 只作单点实测值：四个探针名等长，量不出它与名字长度的关系。skip 那棵只有第一条会话，标记文件 15 秒内不出现。标记的内容各等于自己的树名——四棵树、四个名字、四份对得上的标记：setup 脚本跑的时候，工作树名是活的展开值，不是母树里写死的字面量。第 3 章按文档摘引过的对照表说 setup 脚本读**新工作树自己的** `orca.yaml`，本批观测与之相容——链默认就跑；三档（默认、inherit、run）在本输出里不可分辨，都跑了链，inherit 继承谁的语义这批无从谈起（调用目录不在登记里），标到边界。

## 11.3 rm 的三道闸门：配对、脏树、豁免

rm 的帮助全文在本批开头钉下（`worktree rm --help`）。先立三句原文：选项行「Force worktree removal when supported; does not force branch deletion」——`--force` 只对树，不对分支；「Repo-defined orca.yaml archive hooks are skipped unless --run-hooks is passed.」——钩子默认不跑；豁免句「It requires --run-hooks and is rejected without it, because with no hook running there is no failure to waive.」——第二道闸在动手前就写好了。

第二道闸先撞（E102）：`--allow-failed-archive-hook` 不带 `--run-hooks`，退出码 1、`invalid_argument`，消息原文「--allow-failed-archive-hook waives a FAILED archive hook, but without --run-hooks no hook runs at all. Pass --run-hooks too, or drop the waiver.」——与帮助原文同义互证。回执 `_meta.runtimeId` 为 null、id 是字符串 `local`：拒绝没出 CLI 进程。第 10 章在 create 上见过的两段式（E82/E83 先校验、后动手），rm 同款：配对错在动手前拦。

第一道闸在运行时层（E100）：探针树里有 setup 留下的未跟踪 `.orca-setup-marker`，rm 退出码 1、`runtime_error`，消息原文「Failed to delete worktree at C:/Users/zhugu/orca/workspaces/ai-engineering-series/ch11-mdef. ?? .orca-setup-marker」——git 的短状态记号 `??` 原样进了拒绝消息，脏在哪、文件叫什么，一句带全。`_meta.runtimeId` 非空，且与本章 E101、E104b 的回执同一个值——拒绝发生在运行时。`--force` 开这道闸（E100b）：removed:true，紧跟着的 git 侧分支行里 mdef 还站在 `464856b`——`--force` 没碰分支，与选项行原文逐字相符。带 `--run-hooks` 也先撞同一道（E101 首次）：同一条消息、路径换成 ch11-minh；`--run-hooks --force` 才放行，回执与不带钩子同形，没有 `archiveHookOverride` 键——该键按帮助原文只在钩子已跑且失败、又被豁免时出现；本批没有钩子失败的样本，钩子跑没跑、跑了什么，回执里看不见。

配齐就放行（E103）：`--run-hooks --allow-failed-archive-hook` 在干净树上 removed:true——四棵探针里只有 skip 那棵干净（标记文件根本没生成）。批后核对：四条探针分支全在 `464856b`，树全消。

## 11.4 --delete-branch：两棵对照树定去留

帮助的分支段原文先钉（本批随全文钉下）：「On newer hosts with branch-choice support, Git worktree removal keeps the local branch, including with --force. Pass --delete-branch to attempt safe branch deletion, including branches that predated the worktree. Branches whose changes Orca cannot prove are already merged are retained.」判据就在末句——但它没说 Orca 拿什么跟什么比。两棵对照树把判据钉到实测上：

| | E104a（keepd） | E104b（inside） |
| --- | --- | --- |
| 建点 | ybase@464856b，哨兵提交未并入 main | main@65279cd |
| 树内新提交 | 无，head=建点 | 一笔 b92124f，head 进过建点 |
| rm --delete-branch 回执 | removed:true 单键 | removed:true 加 preservedBranch{branchName, head} |
| git 侧分支 | 即查即无；扫尾 branch -D 报 not found | 仍在 b92124f；扫尾的 Deleted 行来自手动 branch -D |

两个事实先立住。其一，判据不是「是否并入 main」：E104a 的 `464856b` 是哨兵提交、没并进 main，照样删——「未合并所以保留」这条读法在本机不成立。其二，两例都与「建之后 head 有没有前进」一致：同头删、进头留。E104b 的回执第一次带回分支证据——`preservedBranch` 把留的分支连名带头点出来。帮助原文的末句（第 10 章引过、本批随全文重钉）在这里凑齐正反面：留的，回执点名；删的（E104a），回执一个字不带，删除这个事实要靠 git 侧核验——即查 0 行，加上扫尾 `branch -D` 的 not found。至于 Orca 拿 head 跟什么比——跟建点比、跟基线比、还是别的——帮助没写，两例只能约束、不能判定，机制表述标推断。

## 11.5 两个对照收尾：谱系自动接上，配置只读对照

第 10 章 E84 用 `--no-parent` 把谱系置空；这一章补上不置空的另一半（E105）：在一棵登记里的树上调用 create，回执 `parentWorktreeId` 直接是调用方的复合格；`lineage` 里 `worktreeId`、`worktreeInstanceId`、`parentWorktreeId`、`parentWorktreeInstanceId`、`origin:"cli"`、`createdByTerminalHandle: "term_<uuid>"` 一样不缺，`capture` 是 `{source:"env-workspace", confidence:"inferred"}`——谱系从环境里推断出来，不是谁声明出来的；`workspaceLineage` 两侧对称，`childWorkspaceKey` 与 `parentWorkspaceKey` 各带 InstanceId。默认谱系挂到调用上下文，第 10 章边界清单上的这一条闭合。这棵树的 rm 回执 removed:true、无 preservedBranch 键；扫尾点名 `zhuguang-ZFG/ch11-line` 报 not found——分支在那一步之前已经没了，零新提交，走的与 E104a 同一条删路。

钩子配置的来源用两条只读的 `repo list` 行对照（E106）：本仓库（探针树都建在它名下）登记行 `hookSettings` 是 `{mode:"auto", setupRunPolicy:"run-by-default", setupAgentStartupPolicy:"start-immediately"}`，`scripts` 里 setup 与 archive 都是空串——可矩阵四棵的链照样跑出了标记：跑的脚本来自树里检出的 yaml，不是登记里的那条。另一行是 E105 调用时所站的那棵树所属的仓库：`scripts.setup` 是 `"npm install"`，还多一个本仓库行没有的键 `commandSourcePolicy:"local-only"`——行键不齐，第 10 章 10.1 的现象在配置行上再现。登记非空、树里无 yaml 时链跑什么，本批无样本，标推断。

## 11.6 这一章的边界

十二项实测（E95–E106），2026-11-23 在本机 1.4.269 上完成，前后 11:25–11:38 当次。收据：本章建过的八棵树全删；保下来的探针分支扫尾手动清六条（mdef、minh、mrun、mskp、ybase、inside——inside 删前 git 侧先核过它仍在），keepd 与 line 两条点删时报 not found，是 rm 自己删掉的；Orca 列表回到 18 行且无 ch11 行，写作目录 porcelain 干净；守护日志只点 ch11 会话收尾行的计数（168 与 42），内容不入账。第 10 章边界挂起的三件事各补了一个样本：默认谱系（E105）、`--setup` 默认链（E96–E99）、删树留分支（E95c/d）。

没有做的事：

- `--setup` 三档之差在本批输出里不可分辨（都跑了链）；inherit 的继承对象无样本；`--setup` 未知名报错未测。
- 链的失败路径全无样本：setup 脚本失败、archive 钩子失败（`worktree_archive_hook_failed`）、`archiveHookOverride` 键均未触发；E101 重试里钩子跑没跑，回执看不见。
- `commandLength:97` 是单点实测值——四个探针名等长，不外推；标记出现的 6/7 秒是轮询到的当次值。
- `--delete-branch` 的比较基准（Orca 拿 head 与什么比）标推断，帮助只给了「cannot prove are already merged are retained」一句；变基、多提交、改名的分支无样本；older hosts 的分支策略与警告未见。
- folder workspace 的 rm、group folder 拒绝 `--delete-branch` 的路径、远程 host 上的写侧均未测。
- 谱系 `capture.confidence` 只见 `inferred` 一档；父树先删之后子树的命运未测。
- 测量注记：E95 首跑因探针管道作废一次——MSYS 的 `/tmp` 与原生 jq 互不可见，哨兵没落进树里，那次 rm 删的是没带 yaml 的母树（分支保在 `65279cd`，扫尾手动删）；重跑改道读回 JSON 才成。作废样本不入正文数字。

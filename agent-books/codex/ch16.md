# 第 16 章：并行任务先隔离工作树

<!-- block: codex-ch16.b-opening -->
多个会话可以并行思考，但代码修改应有明确文件责任和独立工作状态；会话分支不能代替 Git 工作树隔离。

两个代理同时修改项目时，可能一个正在改接口，另一个仍按旧接口写测试；也可能一方格式化了另一方正在审阅的文件。并行之前，需要确定文件责任、共同接口和各自的工作状态。

## 16.1 先按责任拆任务

适合并行的任务有相对独立的输入输出，例如分别负责文档与示例、数据库适配和 UI。共享类型、公共配置与依赖锁则指定一个负责人。任务名称之外，再列清允许修改的文件。

每个任务说明至少包含目标、允许修改的目录、共同接口、验证命令与禁止覆盖的已有修改。代理还应知道其他人也在工作，遇到新变化先理解与协调，不能用还原命令清理掉不属于自己的差异。

## 16.2 工作树隔离文件状态

```powershell
git worktree add ../task-parser -b task/parser
git worktree add ../task-docs -b task/docs
```

每个工作树有自己的已检出文件和分支，适合两项独立修改。它们仍共享 Git 仓库的部分内部数据，也可能共享系统工具、全局缓存、外部数据库和账号。因此工作树隔离不是进程沙箱，更不是所有资源的独占环境。

固定 CLI 也提供 `--worktree` 托管工作树入口。使用自动创建前仍应理解它选择的基线、目录和分支，以及完成后如何取回结果。不要因为工具替你创建目录，就省略结果合并与清理检查。

## 16.3 会话 fork 解决的是上下文分支

你可以把同一问题交给两条 fork 会话，比较两种算法；但若它们指向同一工作目录，仍会编辑同一文件。相反，两个 Git 工作树如果沿用同一段过时任务描述，也可能各自做出一致却错误的修改。

```mermaid
flowchart TD
  R[共同基线与明确需求] --> A[任务 A 的会话]
  R --> B[任务 B 的会话]
  A --> WA[工作树 A]
  B --> WB[工作树 B]
  WA --> TA[独立检查]
  WB --> TB[独立检查]
  TA --> M[合并与整体检查]
  TB --> M
```

## 16.4 交付接口要能被另一项任务使用

并行前先确定数据结构、文件位置和公共约定。比如文档 agent 需要知道命令最终叫什么，测试 agent 需要知道错误返回形状。接口未定时，可以先做只读研究或准备独立用例，等待接口明确后再改依赖部分。

接口变化时，通知相关任务具体文件、字段、旧值和新值，并说明谁需要跟进，避免各自重新搜索确认。

共享文件的修改建议由负责人统一应用。锁文件和构建注册表尤其适合集中维护，避免不同任务生成不同顺序或覆盖彼此条目。

## 16.5 合并冲突揭示的是未解决的设计问题

文本冲突可以机械选择一边，但语义冲突不一定出现冲突标记。例如两个分支各自通过测试，合并后一个更改错误类型，另一个仍捕获旧类型。整体检查应覆盖交界处，而不只是把两个分支的绿色结果加在一起。

合并时先读两边意图，再形成最终实现；不要简单保留行数更多的一边。测试失败则回到共同契约，判断是实现回归还是测试假设已经过时。解决后更新文档与示例，让仓库只保留一套当前行为。

## 16.6 取消子任务与清理目录

子任务取消后，已经产生的文件和提交仍可能有价值。先记录状态，再决定保留、合并或丢弃。清理工作树前检查其中有没有未提交修改，确认它确实属于已结束任务。

自动化清理应验证绝对路径落在指定任务根目录，避免字符串拼错后删除用户工作。对于 Windows，保持一种 shell 完成路径检查与删除，不要在 PowerShell 中枚举再把未转义路径传给另一层 shell。

拆分时也要考虑协调成本：小任务可能顺序完成更快，大任务则按接口清楚、可独立验证的模块划分，减少整合时的返工。

## 16.7 把并行任务分成真正独立的工作

运费例子只改一行公式，适合用分工审阅来练习并行：一项任务检查业务边界，另一项检查工具日志和交付脚本，再由主任务汇总修改。两项任务各有输出，也无需同时编辑公式。

规模稍大时，可以把范围写得更明确：任务 A 只修改计费模块与对应测试，任务 B 只修改用户文档，任务 C 只读审阅接口兼容性。每份任务都说明基线、拥有的文件和输出位置，尤其告诉执行者还有其他人在工作，不要把新出现的差异一概还原。

同一共享目录能即时看到其他人的修改，优点是合并简单，缺点是运行时状态会变化。独立 worktree 让各自检出更清楚，但共享 Git 仓库的一些元数据仍然相关。选择方式应围绕修改是否独立，不能把 worktree 当成没有任何共享状态的完整容器。

## 16.8 合并后测试应对应组合结果

接口名称、配置文件和生成产物可能跨任务关联。两项任务各自通过后，主任务仍需检查整合后的差异，并运行覆盖这些连接位置的测试。

对运费项目，如果 A 修改参数名而 B 按旧名写调用示例，两边各自检查都可能通过，整合后读者却无法复制例子。用一条最小集成命令执行文档中的调用，就能发现这种连接处的问题。并行节省的是独立工作的时间，整合判断仍需要有人承担。

各任务汇报具体修改、验证命令和已知冲突，标明结果对应的基线。未完成的任务保留已有差异与失败信息，由主任务决定继续、调整或舍弃。

## 16.9 取消一个任务之后检查资源和文件

代理被中断时，已经写入的文件通常仍在；它启动的测试或服务也可能处于独立状态。先看任务状态，再检查本轮文件与进程，最后决定是否恢复。不要因为协作工具返回“已关闭”就删除整个工作区，里面可能还有其他任务的成果。

一行运费补丁可以直接对照公式与测试恢复；上千行混合代码、文档和配置则需要更多核对。拆任务时按可审阅的修改组织，每块写清解决的问题、检查方法和依赖任务，恢复时便能逐块处理。

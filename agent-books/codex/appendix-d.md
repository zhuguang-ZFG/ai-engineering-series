# 附录 D：术语与跨册对照

<!-- block: codex-apxd.b-opening -->
相似名称不保证相同契约；比较代理时，应逐项核对入口、状态、权限、错误与清理方式。

## D.1 常用术语

| 术语 | 在本书中的含义 | 回看章节 |
| --- | --- | --- |
| CLI | 终端命令入口及其交互方式 | 第 1、2 章 |
| Thread | 一条持续任务历史的身份 | 第 4、15 章 |
| Turn | 一次输入推动的处理回合 | 第 4、5 章 |
| Item | 回合中的消息、工具等活动记录 | 第 5、15 章 |
| Approval | 对某项待执行动作的决定流程 | 第 7 章 |
| Sandbox | 执行能力的运行环境约束 | 第 8、9 章 |
| Execpolicy | 命令 token 的规则判断 | 第 10 章 |
| Skill | 可按任务使用的方法与资源说明 | 第 12 章 |
| Hook | 在指定生命周期事件运行的处理器 | 第 12 章 |
| Plugin | 多类扩展资源的包装与分发单元 | 第 12 章 |
| MCP | 外部工具和资源的协议边界 | 第 13 章 |
| Worktree | 一份独立检出的 Git 文件状态 | 第 16 章 |
| Resume | 延续既有会话历史 | 第 4、17 章 |
| Fork | 从既有历史另起会话分支 | 第 4、16 章 |

一个词可以出现在不同层。比如“取消”可能指用户取消审批、客户端发中断、进程收到终止信号，或业务系统取消排队任务。讨论时加上对象，能避免把某一层的成功误认为全链路都停止。

## D.2 与其他分册比较时查什么

OpenCode 的 V1 插件返回 Hooks 对象，Codex 插件清单则组织技能、Hook、MCP 等资源。二者都叫插件，加载和执行契约却不同。迁移观察器时，应先找实际事件输入与结果形状，再处理错误、并发和清理。

DeepSeek Harness 分册侧重服务与循环的插件组合，Hermes 侧重记忆、技能和持续任务，Pi 侧重较小核心与扩展。各项目还包含其他能力；按这些入口比较时，先核对各册版本和实验范围。

## D.3 用一张接口表迁移扩展

| 要素 | 必须回答的问题 |
| --- | --- |
| 发现 | 文件、配置或包怎样进入候选列表？ |
| 加载 | 入口何时执行，失败是否隔离？ |
| 调用 | 参数由谁创建，返回值是否被使用？ |
| 状态 | 属于单次调用、会话、实例还是进程？ |
| 权限 | 工具审批、插件进程与外部服务各受什么约束？ |
| 清理 | 取消、卸载、实例重建和进程退出分别做什么？ |
| 证据 | 哪些来自源码，哪些在真实宿主运行过？ |

填写这张表时，就能列出需要适配的差异。例如后置回调是否可能收到缺失结果、是否只在成功分支触发，以及卸载时由宿主释放作用域还是由作者管理后台进程。随后再按这些差异编写适配代码。

## D.4 交付词汇也要准确

“已写”表示正文存在；“已检查”要说明检查对象；“已构建”表示实际产物生成；“已验证”应指向具体运行记录；“已部署”意味着目标环境发生变化。不要把这几个词混用成一个笼统的“完成”。

最终报告写清修改、结果位置、实际检查和限制即可，详细命令与实验记录放在可回查文件中。

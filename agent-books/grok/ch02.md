# 第 2 章：让发布闸门先错一次

<!-- block: grok-ch02.b-opening -->
一个能跑通、退出码为 0 的发布脚本，可能同时放过三个坏版本；先让它错，才知道该改哪里。

<!-- block: grok-ch02.b-gate -->
发布闸门通常写成三步：版本够新、变更日志有对应小节、测试日志是绿的。每步都返回一句原因字符串，失败时好读。看起来完整，实际可能三步都判错。

本章的闸门就是这样一份实现。它在坏输入上返回 0 个原因，读者第一眼看到的会是「通过」。

## 2.1 先跑两条命令

在本书仓库根目录运行：

```powershell
python grok/examples/check_release.py
python grok/examples/check_release.py --fixed
```

第一条的退出码是 `1`，第二条是 `0`。这是本次实测结果。脚本用同一张用例表分别喂给两个实现，`--fixed` 只切换实际调用的 `gate`（`grok/examples/check_release.py:31-32`）。

不符的用例有三条，摘录自第一条命令的 JSON 输出：

```json
{
  "build": "faulty",
  "cases": [
    { "case": "numeric_order",   "expected": 1, "actual": 0, "reasons": [] },
    { "case": "missing_section", "expected": 1, "actual": 0, "reasons": [] },
    { "case": "failed_suite",    "expected": 1, "actual": 0, "reasons": [] }
  ],
  "disagreements": 3
}
```

`reasons` 为空说明闸门认为这批输入无可指责。`clean` 与 `no_changelog` 两条是对的：前者应当通过，后者缺少文件，闸门应当拒绝它（用例表见 `grok/examples/check_release.py:20-28`）。

## 2.2 三个缺陷各占几行

| 用例 | 业务预期 | 故障版实际 | 缺陷位置 |
| --- | --- | --- | --- |
| `numeric_order` | `1.9.0` 低于 `1.10.0`，拒绝 | 放行 | `release_gate.py:22` |
| `missing_section` | 日志里没有 `1.10.0` 小节，拒绝 | 放行 | `release_gate.py:27-30` |
| `failed_suite` | 日志出现 `FAILED`，拒绝 | 放行 | `release_gate.py:33-38` |

第一处是字符串比较。`package_version < REQUIRED_VERSION` 按字典序比较，`"1.9.0"` 与 `"1.10.0"` 在第二个字符就分出大小：`9` 大于 `1`，于是条件不成立，函数返回 `None`（`grok/examples/release_gate.py:19-24`）。版本号的分段数值顺序与字符顺序不一致，十个版本之后就会撞上。

第二处只检查文件是否存在。`changelog_ok` 收到 `changelog` 与 `version` 两个参数，实际只用了 `changelog.exists()`（`grok/examples/release_gate.py:27-30`）。代码没有读取参数 `version`，因此无法发现「日志里没有这一版的小节」。

第三处是子串搜索。`if "OK" not in log.read_text()` 只排除完全找不到 `OK` 的日志；一段先写 `FAILED (failures=1)`、末尾又带 `OK` 的日志照样通过（`grok/examples/release_gate.py:33-38`，用例构造见 `check_release.py:25-26`）。

## 2.3 参考实现怎样把规则写清楚

```python
def parse_version(text: str) -> tuple[int, ...] | None:
    parts = text.strip().split(".")
    if not parts or any(not p.isdigit() for p in parts):
        return None
    return tuple(int(p) for p in parts)
```

这段在 `grok/examples/release_gate_fixed.py:16-20`。非数字输入返回 `None`，调用方据此给出「不是数字」而不是静默比较。

版本比较改用元组，`(1, 9, 0) < (1, 10, 0)` 成立（`release_gate_fixed.py:23-30`）。变更日志要求出现对应版本的标题行，正则匹配 `## [x.y.z]`（`release_gate_fixed.py:33-39`）。测试日志先拒 `FAILED`，再要求出现 `Ran N tests in ...` 的汇总行（`release_gate_fixed.py:42-50`，正则定义在 `:13`）。

三处修改对应三条业务规则，不是三处修补技巧。规则写进用例表之后，才算固定下来。

## 2.4 为什么先复现再改

`test_release.py` 把两类结果写进断言：故障版必须漏掉 `failed_suite`、`missing_section`、`numeric_order` 三条，参考版必须一条不漏（`grok/examples/test_release.py:12-20`），并且 `numeric_order` 的原因里要出现 `below 1.10.0`（`:22-25`）。本次运行 `python -m unittest discover -s grok/examples -p "test_*.py" -v`，3 条测试通过。

如果先读代码再改，你得到的是实现者声称的规则。先跑用例，你拿到的是实际判定：退出码、每个用例的 `expected` 与 `actual`、原因字符串。这两组信息不一致时，可复现的那组才是修改依据。

脚本的退出码约定写在文件头：退出码 `1` 表示至少一个用例与预期不符，对故障版这是预期结果（`grok/examples/check_release.py:1-8`）。约定与实测一致，才说明后面可以用退出码做门禁。

## 2.5 这一章的边界

两条命令与三行不符是本次实测，运行环境为本书仓库根目录。`check_release.py` 不读取真实项目、不联网、不调用模型，它只验证这道闸门对五个构造用例的判定。

文档与实测没有覆盖的部分：在真实 CI 日志上，`Ran N tests in` 的格式是否稳定；版本号带预发布后缀（如 `1.10.0-rc1`）时参考实现会返回「不是数字」，这是刻意的保守选择，需要由你的发布规则决定是否接受。

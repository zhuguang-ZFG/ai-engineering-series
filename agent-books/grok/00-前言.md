# 前言

<!-- block: grok-front.b-opening -->
Grok Build 把一个终端编码 Agent 拆成界面、运行时、工具、工作区四块装进同一个 Rust 工作区，本书从一道会放过错误版本的发布闸门走进去。

第一次给项目写发布检查，脚本跑通了，退出码是 0，你会以为发布条件已经覆盖。下一个版本号一出现，问题就露出来：脚本把 `1.9.0` 当成低于 `1.10.0`，或者测试日志里出现一个 `OK` 就算通过。

本书用一个三处缺陷的发布闸门做起点。我们先在终端里看到它放过三个坏用例，再逐个指出缺陷所在的行，然后才谈配置、规则、记忆和会话。顺序不能颠倒：先读行为，再读承诺。

## 这本书研究的程序

Grok Build 是 SpaceXAI 的终端编码助手。官方安装后命令名是 `grok`，源码在公开仓库 [`xai-org/grok-build`](https://github.com/xai-org/grok-build)，许可证为 Apache License 2.0（`CONTRIBUTING.md:5`）。

公开树由单仓周期同步而来，根目录的 `SOURCE_REV` 记录这份源码对应的**内部单仓**提交。本次写作固定的是公开提交 [`2bdd1d6a`](https://github.com/xai-org/grok-build/tree/2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8)，它对应的内部单仓提交是 `559751fdcec02d413e4c57c8832ab275e4f44980`（`SOURCE_REV`；说明见 `README.md:34-35`）。两个 SHA 不能混用：公开链接只能用 `2bdd1d6a`，拿内部 SHA 拼 GitHub 地址会返回 404。书中的 `文件:行` 都指这份公开提交的树。

官方用户手册随 pager crate 发布，共 27 篇，路径为 `crates/codegen/xai-grok-pager/docs/user-guide/`（文件清单：该目录，访问日期 2026-11-13）。本书引用的配置、规则、记忆、会话说明都在其中。

## 案例与实测范围

全部示例位于本书仓库的 `grok/examples/`。`release_gate.py` 是故意留错的实现，`release_gate_fixed.py` 是参考实现，`check_release.py` 用同一张用例表跑两者，`test_release.py` 把结果钉住。

三条命令都不需要账号，也不需要网络：

```powershell
python grok/examples/check_release.py
python grok/examples/check_release.py --fixed
python -m unittest discover -s grok/examples -p "test_*.py" -v
```

第一条退出码为 `1`，报告 3 个用例不符；第二条退出码为 `0`。写作环境里 `grok` 不在 PATH 上，因此本书没有运行 `grok --version`，也没有启动过交互界面。凡是这类情况，正文会写明「按文档」并给出出处。

## 阅读顺序

第 1 章确认你面对的是哪个程序：同一台机器上的命令名、包名、产物名并不相同。第 2 章复现闸门的错误，建立「先行为后承诺」的基线。

第 3 到第 5 章解释运行环境的三个落点：配置按七层优先级合并，项目规则与记忆各自存在哪里，会话与检查点分别能恢复什么。这三章合起来回答同一个问题：Agent 启动时到底读到了什么。

第一次接触这套程序的读者，可以在第 1 章核对入口后直接跳到第 3 章，因为配置错误最常见的表现就是「改了没生效」。负责团队下发的读者从第 3 章的 `requirements.toml` 与 MDM 读起，那里决定哪些键开发者改不动。

每章最后一节写边界：哪些结论只来自文档，哪些需要你在装好程序的机器上自行实测。

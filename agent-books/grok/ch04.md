# 第 4 章：项目规则与记忆放在哪

<!-- block: grok-ch04.b-opening -->
项目规则是随仓库走的 Markdown，启动时按目录顺序装入；记忆是跨会话的笔记，默认关闭。

两者都能让模型「记得」事情，落点完全不同。规则存在于你的仓库里，提交、评审、回滚都跟着代码走。记忆存在用户目录下，默认不开启，需要显式打开。

分清这一点，才能回答「为什么换一台机器就没有这条约定」。

## 4.1 项目规则认哪些文件名

手册标题直接写 `Project Rules (AGENTS.md)`（`12-project-rules.md:1`）。每个目录按下列名字检查（`12-project-rules.md:17-24`）：

```text
Agents.md
Claude.md
CLAUDE.md
CLAUDE.local.md
AGENT.md
AGENTS.md
```

同一目录里所有匹配的文件都会一起加载，因此同时存在 `AGENTS.md` 与 `CLAUDE.md` 时，两份都进入上下文（`12-project-rules.md:26`）。在大小写不敏感的文件系统上，解析到同一个文件的名字会自动去重。

`Claude.md`、`CLAUDE.md`、`CLAUDE.local.md` 是为兼容 Claude Code 工作流保留的。默认启用 Claude 兼容时，Grok 还会扫描用户目录下的 `~/.claude/`，并在每一层目录检查 `.claude/CLAUDE.md` 与 `.claude/CLAUDE.local.md`；启用 Cursor 兼容时同理扫描 `~/.cursor/`（`12-project-rules.md:26`）。

除固定文件名外，还会扫描每层的 rules 目录（`12-project-rules.md:32-36`）：

| 位置 | 说明 |
| --- | --- |
| `<dir>/.grok/rules/` | 总是扫描 |
| `<dir>/.claude/rules/` | Claude 兼容，可配置 |
| `<dir>/.cursor/rules/` | Cursor 兼容，可配置 |

用户级规则先加载：`$GROK_HOME/rules/`（默认 `~/.grok/rules/`）总是扫描，`~/.claude/rules/` 与 `~/.cursor/rules/` 由兼容开关控制，`[paths] extra_rule_dirs` 可追加任意绝对目录（`12-project-rules.md:42-45`）。顺序是先用户级、再从仓库根到当前目录，同一 rules 目录内按字母序（`12-project-rules.md:47`）。

## 4.2 扫描顺序与冲突裁决

```text
1. 用户级规则：$GROK_HOME → 启用的 ~/.claude/ 与 ~/.cursor/ → [paths] extra_rule_dirs
2. 仓库规则：在 git 仓库内，从仓库根逐层到当前工作目录
3. 非仓库：只扫当前工作目录
```

顺序出自 `12-project-rules.md:62-64`。规则叠加而非替换：在 `my-app/src/components/` 启动时，根、`src/`、`components/` 三份 `AGENTS.md` 都进入上下文（`12-project-rules.md:79`）。冲突时更深的文件排在后面，后面的文件覆盖前面的文件；手册用的例子是根目录写 styled-components、`components/` 写 CSS modules，后者生效（`12-project-rules.md:83`）。

`[paths] extra_rule_dirs` 是一个例外：列出的目录在每个项目、无论目录信任状态、无论 `.gitignore` 都会加载，`grok inspect` 把它们列为 `global`（`12-project-rules.md:54`）。这条通道适合团队共享规则，也意味着它绕过了项目级信任检查。

## 4.3 记忆存在哪里

记忆是实验性功能，默认关闭（`13-memory.md:16`）。打开方式二选一：

```toml
# ~/.grok/config.toml
[memory]
enabled = true
```

或者用环境变量 `GROK_MEMORY=1`（`13-memory.md:49-58`）。优先级从高到低是：进程级强制关闭（`--no-memory` 或 `GROK_MEMORY=0`）、生效 TOML 中的 `[memory] enabled = false`、然后才是任一开启来源（`13-memory.md:78-86`）。

存储路径分两套（`13-memory.md:95`）：

| 模式 | 目录 | 内容 |
| --- | --- | --- |
| v2（`[memory_v2] enabled`） | `~/.grok/memory-v2/` | `topics/` 整理后的笔记，`observations/_inbox/` 新事实 |
| 旧版（仅 `[memory] enabled`） | `~/.grok/memory/` | `MEMORY.md` 加按 hash 命名的工作区目录 |

两个开关都默认关闭（`13-memory.md:95`）。作用域有两个：全局记忆跨项目，工作区记忆属于一个仓库，同一仓库的克隆与 worktree 共享同一工作区作用域（`13-memory.md:20-22`）。

写入方式有三种：`/remember` 写入 `MEMORY.md`，保存时提示 `Memory saved to ~/.grok/memory/MEMORY.md`（`13-memory.md:134-148`）；`/flush` 生成当前会话的 LLM 摘要并写入带日期的会话日志（`13-memory.md:38-44`）；`/dream` 把散落片段合并成主题（`13-memory.md:229`）。每次会话还会注入一份有上限的两作用域索引，供模型决定打开哪些主题（`13-memory.md:28-30`）。

## 4.4 分工与信任边界

`12-project-rules.md:3` 把规则定位为「按项目或目录配置 Grok」，机制是把 Markdown 加入上下文。`13-memory.md:3` 把记忆定位为「跨会话回忆事实、决策与模式」，机制是索引加搜索。

| 维度 | 项目规则 | 记忆 |
| --- | --- | --- |
| 存放 | 仓库内文件与 `$GROK_HOME/rules/` | `~/.grok/memory-v2/` 或 `~/.grok/memory/` |
| 默认状态 | 启动即加载 | 默认关闭，需显式开启 |
| 生效范围 | 目录树，越深越优先 | 全局或单个工作区 |
| 改写者 | 提交与评审 | `/remember`、`/flush`、`/dream` |

信任边界写在两处。项目规则的启动加载要求目录先获得信任，通过 `--trust` 或交互式授权（`12-project-rules.md:3`）。技能文档的首段更直接：`Startup discovery skips project skills and commands in untrusted folders.`（`08-skills.md:3`）。克隆一个仓库并不等于授权它向模型注入指令。

`.grok/` 目录下还有几类项目级配置：`config.toml`（只提供 MCP、插件、权限等键）、`skills/`、`plugins/`、`agents/`、`hooks/`、`lsp.json`（`12-project-rules.md:206-213`）。它们与规则共用同一个信任前提。

## 4.5 这一章的边界

本章全部来自 `12-project-rules.md`、`13-memory.md` 与 `08-skills.md`，本次没有运行 `grok inspect`，也没有在真实仓库里放置多份 `AGENTS.md` 去观察加载结果。规则文件的加载顺序、去重规则、记忆文件的实际落盘位置都属于「按文档」，需要在装好程序的机器上验证。

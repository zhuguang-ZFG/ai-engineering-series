# 第 1 章：先确认跑的是哪个程序

<!-- block: grok-ch01.b-opening -->
命令名、包名与产物名在 Grok Build 里是三个不同的东西；先把它们对齐，再谈行为。

终端里输入 `grok` 能启动，只说明 PATH 上某个可执行文件应了这个名字。发布安装、源码构建、包管理器安装可能同时存在，它们未必来自同一份源码。排查参数缺失或配置失效之前，先记录版本与入口路径。

## 1.1 记录安装来源与版本

发布二进制覆盖 macOS、Linux 和 Windows（`README.md:43`）。官方给出的命令是：

```sh
curl -fsSL https://x.ai/cli/install.sh | bash   # macOS / Linux / Git Bash
irm https://x.ai/cli/install.ps1 | iex          # Windows PowerShell
grok --version
```

这三行位于 `README.md:45-49`，小节标题为 Installing the released binary（`README.md:41`）。安装固定版本的写法在手册里：bash 脚本接 `bash -s 0.1.42`，PowerShell 先设 `$env:GROK_VERSION`（`01-getting-started.md:17-33`）。PowerShell 安装器会把 `%USERPROFILE%\.grok\bin` 写进用户 PATH（`01-getting-started.md:35`）。

核对版本用 `grok --version`（`01-getting-started.md:37-41`）。升级用 `grok update`；WinGet 安装的副本由 `winget upgrade --id xAI.GrokBuild -e` 升级，此时 `grok update` 只打印该命令、不改动文件（`01-getting-started.md:43-55`）。

本次写作环境里 `command -v grok` 没有输出，所以上面这些命令都没有在本机实际执行。它们是文档声明的入口，不是我的实测结果。

## 1.2 源码构建得到的是另一个名字

仓库根 `Cargo.toml` 是自动生成的 workspace 清单（`Cargo.toml:1`），成员从 `crates/build/` 与 `crates/codegen/` 下逐个列出（`Cargo.toml:6-8`）。工具链固定在 `rust-toolchain.toml`，通道为 `1.94.0`，附带 rustfmt 与 clippy。

构建目标是一个组合根包，包名与产物名不同：

```toml
[package]
name = "xai-grok-pager-bin"
version = "1.0.45"
default-run = "xai-grok-pager"

[[bin]]
name = "xai-grok-pager"
path = "src/main.rs"
```

以上四段分别取自 `crates/codegen/xai-grok-pager-bin/Cargo.toml:2`、`:3`、`:7` 与 `:14-16`。包注释说明这个包存在的理由：二进制要同时链接 pager 库与可选的 minimal 渲染模式，而 minimal 依赖 pager，pager 不能再反向依赖它（`crates/codegen/xai-grok-pager-bin/Cargo.toml:9-13`）。

README 把关系写成一句话：产物名为 `xai-grok-pager`，官方安装把它作为 `grok` 发布（`README.md:57-59`）。构建命令与产物路径：

```sh
cargo run -p xai-grok-pager-bin              # build + launch the TUI
cargo build -p xai-grok-pager-bin --release  # release binary: target/release/xai-grok-pager
cargo check -p xai-grok-pager-bin            # fast validation
```

命令来自 `README.md:75-79`。构建需要 DotSlash，`bin/protoc` 经它下载；缺失时回退到 PATH 或 `$PROTOC` 上的 protoc（`README.md:60-71`）。macOS 与 Linux 是受支持的构建宿主，Windows 构建标注为尽力而为、当前未从这棵源码树测试（`README.md:72-73`）。

## 1.3 四个角色各管一段

README 的 Repository layout 表把 CLI 闭包拆成几块（`README.md:95-106`），其中与阅读顺序直接相关的四行如下：

| 路径 | README 的职责描述 | 接手的问题 |
| --- | --- | --- |
| `crates/codegen/xai-grok-pager` | The TUI: scrollback, prompt, modals, rendering | 屏幕上看到什么 |
| `crates/codegen/xai-grok-shell` | Agent runtime + leader/stdio/headless entry points | 一次请求怎样跑起来 |
| `crates/codegen/xai-grok-tools` | Tool implementations (terminal, file edit, search, ...) | 模型能调用什么 |
| `crates/codegen/xai-grok-workspace` | Host filesystem, VCS, execution, checkpoints | 落在磁盘上的状态 |

出处依次为 `README.md:100`、`README.md:101`、`README.md:102`、`README.md:103`。这四行决定了后续章节的落点：配置由 pager 与 shell 共同消费，规则与记忆在启动时装入运行时，会话与检查点写入 workspace 管理的目录。

## 1.4 SOURCE_REV 与不接受外部贡献

公开树不是主开发树。`SOURCE_REV` 记录代码对应的单仓提交，README 对这一点的描述是：仓库定期从 SpaceXAI 单仓同步（`README.md:31-35`）。

贡献政策写得很直接：不接受外部 pull request 与主动提交的补丁，公开源码用于源码透明与本地构建，安全报告走 `SECURITY.md`（`CONTRIBUTING.md:3-9`）。读到缺陷时，正确动作是记录证据与复现步骤，而不是提交补丁。

## 1.5 这一章的边界

安装脚本、版本命令、构建要求都来自文档，本次没有在装有 `grok` 的机器上执行。`xai-grok-pager-bin` 是包名、`xai-grok-pager` 是产物名、`grok` 是安装后命令名，这三条能指到 `Cargo.toml` 的行与 `README.md:57-59`。

未验证的部分包括：安装脚本当前下载的版本号、Windows 构建是否可用、`grok --version` 的实际输出格式。要确认它们，需要在目标机器上运行命令并保留输出。

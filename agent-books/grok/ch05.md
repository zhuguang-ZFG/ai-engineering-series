# 第 5 章：会话、恢复与检查点

<!-- block: grok-ch05.b-opening -->
会话能恢复到某一轮对话，不等于代码能回到那一刻；两件事各有一套落盘证据。

<!-- block: grok-ch05.b-checkpoint -->
长任务中断后重开，你希望接着上次的对话继续。改坏三个文件后想退回去，你希望磁盘状态回到修改前。终端里都叫「恢复」，实现上一条走会话日志，一条走检查点。

本章把两者分开，各自指出文件与行。

## 5.1 会话在哪里

Grok 把每次对话自动存盘，TUI、headless 与 agent stdio 都算一个会话（`17-sessions.md:3`）。会话包含用户提示与模型回复、工具调用与结果、TODO 状态、供撤销用的回退点、token 用量与轮次、以及子会话（`17-sessions.md:9-16`）。

会话 ID 在 Grok 自行生成时是 UUIDv7，客户端可以用 `-s` 指定；存放在 `~/.grok/sessions/` 下，`GROK_HOME` 可改基目录（`17-sessions.md:18`）。

目录布局（`17-sessions.md:24-40`）按工作目录分组，工作目录做 URL 编码后作为组名：

```text
~/.grok/sessions/<encoded-cwd>/<session-id>/
  summary.json            # 元数据：标题、时间戳、模型、消息计数
  updates.jsonl           # ACP 会话更新流（对话与工具调用）
  chat_history.jsonl      # 发给模型的原始消息
  system_prompt.txt       # 渲染后的系统提示
  prompt_context.json     # 渲染系统提示所用的输入
  tool_definitions.json   # 最近一次模型调用的函数工具
  plan.json               # TODO/任务列表状态
  rewind_points.jsonl     # /rewind 用的回退点
  signals.json            # token 用量、工具与轮次计数
  feedback.jsonl          # 用户反馈
  compaction_checkpoints/ # 压缩时保存的状态
  subagents/              # 每个子会话的 meta.json
```

编码后的目录名超过 255 字节时，会改用 slug 加 hash，并把原始路径写进组内的 `.cwd` 文件（`17-sessions.md:24`）。

`summary.json` 是索引条目，记录标题、模型、时间与消息计数；`updates.jsonl` 是权威对话日志，`/resume` 与会话恢复都由它驱动（`17-sessions.md:42`）。`tool_definitions.json` 不含 MCP 的 `server__tool` 条目，因为模型经 `search_tool` 与 `use_tool` 触达它们（`17-sessions.md:42`）。

## 5.2 恢复的三个入口

```text
/resume                          # TUI 内打开选择器
grok --resume <session-id-or-title>
grok --resume                    # 不带值：当前目录最近一次会话
```

三条来自 `17-sessions.md:86-108`。标题匹配只对当前目录的会话生效、忽略大小写；同名会话多于一个时，手工改过名的那条优先，否则报错并列出候选 ID；UUID 形状的值只按 ID 处理，脚本应优先用 ID（`17-sessions.md:106`）。启动欢迎界面也会列出当前目录的最近会话（`17-sessions.md:112`）。

会话目录里还有一个 `rewind_points.jsonl`（`17-sessions.md:35`）。它服务于 `/rewind`，与会话恢复是两件不同的事。

## 5.3 /rewind 只截断对话

`/rewind`（别名 `/undo`）把对话退回到较早的一轮，丢弃其后的轮次，磁盘上的文件改动保持不变（`17-sessions.md:143`）。执行时它列出回退点（每个用户提示一个），让你选择，然后截断对话历史（`17-sessions.md:150-155`）。

手册在最显眼的位置写了一句：`/rewind` 不还原磁盘文件，只截断对话历史（`17-sessions.md:158`）。因此把「回退对话」当成「撤销代码」会丢工作。

## 5.4 检查点在 workspace 里

README 对 `crates/codegen/xai-grok-workspace` 的描述包含 checkpoints（`README.md:103`）。这部分的落点在源码：

```rust
// A rewind checkpoint is keyed by `prompt_index` and bundles the filesystem
// [`RewindPoint`], an optional hunk delta, and optional git HEAD/index.
// Restore reverts all enabled domains together.
```

注释在 `crates/codegen/xai-grok-workspace/src/session/checkpoint.rs:5-6`。一个检查点以 `prompt_index` 为键，打包三样东西：文件系统回退点、可选的 hunk 增量、可选的 git HEAD 与索引。恢复会把所有启用的域一起还原。

存储位置在 `<cwd>/.grok/rewind-checkpoints/<session_id>`，每个会话一个子目录（`crates/codegen/xai-grok-workspace/src/session/checkpoint_store.rs:17`、`:45`）；保留数量有上限，超出后淘汰最旧的（同文件 `:34`、`:52`）。磁盘是持久副本，内存缓存是热读路径（同文件 `:4-6`）。

把这些证据对齐后，两件事的边界如下：

| 问题 | 证据 | 数据 |
| --- | --- | --- |
| 对话能回到第几轮 | `17-sessions.md:42`、`:143` | `updates.jsonl`、`rewind_points.jsonl` |
| 磁盘文件能回到哪一刻 | `checkpoint.rs:5-6`、`checkpoint_store.rs:17` | `RewindPoint`、hunk 增量、git HEAD/index |

手册明说 `/rewind` 不动文件（`17-sessions.md:158`），源码里的 `Restore reverts all enabled domains together` 属于 workspace 的恢复路径（`checkpoint.rs:6`）。两条证据放在一起，能得到的结论是：会话恢复有明确入口，代码回退的检查点机制存在，但文档没有给出一个「用它回滚磁盘文件」的命令。

```ill
grok-rewind-checkpoint
```

图：`/rewind` 只截断对话历史并丢弃后续轮次，磁盘文件保持不变。workspace 检查点以 `prompt_index` 为键，打包 `RewindPoint`、可选的 hunk 增量与可选的 git HEAD/index；`Restore` 将所有启用域一起还原。检查点存于 `<cwd>/.grok/rewind-checkpoints/<session_id>`。

## 5.5 这一章的边界

会话存放位置、`updates.jsonl` 的权威地位、`/resume` 与 `--resume` 的语义来自 `17-sessions.md`。检查点的键、打包内容与存储路径来自源码注释与常量，属于静态阅读，不是运行观察。

本次没有在装有 `grok` 的机器上运行 `/resume`、`--resume` 或 `/rewind`，也没有检查真实会话目录。需要实测的三点：恢复后上下文是否完整、`compaction_checkpoints/` 与 `rewind-checkpoints/` 在压缩加回退同时发生时的关系、以及代码回退的实际触发方式。文档没有回答，我不替它回答。

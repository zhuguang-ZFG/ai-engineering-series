# 第 11 章：LSP、搜索与代码上下文

<!-- block: opencode-ch11.b-opening -->
找代码既可以按文本检索，也可以问语言服务“这个符号在哪里定义”。两条路径回答的问题不同：搜索找到字符，LSP 结合项目和语言规则提供语义信息。模型仍需判断哪些证据与任务有关。

## 11.1 从报错找起，别先把整个仓库读进来

遇到失败测试，先定位报错文件、调用位置和相关定义。文本搜索适合找错误消息、配置项和函数名；语言服务适合跟踪定义、引用和诊断。读取目标文件后，再检查它依赖的类型或模块。

这样每次读取都有明确目的，也容易回看自己从哪里找到下一个文件。一次放入大量源码，可能增加成本，还会使遗漏原因更难排查。这是建议的任务策略，OpenCode 不保证每次都按这个顺序检索。

```mermaid
flowchart LR
  E[失败测试或报错] --> S[文本搜索定位]
  S --> R[读取局部代码]
  R --> L[LSP 定义、引用、诊断]
  L --> H[形成修改假设]
  H --> T[运行针对性测试]
  T -->|仍失败| R
```

## 11.2 LSP 客户端怎样对应项目

本书所用版本的 LSP 服务按文件选择服务器和项目根，并管理已经启动的客户端。相同 server 与 root 的启动会通过正在启动的记录协调，避免简单重复创建。客户端准备好后再发送文件与诊断相关请求。

语言服务的项目根可能不同于 Git 工作树根。一个 monorepo 包含多个语言项目时，不能因为两个文件在同一仓库就认定它们使用同一个 LSP 实例。遇到诊断缺失，检查服务器识别的 root、配置文件和依赖。

配置还可以关闭全部 LSP 或某个服务，覆盖命令和文件扩展。实验关闭下载后，没有语言服务运行是预期结果，不应把它解释成 OpenCode 不支持相应语言。

## 11.3 诊断是特定时刻的结果

文件变化、依赖安装和项目配置变更都可能改变诊断。某一轮读取到“没有错误”，不意味着随后修改后仍然正确。工具需要让语言服务知道文件变化，并等待相应结果；具体时序会受服务实现影响。

源码里的 touchFile 和诊断接口说明宿主会主动与语言服务交互，但不是所有诊断都等价于构建结果。类型检查可能没有执行测试，LSP 也可能缺少 CI 中的环境变量或生成代码。

LSP 适合提供快速反馈。修改后仍需运行项目规定的检查，尤其是运行时异常、网络协议和数据库约束，通常要靠实际测试才能发现。

## 11.4 读取代码也会带入邻近指令

第三章提到，指令服务会在读取文件时寻找附近规则文件。这样一个模块的约定可以在需要时加入上下文，但也要求排查者知道它何时加载。

假设根目录要求使用通用测试命令，而子目录说明某个包必须先生成代码。模型没有读过子目录规则时，可能只执行根级命令。解决办法是让任务描述明确模块范围，并检查实际加载内容；不能依赖一个从未进入请求的文件影响行为。

不可信源码或日志也可能含指令式文字。它们应作为任务数据来分析，不能因为出现在工具结果里就变成新的高优先级要求。提示词层可以提醒模型注意来源，执行层仍须守住工具权限与文件边界。

## 11.5 做一个有用的有无 LSP 对照

固定仓库提交和测试任务，分别关闭与开启语言服务，记录检索路径、实际请求、诊断和最终检查。不要只比较耗时；如果一轮读到更多文件却修复了不同问题，数字不可直接对比。

本轮未做此对照，也未给出语言服务带来的成功率结论。实际部署时，优先确认服务能稳定启动、项目根正确、依赖与 CI 接近，再考虑性能优化。

## 11.6 从一个符号位置跟到协议请求

假设搜索在 `src/pricing.ts` 第 24 行找到 calculateTotal 的调用，接下来要知道它解析到哪个定义。工具层的请求可以写成如下形状；这是固定版本参数示例，不是本轮运行日志：

```json
{
  "operation": "goToDefinition",
  "filePath": "src/pricing.ts",
  "line": 24,
  "character": 9
}
```

入口在 `tool/lsp.ts`，而不是直接跳到语言服务器。它先把相对路径接到 instance.directory，执行外部目录检查，再请求 lsp 权限。接着检查文件存在、是否有适配的服务，调用 touchFile，最后才按 operation 分派。文件路径拼错时会得到 File not found；没有服务匹配时是 No LSP server available。这两种失败都早于定义查询。

位置还经过一次关键转换。工具参数按编辑器习惯从 1 开始，内部 position 使用 `line - 1` 与 `character - 1`。因此上例会发送 line 23、character 8。维护客户端时不能在请求侧先减一次，又让工具再减一次。返回的 LSP Range 属于协议坐标，展示时也要清楚由哪一层转换。

definition 方法将文件转成 file URI，调用 `textDocument/definition`；references 调用 `textDocument/references`，并设置 includeDeclaration 为 true。引用列表里出现定义本身是代码明确要求的行为，不表示搜索重复。implementation 与 definition 也不能互换：前者寻找接口或抽象声明的具体实现，后者回答当前位置解析到哪里。

## 11.7 两个请求怎样共享同一次服务启动

LSP 用四类状态管理启动过程：servers 保存可选服务器定义，clients 保存已建立的客户端，spawning 记录正在创建的 Promise，broken 记录启动失败的组合。

`getClients(file)` 先检查文件是否处于 instance 允许的范围，按扩展名筛选服务，再调用每个服务的 root 函数。匹配身份使用 root 与 server.id。已有客户端就复用；同一身份正在启动，就等待 spawning 里的 Promise；否则由 schedule 创建进程与客户端。

假设模型先后读到同一个包里的两个 TypeScript 文件，它们解析出相同 root。第二次请求不应再启动另一份语言服务，而是接上第一份启动结果。schedule 完成后还会检查是否已经存在同身份客户端，若存在则停止新建进程并复用旧对象。这是启动去重的第二层保护。

spawn 返回空值、抛错，或 LSPClient.create 失败，都会把该 root/server 组合放入 broken；客户端创建失败还会停止已启动进程。后续查询跳过 broken 组合，因此即使修好了 PATH，同一 instance 也未必重试，需要结合启动日志与实例状态排查。

配置里的自定义服务可以覆盖 command、env、extensions 和 initialization。若没有已有服务的 root 函数，自定义服务默认使用 instance.directory。monorepo 中这尤其重要：两个子包若需要各自的编译配置，一个错误的大根目录可能导致两个文件看似共享客户端，却使用了错误的项目环境。

## 11.8 无结果、无服务和旧诊断是三件事

`hasClients` 这个名字容易让人误会。固定实现检查的是是否存在扩展与 root 匹配、且不在 broken 集合里的服务器，它不要求 clients 数组中已经有连接。因此它回答“有可尝试的服务”，真正启动发生在后面的 touchFile/getClients。

touchFile 取得客户端后记录 after 时间，调用 notify.open，拿到文档 version。需要诊断时，把 path、version、mode 和 after 一并交给 waitForDiagnostics。这里等待的是特定打开版本之后的反馈。直接读取 diagnostics 方法，则只是汇总当前客户端已保存的诊断 Map；它本身不会启动所有项目，也不会扫描全仓。

查询方法还会处理单个请求失败：definition 的失败被转换成 null，references 的失败变成空数组，最终结果展开并过滤空值。于是工具显示 No results found 时，既可能真的没有目标，也可能底层查询失败后被折叠为空。先确认客户端连接、文件版本与服务器日志，再把“无结果”解释为源码关系不存在。

workspaceSymbol 同样有范围：它遍历已经存在的客户端，按允许的符号类型筛选，每个客户端最多留下十项，然后合并。结果不是整个仓库的完整符号索引。调用层先 touchFile 指定文件，能启动该文件对应服务，却不会因此自动启动仓库里所有语言项目。

## 11.9 把检索结果变成一个能验证的修改

回到价格函数的例子。文本搜索先告诉我们 calculateTotal 出现在哪里；定义查询确认调用解析到哪个实现；references 列出其他使用者；读取对应测试后，才能判断修改会影响哪些输入。若函数通过接口调用，还可以用 goToImplementation 查实现，而不是把所有同名函数当成同一个目标。

调用层级也有具体限制。incomingCalls 和 outgoingCalls 会先 prepareCallHierarchy，取返回列表的第一项，再发下一次请求。一个位置产生多个候选时，这条路径没有逐一展开全部候选。因此图上的调用关系可用来缩小范围，但不能用来证明“其他调用绝对不存在”。

如果查询和测试都支持，可以把调查结果写成：“当前调用解析到 pricing.ts，references 包含结算入口和两处测试；空购物车分支返回错误值，已有测试可以复现。”语言服务帮助定位，测试负责确认行为。这里仍是调查方法示例，本书尚未实际运行这组 LSP 查询。

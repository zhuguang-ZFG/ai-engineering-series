# C15 答案与核对依据

检索结果必须来自你的实际运行；下面给记录方法和判定标准，不填虚构分数。

## 1. 词项与 embedding 对照

建议表格：

```markdown
| 查询 | 检索器 | 前 3 chunk_id | 正确片段排名 | 无命中 | 备注 |
| --- | --- | --- | --- | --- | --- |
| 闭馆前要关什么 | keyword | ... | 1 | 否 | 命中标题词 |
| 晚上结束后处理哪些设备 | keyword | （空） | 未命中 | 是 | 同义改写漏检 |
| 晚上结束后处理哪些设备 | embedding | ... | ? | 否 | 需人工核对是否支持 |
```

`chunk_id` 形如 `doc@<sha256 前 12 位>#000`；文档版本在单独的 `version` 字段，不要用版本号拼 chunk_id。

判定：

- **命中**：正确片段出现在前 k，且包含回答问题所需的完整条件；
- **漏检**：正确片段存在，但没有进入前 k；
- **误排**：无关/旧版片段排名高于正确片段；
- **无命中**：没有任何片段达到阈值，不能把最低分当证据。

embedding 分数不是概率，不能解释为“92% 正确”。它只用于同一查询内的相对排序；不同查询、不同模型的分数不可直接比较。

## 2. 两类查询

字面不重合但语义相近：

```text
查询：晚上结束营业后要处理哪些设备？
原文：闭馆前关闭饮水机电源。
```

词项可能漏掉“闭馆/结束营业”的对应；embedding 可能命中。但即使命中，也要检查原文是否真的说“饮水机”，不能因为语义相近就补一个设备。

字面重合但语义无关：

```text
查询：设备采购流程
原文：设备检查流程
```

两者都含“设备”和“流程”，词项可能误排；embedding 可能区分，也可能不区分。结论只对当前模型和语料成立。

## 3. 引用支持分类

对每条 `quote`：

- **完全支持**：原文直接陈述主张，条件和否定词一致；
- **部分支持**：原文支持一部分，另一部分是推断；
- **不支持**：原文没有该信息，或关键词相同但关系不同；
- **条件被省略**：原文有“若/除非/仅在”，答案写成无条件规则。

示例：

```text
原文：若当晚有维护施工，保留主电源，由值班人员签字确认。
答案：闭馆时必须保留主电源。
```

这是“条件被省略”。引用片段包含“保留主电源”，但答案删掉了“若……施工”和“签字确认”，结论强度被改变。注意这是人工复核的改写例；助手的自动校验要求 `claim.text` 是 `quote` 的逐字连续子串、`answer` 只列已核验 claims，上面这句改写会被判 `citation-failed`，不能算自动通过。

## 4. top-k 增大后的风险

取回 3 → 8 后可能出现：

- 正确片段仍在，但被更多无关片段包围，模型忽略关键条件；
- 旧版本片段进入上下文，与新版冲突；
- 上下文超预算，前面的材料被截断；
- 延迟和 token 成本上升。

记录答案是否变化、引用是否仍指向正确片段、是否出现冲突。不能只记录“取回更多，效果更好”。

## 5. 为什么分数高不等于事实可信

- 相似度衡量的是表示空间中的接近，不是真值；
- 旧版规则可能与查询高度相似，但已失效；
- 无权限片段可能相似，但不能使用；
- 片段可能只包含结论的一半，缺条件；
- 模型可能误读高分片段，或把两个片段拼成新关系。

因此需要三层检查：检索集合（有没有找对）→ 引用支持（原文是否支持）→ 答案一致性（主张之间是否冲突）。C19 会把这三层用于失败定位。

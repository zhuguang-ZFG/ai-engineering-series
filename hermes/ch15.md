# 第 15 章：迁移、备份和隐私

<!-- block: hermes-ch15.b-opening -->
把 Hermes 搬到另一台机器，最简单的想法是复制整个目录。这样可能带走过期进程状态、绝对路径和不该共享的凭据，也可能漏掉正在写入的数据库内容。迁移要先决定需要延续什么，再选择对应材料。

## 15.1 先列出数据，而不是先打包

记忆和技能是知识材料；会话数据库是历史；config.yaml 是运行设置；凭据是身份；项目文件是工作结果；cron 和 gateway 状态则涉及未来会发生的动作。把它们都叫“配置”会掩盖迁移后的行为差异。

| 材料 | 迁移前检查 |
| --- | --- |
| MEMORY.md、USER.md | 是否含私人信息、旧项目事实或重复条目 |
| skills | 是否依赖本机路径、脚本环境和私人资料 |
| 会话数据库 | 是否需要完整历史、是否有正在写入的进程 |
| config 与凭据 | 新机器是否适用，秘密是否应重新配置 |
| cron 任务 | 恢复后是否可能立刻执行或投递 |
| 项目产物 | 是否来自完整成功运行，有无半成品 |

知识迁移不必等于身份迁移。很多时候只迁移经过筛选的技能与项目记忆，在新机器重新设置凭据，反而更容易验证。

## 15.2 让备份对应一个稳定时刻

普通文件可以在停止写入后复制；SQLite 数据库可能涉及 WAL 和其他伴随状态。不能只复制看起来像主数据库的一个文件，然后宣称备份完整。使用数据库支持的备份方式，或先有序停掉相关进程，再按文档处理整个一致状态。

本书不提供一条未经版本验证的全目录删除或恢复命令。更重要的是保留备份清单、时间、源版本和内容摘要，并在另一个隔离位置做恢复演练。只验证压缩包能解开，不等于应用可以读取其中的数据。

profile 目录也可能有删除标记或身份元数据。钉版 home 工具显式避免后台写入复活已经删除的命名 profile；这说明手工随意创建旧路径不一定等于合法恢复。迁移时应尊重应用的 profile 管理方式，而不是绕过所有状态检查。

## 15.3 公开样例要做内容级脱敏

删掉文件名中的用户名还不够。会话正文、工具参数、绝对路径、远程地址和错误输出都可能包含秘密。技能可能把某次真实任务的内部域名或访问令牌写进示例。记忆则可能保存用户偏好以外的敏感信息。

发布前从内容上筛选，只保留证明结论所需的片段。本书公开的组件结果只包含版本、文件摘要、用例名称与结果，不提交临时 profile 的全部文件，也不把个人配置复制进仓库。原始证据留在忽略目录供本地排查。

脱敏后的结果仍要能理解。例如把全部字段都替换为“已隐藏”，就很难判断两个请求是否属于同一会话。可以使用稳定的虚构 ID 保留关联关系，同时去掉真实身份。

## 15.4 恢复后先关闭自动动作

先验证记忆、技能和历史能读取，再恢复 cron 或平台连接。否则你可能在还没确认目标账号时，就让旧任务向真实频道投递。检查工作目录与挂载，避免旧绝对路径指向新机器上含义不同的位置。

恢复演练可以选一个只读任务：列出指定资料、读取一条记忆、查看一个技能，并检查输出。随后再逐项启用写入和外部服务。每个阶段都保留可回退的备份，避免第一次启动就覆盖唯一副本。

## 15.5 删除也需要明确范围

删除一个 profile，不保证备份、平台历史、外部记忆服务和导出报告同时消失。反过来，为了删除一条私人事实而清空整个项目历史，也可能破坏其他需要保留的工作记录。先列出目标与副本，再选择应用提供的删除入口。

长期使用中，定期检查技能是否仍含过期凭据、记忆是否仍指向旧项目，比只在迁移时清理更有效。让“可共享”和“仅本机”从目录结构与版本管理上分开，也能降低误发布概率。

## 15.6 给 Aurora 做一份能恢复的资料包
先备份项目本身：rules.json、docs、archive、原创检查器版本和必要报告。项目包不需要包含 Hermes 的模型凭据。再单独决定是否迁移 memory、skills 和会话记录；将两部分分开，你就能把资料交给别人复查，而不必交出个人助手的全部历史。

一份项目清单可以记录文件相对路径、字节数与 SHA256。恢复后逐项计算，确认拿到的是同一份输入。Aurora 报告已经保存 docs 范围和规则摘要，但没有自动把被排除的 archive 全部打包，所以它不能直接充当整个项目的备份清单。检查范围与备份范围是两个决定，读者应当分别写清楚。

不要只复制最终报告。第 17 章已经演示，报告可能来自旧输入，或者在配置失败后留在磁盘。保留当时规则和文档，才有机会重做那次检查。如果报告称一个文件不存在，备份中却没有完整目录结构，后来的人就很难判断这是检查正确还是打包漏了文件。

## 15.7 SQLite 的副文件为什么不能随意忽略
SessionDB 使用 SQLite 和 WAL 相关机制。一个正在运行的数据库可能同时有 state.db、state.db-wal 与 state.db-shm。只看到主文件名字最显眼，就在进程持续写入时复制它，可能得不到你以为的完整时点。源码里专门处理这些文件的权限和连接生命周期，也说明它们不是无关的临时垃圾。

对一般操作者，最容易理解的方案是停止相关写入进程，确认它们结束后再做受控备份；对需要在线备份的部署，应使用经过验证的数据库备份方式，并实际恢复到临时位置检查。不要在教程里给一个“复制 *.db”命令就暗示它对所有在线场景都成立。

恢复的目的地应是新的实验 home，而不是直接覆盖正在使用的个人 home。先检查目录、文件权限与版本，再打开数据库。升级后恢复旧数据还涉及迁移路径，不能仅因文件复制成功就判断兼容。将旧备份保留到新环境完成验证，能为失败迁移留下回退依据。

## 15.8 路径可迁移，记忆中的路径未必会自动改变
把 Aurora 从 D 盘移到另一台机器后，项目内容可以保持不变，插件 settings.root 却必须更新。技能若写死本机的完整脚本路径，也需要修改。memory 中保存的“资料在 D:/...”可能继续进入提示，让模型追着旧路径查找。

因此，稳定记忆尽量描述项目内相对位置与查找方式，例如“规则在项目根目录 rules.json”。机器相关的根路径留在配置。迁移检查应同时覆盖配置、技能正文和持久记忆，不能只搜索 Python 文件。一个看似自然语言的旧路径，同样会影响工具调用。

报告中使用相对路径与内容摘要，就更容易比较迁移前后结果。绝对路径改变而输入内容不变，Aurora 的检查结果可以一致。若结果变化，先看规则字节、换行、编码和文件集合，再怀疑运行时差异。这也解释了为什么我们没有把用户名或临时目录写进正式事实报告。

## 15.9 恢复后先观察，再恢复自动动作
迁移不仅带走历史，也可能带走定时任务和平台配置。新机器一启动就恢复所有 cron 与 gateway，可能在你还没确认目录和身份时开始执行。恢复练习可以先只使用本地检查器，核对输入摘要，再逐项恢复需要的能力。

例如先让 book-inventory 指向新 Aurora docs，观察清单；再运行 aurora-review 的确定性步骤；随后在新会话中检查 memory 的项目入口；最后才考虑调度。每一步都依赖前一步已经可用的文件与配置，这样出现错误时不会同时面对模型、平台、数据库和后端四种不确定性。

恢复后不要立刻删除原备份。先记录新版本、恢复日期、核对结果和仍未迁移的内容。若某份技能被主动舍弃，也写明是决定，不要让下次维护者把缺少文件误判为迁移损坏。

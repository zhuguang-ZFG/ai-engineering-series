# 第 15 章：迁移、备份和隐私

<!-- block: hermes-ch15.b-opening -->
把 Hermes 搬到另一台机器，最简单的想法是复制整个目录。这样可能带走过期进程状态、绝对路径和不该共享的凭据，也可能漏掉正在写入的数据库内容。迁移要先决定需要延续什么，再选择对应材料。

## 15.1 先列出数据，而不是先打包

记忆和技能是知识材料；会话数据库是历史；config.yaml 是运行设置；凭据是身份；项目文件是工作结果；cron 和 gateway 状态则涉及未来会发生的动作。把它们都叫“配置”会掩盖迁移后的行为差异。

| 材料 | 迁移前检查 |
| --- | --- |
| MEMORY.md、USER.md | 是否含私人信息、旧项目事实或重复条目 |
| skills | 是否依赖本机路径、脚本环境和私人资料 |
| 会话数据库 | 是否需要完整历史、是否有正在写入的进程 |
| config 与凭据 | 新机器是否适用，秘密是否应重新配置 |
| cron 任务 | 恢复后是否可能立刻执行或投递 |
| 项目产物 | 是否来自完整成功运行，有无半成品 |

知识迁移不必等于身份迁移。很多时候只迁移经过筛选的技能与项目记忆，在新机器重新设置凭据，反而更容易验证。

## 15.2 让备份对应一个稳定时刻

普通文件可以在停止写入后复制；SQLite 数据库可能涉及 WAL 和其他伴随状态。不能只复制看起来像主数据库的一个文件，然后宣称备份完整。使用数据库支持的备份方式，或先有序停掉相关进程，再按文档处理整个一致状态。

本书不提供一条未经版本验证的全目录删除或恢复命令。更重要的是保留备份清单、时间、源版本和内容摘要，并在另一个隔离位置做恢复演练。只验证压缩包能解开，不等于应用可以读取其中的数据。

profile 目录也可能有删除标记或身份元数据。钉版 home 工具显式避免后台写入复活已经删除的命名 profile；这说明手工随意创建旧路径不一定等于合法恢复。迁移时应尊重应用的 profile 管理方式，而不是绕过所有状态检查。

## 15.3 公开样例要做内容级脱敏

删掉文件名中的用户名还不够。会话正文、工具参数、绝对路径、远程地址和错误输出都可能包含秘密。技能可能把某次真实任务的内部域名或访问令牌写进示例。记忆则可能保存用户偏好以外的敏感信息。

发布前从内容上筛选，只保留证明结论所需的片段。本书公开的组件结果只包含版本、文件摘要、用例名称与结果，不提交临时 profile 的全部文件，也不把个人配置复制进仓库。原始证据留在忽略目录供本地排查。

脱敏后的结果仍要能理解。例如把全部字段都替换为“已隐藏”，就很难判断两个请求是否属于同一会话。可以使用稳定的虚构 ID 保留关联关系，同时去掉真实身份。

## 15.4 恢复后先关闭自动动作

先验证记忆、技能和历史能读取，再恢复 cron 或平台连接。否则你可能在还没确认目标账号时，就让旧任务向真实频道投递。检查工作目录与挂载，避免旧绝对路径指向新机器上含义不同的位置。

恢复演练可以选一个只读任务：列出指定资料、读取一条记忆、查看一个技能，并检查输出。随后再逐项启用写入和外部服务。每个阶段都保留可回退的备份，避免第一次启动就覆盖唯一副本。

## 15.5 删除也需要明确范围

删除一个 profile，不保证备份、平台历史、外部记忆服务和导出报告同时消失。反过来，为了删除一条私人事实而清空整个项目历史，也可能破坏其他需要保留的工作记录。先列出目标与副本，再选择应用提供的删除入口。

长期使用中，定期检查技能是否仍含过期凭据、记忆是否仍指向旧项目，比只在迁移时清理更有效。让“可共享”和“仅本机”从目录结构与版本管理上分开，也能降低误发布概率。

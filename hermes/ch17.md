# 第 17 章：长期项目实战

<!-- block: hermes-ch17.b-opening -->
这一章把前面的部件放回 Aurora 资料项目。目标不是证明 Hermes 永远记得一切，而是建立一个可重复的三次会话流程：第一次形成方法，第二次面对变化，第三次检查旧经验是否仍然有效。每一步都留下可观察的文件和判断依据。

## 17.1 准备一份会变化的资料库

创建 docs、rules 和 output 三个目录。docs 放三份虚构文档，其中一份使用旧日期，一份有缺少来源的结论；rules 写本次检查标准；output 保存清单和报告。使用本书 book-inventory 工具只列出 docs 下的 Markdown，不允许任意路径输入。

```text
aurora/
  docs/
    overview.md
    release.md
    references.md
  rules/
    review.md
  output/
```

把项目纳入版本管理，记录初始提交。这样后续的人工改动、Agent 改动和技能修订可以分别查看。不要为了实验把真实内部文档复制进去，虚构材料已足够触发这些机制。

## 17.2 第一次会话：先做完，再提炼

给出明确目标：“只检查 docs，列出日期和来源问题，暂不修改文件。”观察工具清单、读取范围和报告。一个合格结果应给出文件名、问题片段、理由与待确认项，不能只是“整体质量不错”。

任务完成后，再决定哪些经验值得保存。稳定事实可以是“Aurora 的资料规则在 rules/review.md”；方法可以是“清点文件后逐篇检查，每个问题保留来源”；一次性错误列表留在报告中。不要把整份报告塞进长期记忆。

写入之后检查文件和返回值。第 4 章告诉我们，同一加载周期的提示快照未必更新；这不妨碍验证磁盘变化，但下一次会话的使用情况应另行观察。

## 17.3 第二次会话：故意改变前提

人工把资料规则改为“代码块里的示例地址只标占位，不做在线有效性判断”，再开始新会话。要求 Agent 先读当前规则，再检查资料。这个步骤用于观察旧技能是否压过了新要求，而不是考模型能否背出上一次操作。

如果结果仍沿用旧规则，先检查技能正文、项目文档与记忆是否相互矛盾。修改技能时引用本次失败样本，并增加适用条件。不要为了让测试通过而把期望答案直接写进所有文档；那只能证明模型看到了答案。

第二次报告应能解释规则变化，并指出哪些旧问题现在不再算错误。这样的差异说明方法有跟随证据调整，而不是机械重复第一次结果。

## 17.4 第三次会话：从历史找决定

询问“为什么示例地址没有被当成失效链接”。理想流程是找到规则变更或相关会话，引用依据，说明当前适用范围。若只回答“因为我记得你不喜欢检查链接”，就把局部项目规则错误扩大成个人偏好。

然后故意移走一份旧文档，要求重新清点。检查输出是否根据当前磁盘更新，而不是沿用旧清单。长期记忆帮助减少重复解释，不能替代对当前项目的读取。

| 会话 | 核心观察 | 留下的材料 |
| --- | --- | --- |
| 第一次 | 能否正确完成受限任务 | 初始报告、必要记忆和技能 |
| 第二次 | 能否接受新规则并修订方法 | 规则 diff、失败样本、技能 diff |
| 第三次 | 能否找到决定来源并检查现状 | 引用的历史、最新清单与报告 |

## 17.5 最后再考虑定时化

三次人工流程稳定后，才把其中确定的只读部分交给 cron。定时任务读取当前规则，输出新报告，并在没有变化时按约定保持安静。外部投递单独启用，避免把调度成功与通知成功混为一谈。

本书没有实际调用模型完成这组三会话项目，因此不会给出虚构耗时或成功率。它是一套完整的读者实战方案，组件脚本和原创工具提供了可运行基础。评估时记录真实结果，包括模型没有使用技能、错误召回和中断等不理想情况，才有改进价值。

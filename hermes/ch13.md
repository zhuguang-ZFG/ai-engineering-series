# 第 13 章：终端后端与隔离

<!-- block: hermes-ch13.b-opening -->
同一条 `python check.py`，在本机终端、Docker 容器或远程 SSH 中运行，能看到的文件可能完全不同。Hermes 的 terminal 工具提供统一入口，却不能抹平这些环境差异。选择后端之前，应先决定任务需要接触什么，再决定把什么交给它。

## 13.1 后端决定执行发生在哪里

钉版 terminal_tool.py 列出 local、docker、modal、daytona、vercel_sandbox、ssh 等后端，并允许插件提供其他实现。工具还涉及后台进程、环境缓存、空闲清理与退出收尾。一个名字相同的 terminal 调用，可能对应不同的宿主系统和持久化策略。

| 后端类型 | 主要要核对的条件 |
| --- | --- |
| local | 启动账号权限、当前目录、环境变量和本机进程 |
| 容器 | 镜像、挂载、用户、网络与宿主目录暴露 |
| SSH | 远端账号、远端工作目录、密钥与连接生命周期 |
| 云沙箱 | 提供者能力、持久存储、重建和计费边界 |

这张表不是能力排名。只读资料整理可能不需要复杂远程环境；执行不可信项目脚本时，本机账号拥有的权限却往往过大。按任务风险和可用证据选择，避免只因为后端名称带 sandbox 就认为所有边界都成立。

## 13.2 文件持久化不等于进程持久化

云环境可能保存工作文件，同时在空闲后销毁进程。下一次启动时文件还在，但内存中的变量、后台服务器和已打开连接不在。钉版终端模块的说明明确区分持久文件系统与同一个活沙箱的存续。

相反，本地后台进程可能在一次工具返回后继续运行。模型看到命令完成的摘要，并不代表那个进程已经退出。需要观察进程标识、输出、退出状态和清理路径。重复启动同一个服务，可能遇到端口占用，也可能创建两个同时写文件的实例。

把状态写入可检查的文件，并让进程启动能够识别已有实例，会让恢复更可靠。不要把“上一轮终端里 export 过变量”当成跨后端、跨重建都成立的承诺。

## 13.3 挂载是容器边界上的开口

容器无法访问未挂载文件，是有意义的限制；把整个个人目录挂进容器后，这项限制就被大幅削弱。钉版代码会区分某些宿主路径与容器路径，说明路径映射是执行链中的真实问题，而不是一个装饰字段。

推荐先只挂载本次项目和明确需要的只读资料。凭据应按需要提供，避免把整个环境文件透传进去。若工具需要写产物，可以给单独输出目录；若只读检查足够，不必为了方便开放所有项目目录的写入。

还要检查链接：挂载内的符号链接可能指向其他位置，操作系统和容器运行时对它的解析未必符合直觉。用已知内容的哨兵文件验证边界，比看配置名称更可靠。

## 13.4 用哨兵验证，而不用私人文件冒险

在允许目录和禁止目录各放一个虚构标记，要求工具读取允许目录，并测试越界读取是否失败。写入测试也使用专门文件，检查拒绝后字节是否未变。网络测试只访问自己控制的端点，不拿真实内部服务做探测目标。

一次拒绝只说明那条路径在那个配置下被拒绝。还需考虑相对路径、绝对路径、链接、不同 shell 和后台进程。测试结果应保留平台、后端版本、挂载与用户身份，否则升级后很难复现。

本书没有运行这组跨后端矩阵，因此不会说 Windows 原生、Docker 或云环境的完整隔离已经验证。已经运行的记忆实验只使用独立应用目录，未把它称为安全沙箱。

## 13.5 取消之后仍要检查产物

取消通常是请求执行链停止继续工作。它无法保证撤销已经完成的写入，也无法保证外部进程马上响应。遇到长命令，先看进程是否真正终止，再检查临时文件与最终文件，避免把半成品当作上次完整结果复用。

对生成报告的工具，可以先写临时文件，全部成功后再替换目标；对数据库动作，应使用数据库事务或业务幂等机制。Agent 的停止按钮不能代替这些工程设计。

## 13.6 同一条命令在两种后端里读到什么
把 Aurora 项目挂到容器后，宿主上的 .scratch/aurora-lab 与容器里的 /work/aurora 可能指向同一份文件；容器内的 /tmp 却未必对应宿主临时目录。终端工具返回的工作目录应结合后端解释，不能拿一个 Linux 路径去宿主文件管理器里搜索，然后断言产物丢失。

准备两个无敏感内容的哨兵文件：一个放在允许读取的项目目录，另一个放在项目外的专用测试目录。先让工具读取项目内文件，再尝试读取项目外哨兵。结果与挂载配置应一致。若外部文件也可见，先检查是否挂载了整个父目录，而不是马上怀疑容器机制失效。

这个实验验证的是实际可见范围。它不能只靠“配置里写了 container”来替代，因为工作目录、额外挂载、网络和凭据都可能扩大能力。若没有可运行的容器后端，也可以先在本地执行模式中完成项目检查，但应明确它继承当前用户的文件权限。

## 13.7 解释器位置也是输入的一部分
Aurora 检查器只依赖 Python 标准库，仍可能因解释器位置不同而失败。宿主的 python 命令可能指向某个虚拟环境，容器里则可能没有这个命令；同名命令也可能是不同版本。开始任务时保存实际解释器版本和工作目录，能快速排除“模型突然不会用了”这种笼统判断。

计划任务更容易暴露路径假设。交互终端中存在的 PATH、已激活虚拟环境和当前目录，在后台运行时未必相同。第 11 章所列 workdir 与 interpreter 字段之所以重要，是因为它们把这些隐含条件转成可检查的配置。不要只把一条在自己终端成功过的命令复制进调度器，就省略运行环境的核对。

## 13.8 退出、超时和文件状态要分别观察
假设一个工具先写临时报告，再计算附加信息。超时发生时，临时文件可能已经存在，最终报告还没替换完成。我们的 Aurora 写入器先写同目录临时文件，再用 os.replace 发布 latest.json，减少半份 JSON 被当作结果读取的机会；它没有声称提供跨进程事务或断电持久性保证。

取消后先检查进程和产物。若进程仍运行，不要立刻启动第二个相同写入任务；若只留下临时文件，确认它没有被其他任务使用后再清理。对任务本身而言，报告是否完整和命令是否结束是两个条件。一个进程退出码为 0 但写到了错误工作目录，也不能算完成目标。

在共享后端中，把每次运行的临时目录与最终输出位置分开能减轻冲突。Aurora 的 latest.json 适合单个操作者串行练习；第 14 章的并行任务会改用不同产物路径或独立项目副本，再由父任务统一比较输入摘要。这个限制来自例子本身，不应被隐藏在“支持并行”四个字后面。

# 第 8 章：知识冲突、过期与遗忘

<!-- block: hermes-ch08.b-opening -->
MEMORY.md 里写着“Aurora 使用 pytest”，用户现在明确说已经迁到 unittest。正确动作不只是再加一条新句子。若两条互相矛盾的事实都长期进入提示词，后续任务仍可能随机采用旧规则。知识维护需要处理冲突、时间和删除范围。

## 8.1 先判断哪一类冲突

同一事实随时间变化，和两个来源说法不同，是不同情况。项目在昨天完成迁移，可以更新旧条目并保留迁移记录；两个未经确认的报告相互矛盾，应先寻找证据。用户的一次临时要求也不一定意味着长期偏好改变。

可以为重要事实补上三个维度：适用对象、有效时间、来源。比如“Aurora 主分支自 11 月起用 unittest，见项目测试配置”，比“我们用 unittest”更不容易误用。并非每条偏好都需要复杂元数据，但跨项目、会改变工具动作的事实值得写得具体。

| 变化 | 合理处理 |
| --- | --- |
| 新事实替代旧事实 | 对唯一旧条目做 patch 或明确删除后添加 |
| 临时例外 | 留在当前任务或项目说明，避免改全局偏好 |
| 两份来源冲突 | 保存冲突与待核实事项，不擅自选边 |
| 事实已失去用途 | 删除目标条目，并检查是否还有其他副本 |

## 8.2 删除词语之前先确定条目

记忆删除按匹配条目执行，模糊关键词可能同时命中多个对象。本书实验中两条项目笔记都含 unittest，以该词删除被拒绝，磁盘不变。这是有价值的失败：它要求调用方给出更明确的目标，避免删错项目事实。

不要把“无法删除”一律归为权限问题。可能是 old_text 没有命中、命中多个条目、目标被禁用、文件无法读取、发生外部漂移，或者写入正在等待批准。先看返回的错误和文件内容，再决定修正输入还是修复环境。

如果目标条目内容很长，复制一个唯一片段通常比重新概述它更可靠。使用 patch 时还要检查同一个片段是否在条目内部重复出现。删除整个条目与删去其中一个短语，不应使用同一种含糊描述。

## 8.3 从文件移除，不等于从所有上下文抹去

第 4 章已经证明系统提示快照在加载时冻结。中途删除文件里的条目后，旧快照仍可能持有它；历史消息和工具结果里也可能有副本。想确认下一次会话不再自动带入，应重新加载并检查新快照，而不是只看当前文件已经空了。

外部记忆提供者还会引入另一份存储。内置文件删除成功，不自动证明外部索引、备份、聊天平台历史或导出报告已经删除。涉及隐私时，应该列出持有副本的系统并逐个确认，而不是让一个 memory 工具调用承担全部“遗忘”承诺。

这也影响测试：删除后立即问当前模型“还记得吗”，模型可能从刚才的对话中回答。这个结果既不能证明删除失败，也不能证明长期记忆仍在。更清楚的测试要在没有携带旧对话的新加载周期中进行。

## 8.4 防注入扫描的作用和局限

记忆会进入系统提示，因此长期保存恶意指令比一次普通网页文本更危险。钉版存储在写入时扫描内容，加载时也会处理命中的威胁模式。加载阶段可以在提示快照中放入阻止占位，而保留原始条目供用户查看和删除。

保留原文让操作者知道发生了什么，但也意味着不能因为当前提示里没出现攻击文字就以为磁盘已经干净。扫描器属于基于模式的检测，不能保证识别所有恶意内容，也可能对某些合法示例过于敏感。测试扫描逻辑时使用专门隔离样本，避免把攻击语句写进日常 profile。

不要通过关闭所有检查来解决一次误报。先确认内容是否需要进入长期记忆，能否改存项目文档并注明它是待分析材料；确实要调整策略时，保留触发样本与理由。

## 8.5 定期整理比无限扩容更有效

一份有价值的记忆应该越来越准确，而不只是越来越长。可以按项目结束、配置迁移、用户偏好变化这些事件整理，避免无意义的固定频率重写。整理时先找重复、失效和缺少范围的条目，再决定合并或删除。

把记忆整理和技能整理分开：前者关注事实是否仍成立，后者关注方法是否有效。历史检索保留决策过程，可以为两者提供来源。清理完记录变更原因；如果之后发现误删，能够回到明确的版本，比指望模型“自己想起来”可靠。

## 8.6 把一个冲突拆成对象、条件和时间
Aurora 的旧记忆写着“归档不检查”，当前用户说“这次发布也检查归档”。这里不需要先删除一切旧知识。应先辨认旧句是否只是某次任务的缩写：若它本来表示日常检查默认排除 archive，而本次是发布检查，两个条件可以并存；若项目规则已经永久改变，就应更新旧事实。

更合适的记忆可以写成“Aurora 日常检查范围以 rules.json 为准；发布检查可能包含 archive”。它保留了下一次有用的入口，避免把一个布尔值无限期复制到系统提示中。代价是 Agent 每次需要读一次小文件，但这比持续纠正过期的范围判断更可控。

将用户新要求落实到 rules.json 后，运行检查器。include_archive=true 会让 archive/old-plan.md 中指向 removed.md 的链接进入 issues。此时不要为了维持原来的全绿结果直接删除归档文件；它可能仍承担历史记录作用。应决定修复引用、标记历史失效，或调整发布范围，每种选择都应有自己的理由。

## 8.7 一个关键词可能指向不同层次的旧内容
MemoryStore 的匹配有两个容易混淆的歧义。一种是多个条目都含某个子串，例如“Aurora 使用 unittest”和“Beacon 使用 unittest”；另一种是一条内容里同一个片段出现多次。前者无法确定修改哪条，后者无法确定改哪一处。

新增组件实验分别覆盖了它们。已有实验用 unittest 删除两个不同项目条目，得到拒绝；新实验在一个条目中写入“Aurora builds docs; Beacon builds docs.”，再把 builds docs patch 成 checks docs，也被拒绝，磁盘保持不变。正确恢复不是让程序一律全局替换，而是提供包含项目名的唯一片段，或明确重写整条内容。

完整条目相等则优先于子串匹配。文件包含“Aurora”和“Aurora backup”时，remove("Aurora") 会选择完全相等的第一条。我们实际核对了剩下的内容是“Aurora backup”。理解这个顺序后，就能解释为什么两个看似相近的删除请求一个成功、一个被判歧义。

## 8.8 删除的时间也属于结果
假设 store 已在系统提示快照中包含“日常排除归档”，随后 memory 工具成功删除该条。磁盘与活列表变化了，当前加载周期的提示快照仍可能保留旧句。这是第 4 章冻结设计的直接后果。新会话加载时才会以新的文件状态构造快照；当前会话还可能从工具结果知道删除已经发生。

因此，测试遗忘时至少要观察当前对话、新加载的 store 和存储文件三个位置。仅在当前窗口继续追问，模型可能因为刚看到删除工具结果而说“已经忘记”；仅在文件里搜索不到，又不能说明所有历史副本已经删除。把测试目标写成“下一次加载的长期记忆不再包含该条”，会比“系统彻底忘掉这个事实”更容易核对。

历史、备份和调试日志有各自的保留策略。若只是修正过期项目事实，保留历史解释往往有帮助；若目的是清理敏感信息，则需要另行确定这些副本的处理范围。两种任务不应共享一个含糊的“清理记忆”按钮说明。

## 8.9 对手工编辑后的文件保持可解释性
记忆文件是文本，人会用编辑器修改它。BOM、空行和重复条目都可能出现。新实验写入带 BOM 的重复条目，条目中还包含一个普通的 § 字符。load_from_disk 去掉 BOM、去重，并保留普通 §；分割采用完整的换行分隔符，不会见到每个 § 都拆开。

接着调用 resolve_entry，磁盘字节完全没有变化。这个区别很有用：对象里已经规范化，不表示磁盘已经被“自动修好”。若你要比较备份哈希，必须知道是读取时的解释变化，还是一次真正写入。将解析后的字符串直接当成原始文件，会让诊断工具悄悄丢掉编码或格式差异的证据。

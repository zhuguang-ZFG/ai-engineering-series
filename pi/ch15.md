# 第15章 扩展实战：工具、命令、快捷键与 UI

上一章说明代码在哪里加载、事件何时触发。这一章把一个扩展做成可使用的功能：让模型调用工具，让用户通过命令调整状态，并把错误、取消和恢复处理完整。

工具与命令有不同的调用者。`registerTool` 把能力声明给模型，`registerCommand` 把操作入口交给终端里的用户。第 18 章的 pi-purge 只需要命令和事件，因为切换提示词模式由用户决定，没有必要注册一个模型工具。

## 15.1 注册工具：给模型一只手

```typescript
import { Type } from "typebox";
import type { ExtensionAPI } from "@earendil-works/pi-coding-agent";

export default function (pi: ExtensionAPI) {
  pi.registerTool({
    name: "greet",
    label: "Greet",
    description: "Greet someone by name",
    parameters: Type.Object({
      name: Type.String({ description: "Name to greet" }),
    }),
    async execute(_toolCallId, params) {
      return {
        content: [{ type: "text", text: `HELLO ${params.name}` }],
        details: {},
      };
    },
  });
}
```

`parameters` 是 TypeBox schema；Pi 用它生成工具声明并校验参数。`execute` 返回 `content`（模型看到的内容）
和 `details`（供渲染与状态使用，不作为模型正文）。默认的 `direct` 工具注册后通常会激活；`defaultActive: false`、显式 `--tools` 等选择会影响可见集合。诊断时同时检查 `pi.getAllTools()` 和 `pi.getActiveTools()`，分别回答“注册了没有”和“当前声明了没有”。

### 把问候工具换成真实工作：读取 Git 状态

下面是一份完整扩展，书仓也保存了 `pi/examples/git-status.ts`。它只执行固定的 Git 参数，不接收模型拼出来的任意 shell 字符串；路径来自当前会话的 `ctx.cwd`。

```typescript
import { Type } from "typebox";
import type { ExtensionAPI } from "@earendil-works/pi-coding-agent";

export default function (pi: ExtensionAPI) {
  pi.registerTool({
    name: "book_git_status",
    label: "Git status",
    description: "Read the current repository status without changing files",
    parameters: Type.Object({}),
    async execute(_id, _params, signal, onUpdate, ctx) {
      signal?.throwIfAborted();
      onUpdate?.({
        content: [{ type: "text", text: "正在读取 Git 状态……" }],
        details: {},
      });
      const result = await pi.exec("git", [
        "--no-optional-locks", "-C", ctx.cwd,
        "status", "--short", "--untracked-files=no",
      ], { signal, timeout: 10000 });
      signal?.throwIfAborted();
      if (result.killed || result.code !== 0) {
        throw new Error(result.killed
          ? "Git 状态读取超时或被中止"
          : `Git 状态读取失败，退出码 ${result.code}`);
      }
      const output = result.stdout.trimEnd();
      const limit = 6000;
      return {
        content: [{ type: "text", text: output.length > limit
          ? output.slice(0, limit) + "\n[输出已截断]"
          : output || "没有已跟踪文件的改动（未列出未跟踪文件）" }],
        details: { truncated: output.length > limit },
      };
    },
  });
}
```

这里的“没有改动”特意限定为已跟踪文件，因为参数排除了未跟踪文件。`6000` 是本例选择的字符上限，不是 Pi 的限制；大量改动时工具必须明确告诉模型结果已截断。`timeout` 与 `signal` 一起交给 `pi.exec()`，取消后也不继续返回“成功”。

若 Git 不在 PATH、当前目录不是仓库，或者进程被终止，工具会报告错误。抛异常和返回带 `isError: true` 的结果都能让 Pi 识别失败；仅把正文写成“ERROR”不会设置错误标志。进度通知的 `onUpdate` 与最终返回值都需要 `content` 和 `details`。

要让模型试用这个工具：

```bash
pi -ne -e ./pi/examples/git-status.ts --tools book_git_status
```

然后请它调用 `book_git_status` 说明当前变更。这个调用会访问你配置的模型；不想调用模型时，用本章后面的离线脚本检查工具逻辑。若继续扩展成文件修改工具，还应使用宿主的文件变更队列，并考虑并发调用；一个工具能执行成功，不代表两个工具同时修改同一文件仍然正确。

## 15.2 命令、快捷键与 UI

```typescript
pi.registerCommand("checkpoint", {
  description: "给当前状态打一个标记",
  handler: async (args, ctx) => {
    await ctx.ui.notify(`checkpoint: ${args || "unnamed"}`, "info");
    pi.appendEntry("checkpoint", { at: Date.now(), name: args });
  },
});

pi.registerShortcut("ctrl+shift+g", {
  description: "打开 checkpoint 命令",
  handler: async (ctx) => ctx.ui.notify("快捷键生效", "info"),
});
```

- `registerCommand` 加一个 `/checkpoint`；命令输入不走 `input` 事件。
- `registerShortcut` 绑定键位；键位语法见 `docs/keybindings.md`。
- `ctx.ui` 提供 `notify`、`confirm`、`select`、`input`，以及 `custom()`（自定义组件）。
- `pi.appendEntry` 把扩展状态写进会话（`custom` 条目，不进模型上下文；要进上下文用 `custom_message`）。

### 内存开关与会话状态怎么选

`checkpoint` 示例追加的是元数据标记，**没有创建 Git 提交，也没有备份文件**。恢复时要从 `ctx.sessionManager.getBranch()` 读取当前分支，筛出 `type === "custom"` 且 `customType === "checkpoint"` 的条目，再检查 `data` 的实际结构。只调用 `appendEntry`，却不在 `session_start` 重建内存，重启后的界面仍然会丢状态；切换树分支时也要重新计算。

相反，临时模式可以有意不持久化。pi-purge 的开关在 `session_start` 关掉，提醒用户每个会话重新作决定。不要把这类设计一概当成“忘记保存”的缺陷。先确定状态属于当前请求、当前会话还是所有项目，再决定存放位置。

### UI 是反馈，不能代替执行结果

`ctx.ui.notify()` 适合短通知，`setStatus()` 适合显示持续状态，`select()` / `confirm()` 适合用户选择，复杂交互才需要 `custom()`。在调用对话框前先看 `ctx.hasUI`；print、JSON、RPC 的交互能力不同，不能让没有交互端的任务无限等一个确认框。

给状态栏一个自己的键，例如 `book-review`，结束时用同一键清空。若通知里写“已启用”，底层读取却失败，用户会得到错误判断。命令应先完成操作，再更新状态，失败时同时说明当前仍保留什么。pi-purge 的文件读取与页脚状态差异在第 18 章有具体例子。

## 15.3 还能改哪里

| API / 事件 | 用途 |
| --- | --- |
| `registerToolRenderer` / `registerMessageRenderer` | 改工具卡片/消息在 TUI 里的样子 |
| `registerEntryRenderer` | 渲染扩展自己的 `custom` 条目 |
| `registerMarkdownTransformer` | 改 Markdown 渲染结果 |
| `registerProvider` / `registerVirtualModel` | 接自定义 provider 或虚拟模型 |
| `registerMcpServer` | 注册 MCP 服务器 |
| `registerFlag` | 给 CLI 加一个旗标 |

这些都在 `docs/extensions.md` 的 API 参考里，签名以你安装的版本为准。

## 15.4 本章小实验：让模型调用你的工具

**第一步：把 15.1 的代码存成 `/tmp/pi-ext/greet.ts`。**

**第二步：只启用这个工具，让它调用。**

```bash
cd /tmp/pi-ext
pi -e ./greet.ts --print --no-session --tools greet \
  "Call greet with name Pi, then reply with exactly the tool's text."
```

本机实测：stdout 是 `HELLO Pi`，stderr 为空，退出码 0。说明扩展被加载、工具被注册、模型调用成功、
结果回到了回复里。这里的 `--tools greet` 是为实验限定工具集合，并非所有扩展工具都必须手动选中；默认 `direct` 工具会激活，设置 `defaultActive: false` 才默认关闭。

**第三步：命令与快捷键。**

这两项需要交互模式，本章**未在本机验证**。复验时在扩展里注册 `/checkpoint`，启动后敲 `/` 看菜单，
再按 `Ctrl+Shift+G` 看是否有提示。

### 离线检查失败路径

书仓的 `pi/examples/check-git-status.mjs` 注册真实扩展后，用临时 Git 仓库模拟实际调用，检查干净仓库、有修改、不是仓库、取消和输出截断。它不启动模型，也不读取你的项目文件。运行方法见 `pi/examples/README.md`。

这类检查不能证明模型一定会选中工具，但能在模型调用之前发现明确的错误：失败被当成功、取消被吞掉、仓库状态被误报，或返回了无上限的文本。之后再做一次交互调用，检查工具卡片与最终解释是否一致。

## 15.5 翻车对照：扩展实战的六个坑

| 翻车做法 | 会看到什么 | 正确做法 |
| --- | --- | --- |
| 注册了工具但当前未激活 | 模型看不到声明 | 对照全部与活动工具集，查 `defaultActive` 和显式选择 |
| 参数 schema 与 `execute` 的类型不一致 | 运行时报错或参数为空 | schema 与函数签名一起改 |
| 在 `execute` 里返回巨大文本 | 下一轮上下文暴涨 | 先在工具里过滤/截断，再返回 |
| 命令里做重活、不返回 | TUI 卡住 | 用 `ctx.ui` 给进度；长任务放工具里 |
| 把状态写进全局变量 | 重启就丢 | 用 `pi.appendEntry` 持久化 |
| 在扩展里直接读 `.env` 并打印 | 凭据进日志/上下文 | 读可以，别回显；日志写 stderr 也要脱敏 |

## 15.6 与另两册的同构点

御舆那册的插件与钩子、Omp 的扩展，都在做“给 agent 加能力”。Pi 把工具、命令、UI、provider 等入口集中在扩展 API 中，内部仍有各自的注册与执行机制。对照时只借“注册 → 声明 → 调用”这条，不要假设权限审批是内置的。

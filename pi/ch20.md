# 第20章 第一次真实交付：从需求到 diff

前面十九章都在讲机制。这一章只做一件事：让 Pi 真的改一次代码，然后**你自己**验收。

选一个足够小、又能暴露问题的任务：一个无限重试的函数。

```python
def retry(operation):
    while True:
        try:
            return operation()
        except Exception:
            pass
```

它有三个问题：没有次数上限、失败后静默、永远不抛错。我们要把它改成"最多 3 次，最后抛 `RuntimeError`"，
并且让现有测试继续通过。

## 20.1 一次交付的六个动作

```mermaid
flowchart LR
  A["写清目标与验收"] --> B["读相关文件"]
  B --> C["改代码"]
  C --> D["跑测试"]
  D -->|失败| E["看报错，回到 C"]
  D -->|通过| F["复核 diff"]
  F --> G["报告改了什么"]
```

这不是 Pi 发明的流程，是你平时写代码的流程。Pi 的价值是把 B–E 转起来；你的价值在 A 和 F。

```ill

```


## 20.2 任务要写成"可验收"

反例："帮我修一下 retry。"

正例（本章实际使用）：

```text
Fix retry.py so it retries at most 3 times and raises RuntimeError after the last failure.
Keep test_retry.py passing. Run the test and report the result.
```

<!-- block: pi-ch20.b-d004451f -->
三句话分别给了：**改什么、约束是什么、怎么算成功**。没有验收标准的任务，模型只能用"看起来对"来收尾，
而"看起来对"正是第 1 章说的、不能信的东西。

## 20.3 实跑记录

准备两个文件：

```python
# retry.py（改前）
def retry(operation):
    while True:
        try:
            return operation()
        except Exception:
            pass
```

```python
# test_retry.py
from retry import retry

calls = {"n": 0}
def flaky():
    calls["n"] += 1
    if calls["n"] < 3:
        raise ValueError("not yet")
    return "ok"

assert retry(flaky) == "ok"
print("PASS")
```

在 `/tmp/pi-deliver2` 里运行（只给 `read`、`edit`、`bash` 三个工具）：

```bash
pi --print --no-session --tools read,edit,bash \
  "Fix retry.py so it retries at most 3 times and raises RuntimeError after the last failure. Keep test_retry.py passing. Run the test and report the result."
```

本机结果：退出码 0；`python test_retry.py` 输出 `PASS`。改后的 `retry.py`：

```python
def retry(operation):
    last_error = None
    for _ in range(3):
        try:
            return operation()
        except Exception as e:
            last_error = e
    raise RuntimeError("operation failed after 3 retries") from last_error
```

它做了三件对的事：次数上限、保留最后一次异常、用 `from` 串起因果。模型的总结也说清了这三点。

## 20.4 你自己要复核的四件事

1. **diff 是否只动了该动的**：`git diff`（或 `diff -u` 原文件）。这次只改了 `retry.py`。
2. **测试是不是真跑过**：看工具卡片/`bash` 输出，不只看总结。这次 `PASS` 是实际输出。
3. **失败路径是否覆盖**：现有测试只覆盖"第三次成功"，没覆盖"三次都失败"。可以让它补一个，
   或自己加一条断言。
4. **有没有引入无关依赖/文件**：`ls` 一下目录，确认没有多出奇怪文件。

第 3 条是这次交付的真实缺口：**测试通过不等于边界正确**。模型改对了实现，但没证明"三次都失败会抛错"。
这就是为什么第 20.2 节要把验收标准写全——你写"run the test"，它就只跑现有测试。

## 20.5 翻车对照：交付阶段的六个坑

| 翻车做法 | 会看到什么 | 正确做法 |
| --- | --- | --- |
| 只说"修一下" | 模型猜意图，改出你别要的行为 | 写清目标、约束、验收命令 |
| 只看总结不看 diff | 改了三个文件，总结只说一个 | 先 `git diff`，再读总结 |
| 测试通过就收工 | 边界/失败路径没覆盖 | 补失败用例，或明确接受缺口 |
| 给 `bash` 全权限跑不可信仓库 | 命令按你的用户权限执行 | 用容器/独立用户（第 22 章） |
| 让它在主分支直接改 | 回滚成本高 | 新分支/临时副本；先提交或备份 |
| 不看工具卡片 | 模型说"已改"，其实 `edit` 没跑 | 往上翻工具调用与结果 |

## 20.6 与另两册的同构点

三册的实战章都在讲"目标 → 改动 → 验证 → 交付"。御舆那册强调权限与交付边界，Omp 有实战失败路径。
Pi 的差别是**没有内置权限门**，所以"在哪个环境里跑"比"它会不会问你"更重要。
对照时只借"验收标准先写"这条，不要假设三家的安全默认值一样。

下一章把这套流程搬进 CI：没有人盯着的时候，怎么让 Pi 跑、怎么判断成功。

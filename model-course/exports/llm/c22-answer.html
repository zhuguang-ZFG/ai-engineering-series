C22 答案与核对依据

本文件给出指标定义、分位数和费用的算例，以及单因素对照的合格结论。实际质量、延迟和费用必须来自你的报告；没有调用就写“未运行”。

1. 质量指标的答案

至少报告：

summary.passed / summary.total       机械检查通过
strict pass / total                  人工逐例严格通过
supported claims / all claims        主张级支持率
status_counts                        完成/不足/冲突/各类失败
first_failure.stage 分布             失败发生在哪一环

summary.passed 只覆盖 status、expectCitationDocs、expectTool；它不判断 quote 是否支持 claim，也不判断 answer 是否只含已核验文本。机械通过率可以很高，但严格通过率很低；两者不能互相替代。

示例：

  • 12 个用例，机械通过 10 个：10/12≈0.8333；
  • 人工严格复核后只有 7 个满足“状态正确 + 全部 claim 有支持 + 无额外文字”：7/12≈0.5833；
  • 共 20 条主张，16 条支持：16/20=0.8。

结论应同时写三个数，并说明失败用例是本应失败还是意外失败。

2. 延迟的答案

两个字段：

  • usage.latency_ms：模型调用累计耗时；
  • elapsed_ms：整条流水线墙钟时间。

本地第一次调用：

usage.latency_ms 包含模型加载；
usage.model_load_ms 是其中加载部分的耗时；
后续调用 load_ms 通常为 0。

因此：

  • 比较本地冷启动时，要标注“冷”并报告 model_load_ms；
  • 比较热启动时，先预热或只取后续调用；
  • 不要把 elapsed_ms 与 usage.latency_ms 混在一列；
  • API 的 load_ms=0，但 latency_ms 包含网络请求；网络波动要多次采样。

失败用例可能很快返回（例如权限失败、零命中），把所有状态混在一起求平均会制造“更快”的假象。正确做法：

  1. 先看质量/状态分布；
  2. 分别报告 all、model_called、strict pass 的 n 和分位数；
  3. 说明每个子集的含义和选择偏差。

3. 分位数算例

数据（毫秒）：

1200, 1300, 1400, 1500, 1600, 1700, 1800, 9000

排序后不变，n=8。

中位数：

  • 偶数个，取中间两个：第 4 个 1500，第 5 个 1600；
  • (1500 + 1600)/2 = 1550 ms。

nearest-rank p95：

  • 0.95 × 8 = 7.6；
  • ceil(7.6) = 8；
  • 第 8 个值是 9000 ms。

平均值：

(1200 + 1300 + 1400 + 1500 + 1600 + 1700 + 1800 + 9000) / 8
= 19500 / 8 = 2437.5

单位为毫秒。逐项相加：1200+1300=2500；+1400=3900；+1500=5400；+1600=7000；+1700=8700；+1800=10500；+9000=19500。

结论：

  • 中位数 1550 ms，p95（nearest-rank）9000 ms，平均 2437.5 ms；
  • n=8 时 p95 就是最大值，不能宣称“95% 请求在 9000 ms 内”作为稳定估计；
  • 若用线性插值，p95 会不同；必须报告算法。

n=20 时 p95 位置是 ceil(19) = 19；n=100 时是第 95 个。样本少时，报告所有原始值或 min/median/max，比只给一个分位数更诚实。

4. API 费用算例

公式：

cost = prompt_tokens / 1000 × price_input_per_1k
     + completion_tokens / 1000 × price_output_per_1k

假设：

prompt_tokens = 1000
completion_tokens = 200
price_input_per_1k = 0.5
price_output_per_1k = 1.5

计算：

1000/1000 × 0.5 + 200/1000 × 1.5
= 0.5 + 0.3 = 0.8

单位是“你的价格表单位”，不要擅自写成美元。若只提供输入价、没有输出价，或 usage 缺字段，报告 cost=null / prices-not-configured-or-usage-missing，不要只算一半。

本地：

{"cost": null, "cost_basis": "local-compute-not-priced"}

null 不是 0。不要把它加入平均值，也不要在汇总时把 null 当 0；正确做法是单独报告“本地未计价”，API 用例单独汇总。

evaluate 的聚合：

usage.cost = null
usage.cost_basis = "per-case reports"

所以总费用要从 cases[].report.usage.cost 汇总，并且只汇总非 null 的用例；同时报告有多少用例没有价格/usage。

5. 单因素对照的合格结论

条件：

同一验证集、同一文档哈希、同一模型、同一提示模板、同一预算
只改 top_k: 3 → 1

两个清单只有 budgets.top_k 不同，因此哈希不同；它们是两个条件，不能声称“同一个冻结清单”。

合格比较表：

质量指标 top_k=3 top_k=1
样本数 n 实际 实际
机械通过 实际 实际
严格通过 实际 实际
支持率 实际 实际
失败状态 实际 实际

运行开销与上表使用同一次评测记录：

运行指标 top_k=3 top_k=1
调用次数 实际 实际
中位耗时 实际 实际
p95 耗时 实际 实际
费用 本地 null / API 实际 本地 null / API 实际

合格结论示例：

在 12 个验证用例上，top_k=1 的严格通过从 7/12 降到 5/12；其中两个需要同一文档多段证据的用例变成 insufficient-evidence。虽然中位耗时下降、调用次数减少，但质量底线未满足，因此不采用。该结论只适用于这批文档、模型和预算，不外推到其他任务。

不合格结论：

  • 只报“平均快 30%”；
  • n=3 却报 p95；
  • 把本地 null 当 0 说“免费”；
  • 只算输入 token 价格；
  • 在 heldout 上调到变好；
  • 同时改 top_k 和 max_new_tokens；
  • 删掉失败用例后重算。

6. “更快但更差”的定位

一个典型：

  1. top_k 从 3 降到 1；
  2. 某些问题只取回一段，缺少第二段条件；
  3. 模型返回 insufficient-evidence，在检索/生成前结束，elapsed_ms 变小；
  4. 平均延迟下降，但严格通过率下降。

定位证据：

  • 对比两个条件的 status_counts；
  • 找出状态变化的 case；
  • 看这些 case 在 top_k=3 时的 retrieval.hits 和 prompt.used_chunk_ids；
  • 看 top_k=1 时缺少哪个 chunk；
  • 确认不是模型/环境变化。

结论：不是“top_k=1 更快更好”，而是“top_k=1 让部分用例更早失败”。质量底线优先。

7. 冷/热、缓存、批处理、模型选择

  • 冷启动：本地第一次调用包含加载；API 也可能冷启动。报告 model_load_ms，不要把冷/热混在一起。
  • 前缀缓存：只复用相同前缀；不同问题不保证命中；缓存要按读者/版本隔离，避免旧内容或越权内容。
  • 批处理：提高吞吐，可能增加单请求排队和 p95；报告批大小、队列等待和单请求延迟。
  • 模型选择：更小模型可能更便宜，但必须同验证集重测质量；tokenizer/聊天模板变化也会影响引用校验。
  • Agent：每步一次模型调用，工具回执增加上下文；质量没有提升时，固定流程更可预测。

8. 评分表

项目 合格 不合格
质量 机械/严格/支持率/失败分布分开 只看平均或只看一个成功案例
样本 报告 n 和原始值 n=3 报 p95、隐去样本数
分位 写明 nearest-rank/插值 与他人 p95 直接比
延迟 冷/热、model/elapsed 分开 混用字段、把失败当快
费用 本地 null、API 公式和单位清楚 本地当 0、只算一半价格
对照 同验证集只改一个因素 多因素混改、heldout 调参
结论 采用/拒绝都有适用条件 宣称通用提升率

没有实际报告时，以上只能作为检查表；不能写成“已通过”。

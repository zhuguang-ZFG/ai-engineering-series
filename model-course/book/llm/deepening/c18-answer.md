# C18 答案与核对依据

本文件给出划分、冻结、算术和复现的参考答案，不提供一份可抄的“高分结果”。你的报告必须来自自己的文档、模型和实际调用；没有调用就如实写“未运行”。

## 1. 三份题怎么分

一个合格的最小划分：

| 集合 | 建议数量 | 用途 | 包含什么 |
| --- | --- | --- | --- |
| dev | 6 | 反复定位和修改 | 正常、无命中、冲突、越权、缺失源、工具各至少一例 |
| val | 3 | 在候选方案间选择 | 覆盖你准备改动的维度，例如检索、切块、工具 |
| heldout | 3 | 最终只跑一次 | 新问题；若条件允许，换成未参与开发的文档或来源组 |

划分原则不是“随机打乱就行”，而是：

1. **先写判据，再看输出**。`expectStatus`、`expectCitationDocs`、严格通过标准都在运行前写好。
2. **近似重复的题分到同一侧**。两个只差一个词的问句不能一个在 dev、一个在 heldout，否则留出集会被开发集“提前泄露”。
3. **留出集在调参期间不打开**。看过失败并据此改参数后，它已经变成验证集。
4. **文档版本一起冻结**。只冻结问题、不冻结文档，等于允许材料在背后变化。
5. **来源留出和问题留出分开写**。同一批文档上的新问题，只能支持“新问题、旧材料”的结论。

题目中的 6/3/3 只是可操作示例。样本更少时可以减少，但必须报告 `n`，不能用一个案例的成败宣布普遍提升。

## 2. 冻结记录应该有哪些字段

最小记录：

```json
{
  "created_at": "运行前的时间戳",
  "note": "before any model call",
  "manifest": {
    "path": "eval-dev.json",
    "sha256": "清单文件字节的 SHA-256",
    "bytes": 1234
  },
  "documents": {
    "docs/station-log.md": {
      "sha256": "文件字节的 SHA-256",
      "version": "1.0.0"
    }
  },
  "budgets": {
    "top_k": 3,
    "max_new_tokens": 192,
    "max_prompt_tokens": 2048,
    "max_steps": 3,
    "max_tool_calls": 2,
    "repair_attempts": 0,
    "chunk_chars": 480,
    "chunk_overlap": 80,
    "min_score": 0.08
  },
  "model": "本地模型目录或 API 模型名；不写密钥",
  "runner": "assistant.py 版本/代码提交标识"
}
```

核对要点：

- `created_at` 必须早于第一次 `run` / `evaluate`；
- 清单哈希覆盖整个 JSON 字节，不只是 `cases` 数组；
- 文档哈希逐个文件记录，不能只写目录名；
- 模型只写路径/名称和版本，不写 API key；
- 预算与清单里的 `budgets` 一致；
- 修改任何一项后，旧哈希作废，不能继续拿旧基线比较。

`evaluate` 自带的 `manifest` 记录是：

```text
path, sha256, size, mtime_ns, frozen_at
```

运行结束后看 `manifest_unchanged`。若为 `false`，说明运行期间清单字节变了；这次结果不能作为对照。它不检查文档和模型，所以外部冻结表仍然必要。

## 3. 指标算术

### 3.1 主张支持率与严格通过率

示例：10 个用例，共提出 22 条主张，人工核对后 17 条有支持。

- 主张支持率：\(17/22\approx0.7727\)，即 77.3%。
- 若 10 个用例中只有 6 个满足“状态正确 + 全部主张有支持 + 无额外文字”，严格通过率是 \(6/10=60\%\)。
- 两者不矛盾：主张级看局部，用例级看能否交付。
- 某用例没有提出主张：主张级分母不加 0，写 `n/a`；用例级仍按状态和“是否应有主张”判断，不能算自动通过。

一个常见错误是把“支持”理解成“quote 存在”。正确顺序是：

1. 先确认 quote 在对应 chunk 和版本中逐字存在；
2. 再读上下文，确认条件、否定、时间范围没有被截断；
3. 最后判断 claim 是否只是对 quote 的逐字提取。若不是，当前助手会以 `citation-failed` 拒绝；人工复核也不应把它算作支持。

### 3.2 检索精确率/召回率

题目表格的计算：

| 查询 | TP | FP | FN | P | R | hit |
| --- | --- | --- | --- | --- | --- | --- |
| Q1 | 1 | 2 | 2 | 1/3 | 1/3 | 1 |
| Q2 | 2 | 0 | 0 | 1 | 1 | 1 |

- 微平均精确率：\((1+2)/(3+2)=3/5=0.6\)。
- 微平均召回率：\((1+2)/(3+2)=3/5=0.6\)。
- 宏平均精确率：\((1/3+1)/2=2/3\approx0.667\)。
- 宏平均召回率：同上 \(2/3\)。
- 命中率：两个查询都至少命中一个相关片段，\(2/2=1.0\)。

核对要点：

- Q1 的检索分母是 3（实际取回 3 条），不是相关总数 3；两个数恰好相等，容易混淆。
- Q2 只取回 2 条，分母是 2；`top_k=3` 并不强制凑满 3 条。
- 微平均给大查询更多权重；宏平均给每个查询相同权重。两者都要写明。
- `hit=1.0` 不代表召回高；Q1 只找到了三分之一的相关内容。

### 3.3 一个可复算的 aggregate 例

假设三个查询：

| 查询 | 相关数 | 取回数 | TP |
| --- | --- | --- | --- |
| A | 2 | 3 | 1 |
| B | 3 | 3 | 3 |
| C | 1 | 1 | 1 |

- 微平均：\(P=5/7\approx0.714\)，\(R=5/6\approx0.833\)。
- 宏平均：\(P=(1/3+1+1)/3=7/9\approx0.778\)，\(R=(1/2+1+1)/3=5/6\approx0.833\)。
- hit：3/3 = 1.0。

这组数说明微/宏可以给出不同的精确率；报告不能只写一个“0.75”而不说口径。

## 4. 提取式契约的三个最小复现

材料原文：

> 地点尚未确定。

| 编号 | claim | quote | 结果 | 说明 |
| --- | --- | --- | --- | --- |
| A | 地点已确定为图书馆 | 地点尚未确定 | `citation-failed` | claim 不是 quote 的逐字提取；旧实现曾错误放行，修复后拒绝 |
| B | 地点尚未确定 | 地点尚未确定 | 机械通过 | 文本一致，但只说明材料没给地点；语义是否回答问题仍要人看 |
| C | answer 含“地点尚未确定。因此地点是图书馆”，claim 只含第一句 | 地点尚未确定 | `citation-failed` | answer 含有已核验 claim 之外的推断文字 |

答案要点：

- A 的失败边界在 `validate` 阶段，不是检索阶段；检索可能完全正常。
- B 只是“引用和提取一致”，不是“事实为真”或“回答有用”。逐字 quote 不自动验证改写、因果和推断。
- C 说明最终 answer 也受约束；把推断塞进 answer 而不放进 claim 仍会被拒绝。
- 这些是提取式契约的机械边界，不是对所有自然语言蕴含的通用判断；语义支持必须人工复核。

## 5. 为什么 `summary.passed` 不够

`evaluate` 的 `passed` 只要求：

```text
status in expectStatus
AND 所有 expectCitationDocs 至少被引用一次
AND 若指定 expectTool，则存在成功回执
```

它不检查：

- quote 是否真的支持 claim；
- claim 是否回答了问题；
- answer 是否有额外推断；
- 工具结果是否被错误使用；
- 失败是否发生在正确阶段。

因此可能出现 `passed=true` 但答案无用，也可能 `passed=false` 但失败原因正是我们想覆盖的安全路径。正确报告方式是：

```text
summary.passed / total（机械检查）
strict pass / total（人工逐例）
claim support / total claims
status_counts 与 first_failure.stage 分布
```

并明确哪些用例本来就应失败（如 `model-missing`、`api-unconfigured`）。

## 6. 清单变更实验

操作：

1. 跑完基线，保存 `baseline.json`；
2. 修改 `eval-manifest.json` 一个字节（例如改一个 `note` 的标点）；
3. 再跑 `evaluate`；
4. 观察新结果的 `manifest.sha256` 与 `manifest_unchanged`。

预期：

- 新旧 `manifest.sha256` 不同；
- 第二次运行的 `manifest_unchanged` 仍可能为 `true`，因为它在**第二次运行期间**没有变化；不要把它误解为“和第一次同一版本”；
- 正确结论是“两次运行使用了不同清单，不能直接比较”。要看的是两次各自的 `manifest.sha256`，以及你的外部冻结表。

如果运行中清单被改，第二次读取的哈希会与第一次不同，`manifest_unchanged=false`；这次结果应丢弃。

## 7. 单因素对照

合格对照必须同时满足：

- 同一批 val 用例、同一文档哈希、同一模型、同一提示模板；
- 只改一个参数，例如只把 `top_k` 从 3 改成 5；
- 两个条件各有自己的清单版本和哈希；
- 先定质量底线，再看延迟/费用；
- 即使结果变差，也如实报告并给出“不采用”。

不合格对照：

- 同时改切块、提示和模型；
- 在 heldout 上试到变好为止；
- 删掉失败用例后重算；
- 只报平均值，不报样本数和失败阶段；
- 把一个案例的提升写成“普遍提升 20%”。

## 8. 评分表

| 项目 | 合格 | 不合格 |
| --- | --- | --- |
| 划分 | dev/val/heldout 用途清楚，近似重复分开 | 同一题跨集合、留出集反复调参 |
| 冻结 | 清单/文档/预算/模型在调用前有哈希 | 先跑后补、只写“我记得” |
| 判据 | 状态、引用、人工支持、失败阶段分开 | 只看 `passed` 或只看截图 |
| 算术 | 分母、微/宏、样本数写清 | 百分比无分母、把 hit 当召回 |
| 提取契约 | 区分机械通过和语义支持 | 声称“有逐字 quote 就证明改写成立” |
| 对照 | 单因素、同验证集、有拒绝结论 | 多因素混改、只挑成功案例 |
| 失败保留 | 失败状态和 `first_failure` 保留 | 删失败、改门槛、手工补答案 |

任何一项“不合格”，这次评测就不能支撑“改进成功”的结论；可以继续做，但不能把未验证的东西写成已验证。

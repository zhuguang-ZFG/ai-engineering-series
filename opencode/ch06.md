# 第 6 章：工具注册与执行管线

<!-- block: opencode-ch06.b-opening -->
自定义工具把模型的一次请求接到真实代码。一个可靠的工具要说明可接收什么参数、执行前检查什么、返回什么，以及取消和失败会留下什么；只给函数起个名字还不够。

## 6.1 从一个固定文件开始

本章的工具只读取当前项目的 `fixture.txt`，没有路径参数。这个限制是刻意的：先把注册、权限、执行和返回接起来，再增加任意路径、目录遍历等复杂情况。完整原创源码在 [read-fixture.ts](examples/read-fixture.ts)。

```typescript
import { readFile } from "node:fs/promises";
import { join } from "node:path";
import { tool, type Plugin } from "@opencode-ai/plugin";

export const ReadFixture: Plugin = async () => ({
  tool: {
    book_probe: tool({
      description: "Read fixture.txt after checking book_read permission.",
      args: {},
      async execute(_args, context) {
        await context.ask({
          permission: "book_read",
          patterns: ["fixture.txt"],
          always: ["fixture.txt"],
          metadata: {},
        });
        if (context.abort.aborted) throw new Error("Fixture read was cancelled");
        const output = await readFile(join(context.directory, "fixture.txt"), {
          encoding: "utf8", signal: context.abort,
        });
        return { title: "Project fixture", output, metadata: { source: "fixture.txt" } };
      },
    }),
  },
});
```

工具 ID 是 `book_probe`，内部申请的权限名是 `book_read`。这两个名字分开，便于下一章观察“工具对模型可见”和“执行中的读取获准”两道判断。普通插件也可以使用同名权限；这里不是强制命名规范。

## 6.2 工具从哪里注册

钉版 registry 有两条自定义入口：扫描配置目录中的 `{tool,tools}/*.{js,ts}`，以及读取已加载插件返回的 `Hooks.tool`。本例走第二条。工具目录的 default 导出使用文件名作工具 ID，其他导出则组合文件名和导出名；插件对象中的键则直接成为 ID。

不要把两种入口同时指向同一个实现而不检查重复。也不要把内部工具 ID 当成用户界面标题：ID 用于协议和权限匹配，description 用来帮助模型判断用途，返回的 title 用来展示某次结果。

公共 `tool()` 包装提供类型与 schema 辅助，钉版实现本身返回传入定义。真正的注册、参数转换和执行发生在宿主 registry 中。把一个普通对象包进 `tool()`，不会自动增加权限检查、重试或文件隔离。

## 6.3 schema 与执行器共同决定边界

添加参数时，使用明确的 schema。例如限定枚举比接收任意字符串再拼 shell 命令更容易检查。schema 是第一道格式约束，业务规则仍应在执行器里处理：文件是否位于允许目录、选项组合是否成立、目标是否已经存在，都不是一个 string 类型能保证的。

registry 会把公共 Zod 参数描述转换为模型所需的 JSON Schema，并在宿主一侧保留验证。工具定义还可能经过 `tool.definition` Hook 修改，因此排查“模型为什么传了这种参数”时，要看最后送出的 schema，而不只看初始源码。

## 6.4 结果很大时会发生什么

工具可以返回字符串，也可以返回含 output、title、metadata 和附件的对象。registry 将它们归一化，再处理输出截断。固定源码中的默认上限是 2000 行与 50 KiB，同时允许配置或调用选项改变限制。

超限内容会保存到截断目录，模型收到预览和后续读取提示。上限按 UTF-8 字节计算，所以中文字符数量不能直接按字节上限估算。metadata 里会记录截断状态及输出路径，调试时应检查它们，而不是因为模型只看见一部分就断言工具执行丢了数据。

本书的 fixture 很小，没有触发截断；上述数字和保存路径行为是钉版源码结论。工具若返回包含密钥的超长日志，即使预览没显示密钥，完整日志仍可能已经写入截断文件。应该在产生结果时就筛掉不该返回的信息。

## 6.5 取消信号要送到真正干活的函数

样例先检查 `context.abort.aborted`，再把 signal 传给异步 readFile。这让等待中的操作有机会响应取消。它并不构成“所有工具取消都完整回滚”的保证；若操作是写数据库，取消通常不会把已提交事务倒回去。

本轮宿主实验验证的是允许与拒绝，不是中途取消。取消用例需要人为控制执行器停在可观察位置，再取消并检查文件与回调，不能只在函数开头传一个已取消信号就宣称覆盖真实时序。

失败时保留错误语义。文件不存在就让读取失败，不要返回一个与正常正文形状相同的“找不到文件”字符串，除非协议明确把它标成错误；否则模型和上层统计很难区分工具失败与成功读取到一段错误说明。

## 6.6 本书实际检查了哪些输出

权限驱动用包装器记录 entered、approved、read-done，包装器调用的仍是上述原创实现。允许时必须出现完整顺序，下一次模型请求还必须带有文件标记；拒绝时只允许 entered 出现。这样既观察权限结果，也观察副作用前后的代码位置。

示例按真实 `@opencode-ai/plugin@1.19.5` 类型严格检查，并在官方宿主中运行。读者修改返回值、错误处理或导入依赖后，可以复跑同一脚本；只检查 TypeScript 编译通过不能代替宿主加载实验。

# 第 11 章：LSP、搜索与代码上下文

<!-- block: opencode-ch11.b-opening -->
找代码既可以按文本检索，也可以问语言服务“这个符号在哪里定义”。两条路径回答的问题不同：搜索找到字符，LSP 结合项目和语言规则提供语义信息。模型仍需判断哪些证据与任务有关。

## 11.1 从报错找起，别先把整个仓库读进来

遇到失败测试，先定位报错文件、调用位置和相关定义。文本搜索适合找错误消息、配置项和函数名；语言服务适合跟踪定义、引用和诊断。读取目标文件后，再检查它依赖的类型或模块。

这是一种任务策略，并非 OpenCode 保证每次都采用的固定顺序。它的好处是留下可核对的证据链：为什么读这个文件、从哪里走到下一个文件。一次把大量源码塞进上下文，可能增加成本，也更难解释模型为何遗漏关键条件。

```mermaid

  E[失败测试或报错] --> S[文本搜索定位]
  S --> R[读取局部代码]
  R --> L[LSP 定义、引用、诊断]
  L --> H[形成修改假设]
  H --> T[运行针对性测试]
  T -->|仍失败| R
```

## 11.2 LSP 客户端怎样对应项目

钉版 LSP 服务按文件选择服务器和项目根，并管理已经启动的客户端。相同 server 与 root 的启动会通过正在启动的记录协调，避免简单重复创建。客户端准备好后再发送文件与诊断相关请求。

语言服务的项目根可能不同于 Git 工作树根。一个 monorepo 包含多个语言项目时，不能因为两个文件在同一仓库就认定它们使用同一个 LSP 实例。遇到诊断缺失，检查服务器识别的 root、配置文件和依赖。

配置还可以关闭全部 LSP 或某个服务，覆盖命令和文件扩展。实验关闭下载后，没有语言服务运行是预期结果，不应把它解释成 OpenCode 不支持相应语言。

## 11.3 诊断是特定时刻的结果

文件变化、依赖安装和项目配置变更都可能改变诊断。某一轮读取到“没有错误”，不意味着随后修改后仍然正确。工具需要让语言服务知道文件变化，并等待相应结果；具体时序会受服务实现影响。

源码里的 touchFile 和诊断接口说明宿主会主动与语言服务交互，但不是所有诊断都等价于构建结果。类型检查可能没有执行测试，LSP 也可能缺少 CI 中的环境变量或生成代码。

因此，修改后仍要执行项目规定的检查。把 LSP 作为快速反馈，而不是让“编辑器没有红线”替代真实测试。尤其是运行时异常、网络协议和数据库约束，通常超出静态诊断范围。

## 11.4 读取代码也会带入邻近指令

第三章提到，指令服务会在读取文件时寻找附近规则文件。这样一个模块的约定可以在需要时加入上下文，但也要求排查者知道它何时加载。

假设根目录要求使用通用测试命令，而子目录说明某个包必须先生成代码。模型没有读过子目录规则时，可能只执行根级命令。解决办法是让任务描述明确模块范围，并检查实际加载内容；不能依赖一个从未进入请求的文件影响行为。

不可信源码或日志也可能含指令式文字。它们应作为任务数据来分析，不能因为出现在工具结果里就变成新的高优先级要求。提示词层可以提醒模型注意来源，执行层仍须守住工具权限与文件边界。

## 11.5 做一个有用的有无 LSP 对照

固定仓库提交和测试任务，分别关闭与开启语言服务，记录检索路径、实际请求、诊断和最终检查。不要只比较耗时；如果一轮读到更多文件却修复了不同问题，数字不可直接对比。

本轮未做此对照，也未给出语言服务带来的成功率结论。实际部署时，优先确认服务能稳定启动、项目根正确、依赖与 CI 接近，再考虑性能优化。

# 第 17 章：把一次修复做成可审阅的结果

<!-- block: opencode-ch17.b-opening -->
完整工程任务的终点是可检查的代码与结果。本章用一个很小的价格计算错误组织从复现、定位、修改到交付的流程，让读者把前面的会话、工具、权限和版本控制放到同一项工作里。

## 17.1 准备一个不会牵连业务的练习项目

假设一个函数接收商品单价、数量和折扣，返回保留两位小数的总价。下面的错误版本过早取整，会把分币信息丢掉。它是本书原创练习，不是上游 OpenCode 的真实缺陷。

```python
from decimal import Decimal

def total(unit_price: str, quantity: int, discount: str = "0") -> Decimal:
    subtotal = int(Decimal(unit_price) * quantity)
    return Decimal(subtotal) * (Decimal("1") - Decimal(discount))
```

在新建临时 Git 仓库保存函数与测试，不加载真实项目的插件或凭据。先人工运行测试并确认失败，再让 Agent 解释失败原因。如果第一次运行就通过，说明练习输入没有覆盖错误，不能继续把它当成修复基线。

## 17.2 任务描述应包含可观察条件

可以这样写任务：“修复 total 的小数精度问题。保持函数签名，新增必要边界测试，结果按 ROUND_HALF_UP 保留两位小数。数量不能为负，折扣必须在 0 到 1 之间。完成后运行测试并说明改了什么。”

这份任务给出业务规则和完成条件，但没有提前指定具体修改行。模型需要读代码、解释为何 int 丢失精度，再提出方案。若只说“优化价格计算”，它可能改命名、换库或添加与你无关的功能。

输入值是否有限也应明确。Decimal 能表示 NaN 和 Infinity；若这是面向账单的函数，应拒绝它们，而不是任由比较或量化阶段产生难以解释的异常。业务边界越明确，测试越有意义。

## 17.3 先用读取和测试建立证据

在初始阶段只允许读取相关文件和运行指定测试。记录失败断言，例如 `19.99 × 2` 应为 `39.98`，错误实现却产生 `39`。然后查看函数，确认问题确实来自 int，而不是测试数据或舍入规则。

如果需要修改代码，再按任务授权开放相应写入能力。权限应服务于这个流程，不必为了“自动化”一开始就给所有工具允许。第七章已经证明，工具可见与具体操作获准可以分开设计。

## 17.4 一份可讨论的修复

```python
from decimal import Decimal, ROUND_HALF_UP

def total(unit_price: str, quantity: int, discount: str = "0") -> Decimal:
    price, rate = Decimal(unit_price), Decimal(discount)
    if not price.is_finite() or not rate.is_finite():
        raise ValueError("price and discount must be finite")
    if price < 0 or quantity < 0 or not Decimal("0") <= rate <= Decimal("1"):
        raise ValueError("invalid price, quantity or discount")
    return (price * quantity * (Decimal("1") - rate)).quantize(
        Decimal("0.01"), rounding=ROUND_HALF_UP,
    )
```

这里保留十进制计算直到最后一步，再按业务规则舍入。它仍需要调用者遵守 quantity 的整数契约；若接口直接接收不可信 JSON，就应再做类型解析，不能把 Python 类型标注当成运行时校验。

最低限度的测试应包括正常小数、零数量、满折扣、非法折扣和非有限数。还应增加一个真实触发舍入的输入，例如 `0.05` 打五折得到 `0.03`。测试应检查需求行为，避免只是把实现公式复制到测试里再比较。

## 17.5 检查代码差异，再检查最后答复

让 Agent 运行测试后，你或流水线还需要读取实际输出和退出码。然后查看 diff，确认没有把测试删掉、放宽断言或修改不相关文件。若测试工具在另一个工作目录运行，绿色结果也不能证明当前改动正确。

```bash
git diff --check
git diff --stat
python -m unittest discover -s tests -v
```

这些是项目练习的命令，不是要求读者在任何仓库都照搬。实际项目以它自己的检查入口为准。最终说明应包含错误触发、修复效果、验证结果和仍有的限制，不必罗列每次打开文件的过程。

## 17.6 这项练习证明什么

本书提供的是可人工复现的工程流程和参考实现，没有声称某个真实模型在本轮自动完成了这个修复。此前宿主实验用确定的替身模型，证明执行链；这个练习则帮助你在自己的真实模型环境中评价任务完成质量。

做对照时固定仓库初始提交、测试、权限和模型版本，保存实际差异。不要只计最终回答长度，也不要因一次成功就推断普遍修复能力。模型可能换一种正确实现，测试和审阅应允许合理差异。

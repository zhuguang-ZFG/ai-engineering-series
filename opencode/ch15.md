# 第 15 章：调试与可观察性

<!-- block: opencode-ch15.b-opening -->
调试 Agent 时，日志越多不一定越有用。最有效的记录能把一次用户任务、一次模型请求和一次工具调用连起来，并指出错误发生在加载、规划、权限还是执行阶段。

## 15.1 先给问题定位到一层

“插件没生效”至少可能表示文件未发现、导入失败、初始化失败、Hook 未触发、输出被覆盖，或修改没有进入最终请求。不同问题需要不同证据，不能都靠在初始化函数里加 console.log 解决。

| 现象 | 先核对 | 后续证据 |
| --- | --- | --- |
| 没有初始化事件 | 配置来源、路径、pure 参数、模块语法 | 插件加载事件与错误 |
| 初始化了但工具不见 | Hooks.tool、工具 ID、权限隐藏 | 最终模型 tools 列表 |
| 工具进入后不继续 | pending permission、超时、执行器 | 请求 ID、批准/拒绝事件 |
| 修改源码后仍旧行为 | 实例与模块生命周期 | 同进程计数、重启后的请求 |
| 结果看起来成功但任务没变 | 工具输出与真实文件 | diff、测试和外部状态 |

这张表的价值在于下一步可以具体执行。不要一开始就升级全部依赖或删除整个缓存；那会同时改变很多变量，让你失去定位根因的机会。

## 15.2 用调用 ID 关联前后，而不是靠时间猜

第八章的 review-trace 使用 sessionID 与 callID 作为联合键。只按工具名记录，无法区分并发的两个 read；只按 callID 记录，则可能混淆不同会话的同名调用。

时间戳用来排序和估算耗时，不能代替身份。两个并发操作可能在同一毫秒发生，日志也可能被缓冲后一起写出。先用 ID 关联，再解释时间差，才能避免把另一次调用的结果配到当前请求。

对于自定义工具，可以记录操作种类、必要的相对目标、状态和错误类别。默认不要原样记录全部 args、提示词与工具正文，因为这些字段可能含源码、用户信息或凭据。

## 15.3 真实 SDK 日志与本地事件文件各有什么用

review-trace 调用 `client.app.log`，由真实服务端写日志；宿主实验的包装器同时把事件写到临时 JSONL 文件。前者证明 SDK 请求走通，后者提供更容易断言的精确事件顺序。

两者都不是完整审计系统。SDK 请求失败时观察器允许丢日志；本地写文件也可能受磁盘错误影响。必须完整保存的操作应采用适合业务的持久记录机制，不能把教学观察器的尽力日志提升为合规保证。

日志还可能改变时序。异步 Hook 中 await 一个慢网络日志，会拖延工具继续执行。测到 duration 增加时，应区分工具自身、其他插件和日志发送的时间，不要直接将它当作工具性能退化。

## 15.4 先用小实验缩短反馈

修改纯处理器逻辑，先运行八项 Node 实验；修改插件发现、依赖或生命周期，再运行真实宿主；修改工具审批，再跑十场景驱动。每组实验回答不同问题，没必要每改一句文案就重装整个环境。

复现失败时保留原始输出。若后续修好了语法错误或路径问题，在记录里解释修复点，而不要把失败日志改写成成功。脱敏摘要可以很短，但必须能追溯到固定脚本和版本。

一个典型错误是从包中导入运行时工具辅助函数，却没有在宿主能找到的位置安装依赖。TypeScript 可能在开发目录解析成功，临时项目的动态 import 却失败。这时应检查实际加载目录，而不是删除类型声明绕过问题。

## 15.5 排错记录怎样留下来才有用

写下触发条件、错误阶段、根因和最小修复。比如“实例 dispose 后重新初始化但模块仍缓存，进程重启后新源码生效”，比“重启解决”更有信息。前者告诉读者哪层状态仍存在，后者只是动作。

升级后先复跑这类历史故障样例。它们代表真实踩过的边界，比为了覆盖率编一个与实现逐行对应的测试更有价值。没有再发生的问题也应保留明确版本范围，避免旧 workaround 永久留在代码里。

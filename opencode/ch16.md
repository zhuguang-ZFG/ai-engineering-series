# 第 16 章：插件发布与兼容升级

<!-- block: opencode-ch16.b-opening -->
把 `review-trace.ts` 放进自己的插件目录能够工作，换成一个 npm 包却不加载，这并不矛盾。本地文件和发布包经过的检查不同，开发目录还可能替你补齐了缺失依赖。发布之前要验证的是别人实际拿到的文件，以及固定宿主怎样解析、导入和初始化它们。

## 16.1 先确定发布物里应该有什么

第八章的观察器只在类型层导入 `Plugin`。正常编译后，这个 `import type` 不需要运行时加载 `@opencode-ai/plugin`。第七章的自定义工具则调用包中的 `tool()`，属于真实运行时依赖。两者都在编辑器中显示类型提示，打包要求却不同。

建议为发布准备一个独立包目录，让源码、编译输出和实验材料的位置清楚：

```text
opencode-review-trace/
  package.json
  src/
    index.ts
  dist/
    index.js
  README.md
  LICENSE
```

源码与测试可以留在开发仓库，包的 `files` 决定实际分发范围。以下仅展示包结构，不是已经通过 npm 宿主兼容实验的完整模板：

```json
{
  "name": "@your-scope/opencode-review-trace",
  "version": "0.1.0",
  "type": "module",
  "exports": {".": "./dist/index.js"},
  "files": ["dist", "README.md", "LICENSE"]
}
```

`exports` 指向的文件必须实际生成；`type` 应与产物的模块语法一致。若编译输出仍引用某个包，就要说明由谁提供它，不能因为开发机器上的工作区碰巧安装了该包，就把它从发布依赖中漏掉。

README 应写插件做了什么、使用哪条 V1 接口、如何配置和停用。观察器可以明确写“追加审查提示、关联工具前后事件、尽力记录日志”；不能写成“阻止危险工具”，因为它没有承担那项职责。包名、许可证和分发文件也在这一阶段确定。

## 16.2 顺着加载器区分五种失败

钉版 `loader.ts` 把配置声明先变为 Plan，再解析成包含 source、target、entry 和包元数据的 Resolved 对象。只有前面的解析成功，才执行动态 import。错误阶段不是装饰字段，它直接告诉你应查哪一份材料。

| 阶段 | 加载器正在做什么 | 发布包的排查方向 |
| --- | --- | --- |
| install | 把 spec 解析为本地目标 | 版本是否存在、目标是否取得、依赖准备情况 |
| entry | 按 server/tui 种类查找入口 | 元数据和实际文件能否对应 |
| missing | 找到目标但没有所需种类入口 | 是否拿 TUI 包当作 server 插件 |
| compatibility | 对 npm 来源检查宿主兼容性 | 声明是否覆盖当前宿主版本 |
| load | 动态导入解析出的入口 | 模块格式、运行时依赖、顶层执行错误 |

missing 与包完全损坏不同。加载器为它保留独立回调，让调用方仍可读取包元数据；源码举出的用途是没有代码入口、但包含主题资源的 TUI 包。因此看到“没有 server entrypoint”时，应先确认安装的是哪一种插件，不要立即归结为下载失败。

导入成功后还有初始化。V1 的 `applyPlugin` 负责提取插件函数并调用，得到 Hooks；工厂抛错发生在这里，不能靠重新填写 exports 修复。发布测试至少要走到你关心的 Hook 或工具真正执行，单独运行 `import()` 只能证明模块能装载。

## 16.3 为什么本地文件通过，npm 包却被跳过

源码只对 `base.source === "npm"` 执行 `checkPluginCompatibility(base.target, InstallationVersion, base.pkg)`。本地 file 插件被当作开发代码，跳过这道门。所以本地成功不能代替发布包的兼容性检查。

兼容函数从 `./shared` 导入。这里已核对调用点，但没有取得该固定文件的完整实现，也未运行 npm 首次安装与兼容声明实验，因此不猜测一个 package.json 字段让读者照填。真正发布时，应沿调用点进入相同提交的实现，确认它读取什么字段、怎样解释版本范围，再对照待发布包元数据。把普通 Node 版本声明误当成 OpenCode 兼容范围，也可能让包在错误层面“看起来写全了”。

版本范围表达作者愿意支持的集合，验证记录表达实际跑过的组合，二者应同时存在。一份说明可以写清“本轮在 Windows x64、OpenCode 1.19.5 的 V1 server 路径运行四场景；其他平台和 V2 未验证”。若将来宣称支持一个更宽范围，就需要有相应理由和代表性组合，不能只把单版本测试的数字改成星号。

## 16.4 导出辅助函数也可能改变插件形状

`review-trace.ts` 当前导出一个插件工厂 `ReviewTrace`。固定 V1 实现先尝试识别模块式插件；进入旧式导出处理时，会遍历模块导出值，去重后检查它们是否为可用插件函数或含 server 函数的对象。不符合形状会抛出类型错误。

因此，发布时为了方便测试，顺手把一个字符串常量、配置对象或内部辅助函数从根入口导出，可能改变宿主对整个模块的解释。一个普通函数虽然通过“可调用”检查，也未必能接收插件输入并返回 Hooks。测试辅助入口最好独立，根入口保持与你选用的插件协议一致；不能假定宿主会自动略过一切非插件导出。

这也是为什么包体检查要看最终 JS。TypeScript 的类型导出编译后可以消失，值导出会保留。只阅读 `.ts` 中一串 `export` 很难判断宿主实际得到什么，应对照编译产物和导入后的模块键值。

## 16.5 用打包结果重跑，而不是借用开发工作区

先在插件包目录执行：

```bash
npm pack --dry-run
npm pack
```

前一条检查包含哪些文件，后一条生成用于安装验证的 tarball。查看列表时重点找三类问题：入口缺失、必要运行时文件漏装、私有配置或实验日志被带入。压缩包很小并不表示完整，体积很大也不表示依赖已经正确声明。

接着在独立临时目录安装这个 tarball，使用隔离的 OpenCode 配置和数据目录运行目标场景。不要直接从发布包软链接回开发源码，否则工作区的依赖和未发布文件仍可能悄悄帮助它通过。`VERIFY.md` 中的宿主驱动展示了如何把 home、data、config、cache、state 和 tmp 约束在实验目录内。

本书的四场景已经验证实际宿主的发现、Hook、read、日志和 dispose，但依赖是预先安装后复制进去的。它没有覆盖用户首次联网安装。因此将这套驱动用于自己的发布包时，应另记录 tarball 安装路径和结果，而不是把已有 JSON 换个包名继续使用。

| 检查 | 能挡住的错误 | 仍需要下一层回答 |
| --- | --- | --- |
| 严格类型检查 | Hook 参数与返回形状不符 | 宿主实际失败路径是否符合声明 |
| 八项处理器检查 | 关联、metadata 合并、清理和防护错误 | 插件能否被发现并装载 |
| 固定宿主实验 | 真实加载、调用、结果与清理差异 | 未测试平台、网络安装和并发路径 |
| 打包后安装实验 | 包体缺失、依赖遗漏、入口不符 | 更宽版本范围是否成立 |

第十五章的 undefined after 和模块缓存分别说明了前两种检查的边界。升级时保留这两个历史样例，比只增加“模块可导入”的断言更有价值。

## 16.6 等待依赖不是通用重试机制

`loadExternal` 可以同时尝试多个候选，收集结果后仍按原候选次序保留成功项。重试只针对 file 插件、导入之前的 install 阶段，并且错误消息包含 `missing package.json or index file`。调用方提供 wait 时，加载器等依赖准备，再重试一次。

入口错误、兼容错误、已经发生的动态导入错误不在这项重试范围。源码明确说明，Bun 会缓存失败的模块解析；动态 import 一旦失败，继续在同一进程等待依赖不能保证它重新成功。发布者若把所有失败都包装成“稍后自动恢复”，会让使用者在错误进程里反复尝试。

排查时保存完整阶段和首次错误。修复缺依赖后用新进程验证，可以避免旧缓存干扰；但不要把“重启能加载”当成包已自洽。仍需从干净安装重跑，确认后来补上的依赖已经进入发布声明。

## 16.7 把 V1 到 V2 的迁移写成能力映射

V1 插件工厂返回 Hooks，共享 output 由 Hook 原地修改。固定 V2 `Plugin.Service` 则公开 add、remove、wait，使用插件 ID、锁和 Scope 管理活跃资源。二者的生命周期组织不同，迁移需要逐项确定能力归属。

| 当前观察器能力 | V1 放在哪里 | 迁移要回答的问题 |
| --- | --- | --- |
| 追加系统说明 | system transform | 新请求组装入口与顺序在哪里 |
| 关联调用 | before/after 与工厂内 Map | 新事件的身份和失败结果是什么 |
| SDK 日志 | 工厂取得的 client | 日志服务怎样取得，失败如何处理 |
| 后台资源 | 插件自己创建和保存 | 是否注册到当前插件 Scope |
| 清理 | dispose 清空状态 | 重加、失败、移除分别关闭什么 |

V2 add 会为插件建立子 Scope，加载失败时关闭它；替换同 ID 的已有插件前会关闭旧 Scope。remove 取出活跃 Scope 并关闭，wait 则围绕加载完成或失败等待。源码还检查加载循环，并防止在同一插件正在加载时移除它。这些细节比简单说“V2 支持热插拔”更能指导资源管理。

不过 Scope 只能管理挂在它上面的资源。已经写入的事件文件、发到远端的请求，不会因 remove 自动撤销。迁移时应为连接、订阅、计时器设计明确 finalizer，把不可回滚的副作用另作处理。本书没有运行 V2 宿主实验，这一节提供源码迁移线索，不把 V1 的通过结果转记到 V2。

## 16.8 升级时留下能解释差异的旧环境

保留旧宿主版本、包版本、锁文件和同一实验输入。先只换宿主，再看加载阶段、事件顺序和输出变化；确认后再换插件。若同时换模型、配置和插件，就很难判断一段不同的回复来自哪里。

发布说明围绕用户能遇到的行为写。例如“修复 after 缺失输出时读取 metadata 的异常”能指出触发和结果；“全面提高稳定性”无法帮助判断是否需要升级。已知的同进程模块缓存问题也应写在开发说明里，给出新进程复验方法。等上游行为改变并由原实验确认后，再删掉旧说明。

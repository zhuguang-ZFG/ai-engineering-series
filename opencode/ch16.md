# 第 16 章：插件发布与兼容升级

<!-- block: opencode-ch16.b-opening -->
本地文件能加载，只证明当前环境接受这份代码。发布成包之后，还会涉及入口、依赖、版本声明和宿主兼容检查；升级时要把这些变化一起核对。

## 16.1 从源码文件变成一个包

一个可用插件包需要明确导出入口、模块格式、运行时依赖和支持的宿主范围。只把开发目录压缩上传，可能包含未编译 TypeScript、私有配置、测试日志或不该分发的文件。

使用自己的包名与许可证，说明插件调用了哪些外部服务、保存什么数据和怎样停用。依赖上游开源代码时遵循其许可证；本书的例子为原创，不把上游整份源码重新包装成自己的实现。

```json
{
  "name": "@your-scope/opencode-review-trace",
  "version": "0.1.0",
  "type": "module",
  "exports": {".": "./dist/index.js"},
  "files": ["dist", "README.md", "LICENSE"]
}
```

这是包结构片段，不能直接当成经过宿主兼容验证的发布模板。固定版本的 `packages/opencode/src/plugin/loader.ts` 从 `./shared` 导入 `checkPluginCompatibility`，在 npm 分支调用 `checkPluginCompatibility(base.target, InstallationVersion, base.pkg)`：检查的是解析后的目标、宿主版本和包元数据。核对兼容声明时，应从这个调用点进入实现，再对照自己的 package.json；本书没有运行 npm 首次安装及兼容声明实验，因此这里不替读者填写未经验证的字段。可以先用 `npm pack --dry-run` 查看将包含的文件，再从一个干净目录安装测试。

## 16.2 本地文件与 npm 包检查不同

第九章已说明，钉版加载器对 npm 来源执行兼容性检查，本地文件走开发分支，跳过这道门。因而“把同一份代码换成 npm spec 后不加载”可能不是工具逻辑错误，而是入口解析或兼容声明不同。

发布测试应从干净目录安装目标包，避免开发工作区的 node_modules 恰好补齐了缺失依赖。可以删除测试副本后重建，但不要清理真实用户目录来模拟干净安装。

显式固定依赖与宿主版本，保存锁文件，再记录包内容摘要。只有包名而没有版本，很难复现几周后的加载差异。

## 16.3 三种检查分别挡住什么

| 检查 | 能发现的典型问题 | 覆盖不到的地方 |
| --- | --- | --- |
| 严格类型检查 | Hook 签名、参数字段、返回类型 | 宿主未声明的失败路径、模块发现 |
| 处理器实验 | 输出修改、关联状态、错误防护 | 完整依赖、服务端时序 |
| 固定宿主实验 | 发现、加载、实际调用、清理 | 未构造的网络、平台和并发情况 |

第八章的 undefined after 防护就是类型声明覆盖不到的例子；第九章的模块缓存则必须在进程与实例之间观察。测试通过时应说清是哪一层通过，不把它们合成一个无范围的“兼容”。

## 16.4 V1 与 V2 要分别迁移

本书 V1 插件返回 Hooks 对象，由宿主在 trigger 中传入共享 output；V2 代码则围绕插件注册、Scope 和服务能力组织生命周期。名称相似，不意味着只改 import 就能迁移。

先列出现有插件依赖的能力：system transform、自定义工具、事件订阅、内存状态、后台连接和日志。逐项找新接口，注明哪个可以直接替代，哪个需要重写，哪个还缺少支持。迁移后重新验证清理和失败，比只看正常路径更重要。

不要把一个 V2 remove 调用解释成磁盘副作用回滚。Scope 管理的是注册在它上面的资源；资源是否能撤销、如何撤销，仍由具体实现决定。本书未运行 V2 宿主实验，保留源码层面的说明。

## 16.5 给升级留一条回退路径

在隔离项目保留旧包、旧宿主和旧实验摘要，运行同样输入比较输出。发现差异后先判断是否属于预期接口变化，再更新书稿与兼容声明。不要同时换模型、插件、配置和宿主，再把最终效果全部归因于版本升级。

发布说明最好写具体触发与行为：例如“实例清理后仍使用旧模块，需要重启进程验证源码修改”，而不是“全面优化稳定性”。用户需要知道自己是否受影响，以及怎样确认新版本生效。

# 第 7 章：Session 事件日志

<!-- block: deepseek-ch07.b-opening -->
恢复会话时，程序应该相信哪一份历史：界面上看到的文字、内存里的消息数组，还是磁盘上的记录？DeepSeek Harness 把会话事件日志放在中心位置，模型历史由它投影出来。这样做的代价是事件设计必须严谨，收益是恢复、转录和观察能围绕同一份事实工作。

## 7.1 日志与模型消息不是同一种数据

会话日志会记录 turn/start、step/start、工具调用、工具结果、系统提示词变化以及结束状态。模型不需要看到全部内部事件；deriveMessages 根据事件形成适合模型的历史。界面也可以从同一日志提取另一种视图。

```text
SessionEvent 日志
  ├─ deriveMessages → 模型历史
  ├─ turn/step 投影 → 任务状态
  ├─ 工具结果投影 → 界面卡片
  └─ 转录与诊断 → 人可读记录
```

把 UI 卡片当成存储原件，会丢掉调用身份、结构化结果或中断标记；把模型消息当成全部日志，又会丢掉尚未进入请求的输入队列。因此每个消费者应明确读取哪一种投影，而不是再维护一份悄悄分叉的真相。

## 7.2 模型看见的内容必须能追溯

架构契约要求模型可见信息可从日志重建。插件若想提供新材料，应使用拥有持久事件的入口；对已有消息的变化则通过定义好的纯投影实现。临时在网络适配器里塞一段额外文字，可能让实际请求无法从会话历史解释。

这是排查提示注入与“模型为什么知道这个”的关键。先定位用户消息、系统片段、工具结果和运行上下文各自的来源，再讨论模型如何使用它们。缺少可追溯记录时，重放得到的请求可能与故障当时不同，再强的调试工具也无法补出失去的事实。

本快照还保存压缩的 assistant stream。成功结果进入 assistant/message，失败、重试、取消或流错误的尝试可以进入 assistant/attempt。attempt 保留诊断事实，但不应被机械拼进正常模型对话。硬进程丢失如果发生在结算写入之前，尚未结算的流片段也可能没有持久记录。

## 7.3 一个工具调用至少有两端

工具请求和结果要按身份关联。只把“读取成功”写进日志，没有 call id，遇到并发时就不知道结果属于哪个路径。默认循环恢复失败 Step 时，会为未配对请求留下明确结果：未启动与结果未知分别处理，已经提交的成功结果保持原样。

结果未知不是一种可安全重试的同义词。假设工具创建了远端工单，服务端已成功，客户端断线未拿到 id；此时重试可能创建第二张工单。恢复逻辑应查询业务幂等标识，或者让用户确认，而不是因模型历史需要配对就发明一次新的调用。

## 7.4 物理文件还要考虑格式版本

逻辑 Session 事件和物理 JSONL 存储由不同层负责。固定版本文档描述了按版本命名的代际文件、只读打开时的内存迁移、写打开时验证并发布新一代。历史源文件不应被原地覆盖成另一种格式。

这能让升级后的读取与旧文件保存同时成立。不要以为扩展名还是 jsonl，就能把不同版本按行拼接。未来版本应拒绝盲读；迁移链要逐步验证，再把完整结果发布。压缩格式、半行写入、独占写句柄都是物理层问题，不应靠改一条模型消息来修复。

备份时，先让写入收敛或使用持久化后端提供的导出入口，再复制完整会话目录及相关附件。仅复制最后一代文件而漏掉它引用的对象，可能得到“能列出标题但打不开正文”的假备份。恢复实验要在另一个空目录运行，不能只检查 zip 包有没有生成。

## 7.5 做一次可解释的恢复练习

创建只读任务并记录唯一输入标记，等待工具结果提交，再停止宿主。重启后先通过只读接口查看历史，不立即发送新任务。比较 turn/step 边界、工具 call/result 和模型可见投影。随后追加另一条输入，确认旧工具结果被复用，而不是再次执行已有副作用。

第二次把停止点放在工具尚未结算的位置，观察系统怎样标记中断尾部。最后测试一个不受支持的未来格式版本，确认它清楚拒绝，而不是尽力猜测字段。以上是本书建议的完整存储实验，尚未在本册组件环境执行；固定版本源码能说明预期职责，实际后端仍需单独验证。

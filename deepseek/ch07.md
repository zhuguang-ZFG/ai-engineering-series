# 第 7 章：Session 事件日志

<!-- block: deepseek-ch07.b-opening -->
DeepSeek Harness 从会话事件日志生成模型历史，恢复、转录和界面观察也以它为依据。要理解恢复行为，需要先分清事件本身，以及各个消费者从中提取的视图。

## 7.1 日志与模型消息不是同一种数据

会话日志会记录 turn/start、step/start、工具调用、工具结果、系统提示词变化以及结束状态。模型不需要看到全部内部事件；deriveMessages 根据事件形成适合模型的历史。界面也可以从同一日志提取另一种视图。

```text
SessionEvent 日志
  ├─ deriveMessages → 模型历史
  ├─ turn/step 投影 → 任务状态
  ├─ 工具结果投影 → 界面卡片
  └─ 转录与诊断 → 人可读记录
```

把 UI 卡片当成存储原件，会丢掉调用身份、结构化结果或中断标记；把模型消息当成全部日志，又会丢掉尚未进入请求的输入队列。因此每个消费者应明确读取哪一种投影，而不是再维护一份悄悄分叉的真相。

## 7.2 模型看见的内容必须能追溯

架构契约要求模型可见信息可从日志重建。插件若想提供新材料，应使用拥有持久事件的入口；对已有消息的变化则通过定义好的纯投影实现。临时在网络适配器里塞一段额外文字，可能让实际请求无法从会话历史解释。

排查提示注入或意外进入模型的信息时，可以分别追踪用户消息、系统片段、工具结果与运行上下文的来源。缺少这些记录，重放请求便可能与故障发生时不同。

本快照还保存压缩的 assistant stream。成功结果进入 assistant/message，失败、重试、取消或流错误的尝试可以进入 assistant/attempt。attempt 保留诊断事实，但不应被机械拼进正常模型对话。硬进程丢失如果发生在结算写入之前，尚未结算的流片段也可能没有持久记录。

## 7.3 一个工具调用至少有两端

工具请求和结果要按身份关联。只把“读取成功”写进日志，没有 call id，遇到并发时就不知道结果属于哪个路径。默认循环恢复失败 Step 时，会为未配对请求留下明确结果：未启动与结果未知分别处理，已经提交的成功结果保持原样。

结果未知不是一种可安全重试的同义词。假设工具创建了远端工单，服务端已成功，客户端断线未拿到 id；此时重试可能创建第二张工单。恢复逻辑应查询业务幂等标识，或者让用户确认，而不是因模型历史需要配对就发明一次新的调用。

## 7.4 物理文件还要考虑格式版本

逻辑 Session 事件和物理 JSONL 存储由不同层负责。固定版本文档描述了按版本命名的代际文件、只读打开时的内存迁移、写打开时验证并发布新一代。历史源文件不应被原地覆盖成另一种格式。

升级后的读取仍可保留旧文件，但不同版本不能仅因扩展名相同就按行拼接。读取器应拒绝不支持的未来格式，迁移链逐步验证后再发布完整结果。压缩格式、半行写入和独占写句柄需要在物理存储层处理，修改模型消息无法修复它们。

备份时，先让写入收敛或使用持久化后端提供的导出入口，再复制完整会话目录及相关附件。仅复制最后一代文件而漏掉它引用的对象，可能得到“能列出标题但打不开正文”的假备份。恢复实验要在另一个空目录运行，不能只检查 zip 包有没有生成。

## 7.5 做一次可解释的恢复练习

创建只读任务并记录唯一输入标记，等待工具结果提交，再停止宿主。重启后先通过只读接口查看历史，不立即发送新任务。比较 turn/step 边界、工具 call/result 和模型可见投影。随后追加另一条输入，确认旧工具结果被复用，而不是再次执行已有副作用。

第二次把停止点放在工具尚未结算的位置，观察系统怎样标记中断尾部。最后测试一个不受支持的未来格式版本，确认它清楚拒绝，而不是尽力猜测字段。以上是本书建议的完整存储实验，尚未在本册组件环境执行；固定版本源码能说明预期职责，实际后端仍需单独验证。

## 7.6 用七条小日志认识事件与投影

运行连续实例加上 `--trace`，首个场景输出一份七条记录的数组。ReviewJournal.append 用数组长度分配 seq，再保存 kind 和复制后的 data。snapshot 返回另一份结构化副本，调用者修改副本不会改掉原日志。它是内存教材，目的在于让事件与视图的关系可直接观察。

```json
[
  {"seq": 0, "kind": "plugin:load", "data": {}},
  {"seq": 1, "kind": "tool:start", "data": {"id": 1}},
  {"seq": 2, "kind": "tool:result", "data": {"id": 1, "lines": 2, "characters": 7, "todo": true}},
  {"seq": 3, "kind": "tool:settled", "data": {"id": 1}},
  {"seq": 4, "kind": "note", "data": {"text": "first"}},
  {"seq": 5, "kind": "plugin:stop", "data": {"active": 0}},
  {"seq": 6, "kind": "plugin:closed", "data": {}}
]
```

界面只想显示“发现 TODO”，可以挑选 kind 为 tool:result 的记录；资源诊断想知道是否清理，则关注 start、settled、stop、closed。二者读取同一份事件，生成不同视图。把展示字符串保存成唯一数据后，你就无法再准确回答当时 active 有几个调用。

seq 只表达这份日志内的顺序。它不是工具 id，也不是世界时间。工具 id=1 的四个阶段拥有不同 seq；另一个进程完全可能也有 id=1。正式 Session 会把序列、消息身份、工具身份和会话身份分别建模，避免一个字段承担所有关联。

## 7.7 为什么先复制再存

若 append 直接保存调用者传入的 data 对象，调用者之后改 `data.status`，旧事件就会跟着变。日志看起来是追加式，实质却仍能被外部引用改写。样例通过 structuredClone 切断引用，再冻结事件与顶层 data；当前记录的数据只有标量字段，这个冻结范围足够覆盖示例。

不能把这段写法机械搬到任意 JSON 审计。structuredClone 支持的值比 JSON 更多，Map、Date 或某些二进制对象都可能被复制，却不是本书事实文件约定的普通 JSON；Object.freeze 也不会递归冻结任意深层对象。官方 Session.append 要求所有事件 data 是可无损 JSON 表达的值，并在入口做运行时校验。

复制切断外部引用，JSON 验证限定可持久表达的值，冻结则防止本地后续写入。三者的失败也不同，例如函数对象可能无法复制，NaN 则可能在 JSON 转换中改变。把检查放在日志入口，能够在存储前发现这些问题。

## 7.8 真实 Session 的消息和边界

SessionEventMap 以事件名映射不同数据结构。turn/start 保存 turn；step/start 保存 turn 与 step；user/message 是带身份和来源的用户角色消息；assistant/message 除消息本身，还保存 compact stream、可选 usage 与 interrupted 标记。tool/call 保存原始 arguments 字符串，tool/result 则保存对应 ToolResultMessage。

为什么工具参数在 call 中保留原始字符串？这是模型实际产生的协议输入。解析后对象便于执行，却可能丢掉原始格式或失败片段；保留原文有助于诊断模型究竟输出了什么。工具执行器仍必须等参数完整并校验，日志保存原始输入不等于允许它直接执行。

tool/result 的 error 可以保留内部失败名、code 和用户可读 reason，它们位于模型 content 之外；meta 是工具私有的展示负载，同样必须能序列化。把错误原文全部拼进模型正文既可能泄漏，也会混淆给人看的诊断和给模型继续推理的内容。

request/header 是日志专用快照，用于重建下一次请求头；request/context 记录路由、容量或提示词更新能力的诊断信息，但不是本次最终能力的权威来源。第 6 章的 prepareCall 仍决定本次具体绑定。一个字段存在于事件里，并不表示每个消费者都该拿它驱动行为。

## 7.9 “看见过的半段回答”怎样保存

正常完成会形成 assistant/message。流中途取消但已经向用户交付可见前缀时，固定契约允许形成带 interrupted:true 的消息，使下一次请求包含用户确实看见的内容。没有形成表面消息的失败、重试或流错误尝试，则使用 assistant/attempt 保存诊断流。

这两类记录不能简单按“有文本就拼进聊天”合并。一次失败尝试可能含工具参数半段或供应商控制内容；把它当完整助手消息，下一次模型可能以为工具已经被合法请求。另一方面，把用户已看见的中断回答完全丢掉，继续对话时又会造成上下文断裂。

compact stream 保留原始增量边界与时间信息，只压缩重复信封。它与把所有 delta 拼成一个长字符串不同。前者还能回答首个可见内容何时出现、哪些片段属于同一个块；后者适合最终文本，却无法还原流过程。记录的用途不同，选择的数据结构也应不同。

## 7.10 从日志推出结论时需要什么前提

拿到 tool:start，没有 tool:result，能推出什么？在本书内存实例里，可能是调用仍停在 checkpoint，也可能已进入 error，或者测试还没读取后续记录。仅凭一个截取片段，不能立刻宣布崩溃。需要结合读取位置、是否已结束和是否拥有完整日志。

正式 Session 更复杂：事件可能已经逻辑追加但还没完成耐久检查点。读取后端取得的前缀，不应与仍活跃内存视图不加说明地混用。状态查询接口若返回不同层的数据，必须把它们的完成条件说清楚。

同理，日志中没有某个敏感值，并不证明它从未离开进程。自定义适配器可能绕过了正常记录，插件也可能直接请求外部服务。事件可追溯原则是一项架构约束，需要扩展代码遵守；它不会自动监控 Node 的全部 I/O。源代码审阅仍要核对业务动作是否进入预期路径。

## 7.11 恢复读取器应该拒绝哪些输入

最简单的日志检查器也应先验证序列连续、事件名对应形状、引用对象存在，再构造派生视图。发现 seq 缺口时，继续把后半段接上可能得到似乎完整的结果，却遗漏了一次撤销或替换；发现未来格式时盲猜字段，则可能把一种新语义降成旧语义。

可以复制样例 trace，删掉 tool:settled，观察资源视图留下的未结算调用；再删 tool:result，查看内容视图缺失的成功结果。数组仍可能被 JSON.parse 解析，但运行历史已经不完整。

正式投影还要处理合法的替换、压缩和分支边界。原始事件保持可追溯，模型表面可以按规则改变；这比直接改写旧行更容易解释。日后查看某条历史为何不再进入请求，能够追到造成变化的事件，而不是面对一份和昨天不同却不知道谁改过的文件。

## 7.12 把实验记录与业务历史分开保存

`facts/review-lab-20261110.json` 记录的是实验版本、源文件摘要、断言名称与通过状态；`--trace` 打印的是一个场景运行时的业务事件。前者便于证明运行过哪份代码，后者便于解释代码经过哪些分支。它们不应该互相代替。

摘要对应程序版本，trace 对应业务顺序，两者关联后才能复现并解释结果。修改事件字段或清理顺序后，需要重新运行相关场景并新增记录，保留原来的 trace。

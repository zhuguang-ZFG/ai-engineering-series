# 第 18 章：升级与架构比较

<!-- block: deepseek-ch18.b-opening -->
研究一个 Harness，最后应该能带走一些可检验的设计判断，而不只是记住几十个包名。DeepSeek Harness 最鲜明的选择，是让服务、插件生命周期和作用域成为同一套组合机制；它带来的灵活性，也要求作者更认真地管理依赖与清理。

## 18.1 从同一个问题比较

比较代理时，先固定问题。例如“给每次工具调用追加观察记录，插件卸载后停止记录”。这比比较功能数量有用，因为每个系统都必须回答注册、调用、错误与卸载四件事。

本书已实测 DeepSeek vendored Cordis 的依赖与 effect，OpenCode 分册则在 v1.19.5 实测了 V1 Hook。两个接口看上去都能监听，但返回值语义不同：Cordis waterfall 要沿 next 返回链委派，OpenCode V1 trigger 使用共享 output 并忽略回调返回值。把一份插件机械翻译过去，很容易“能加载、没效果”。

| 比较问题 | DeepSeek Harness 本册关注点 | 对照时应查什么 |
| --- | --- | --- |
| 依赖如何出现 | inject 与服务解析域 | 是显式依赖还是初始化上下文 |
| 修改发生在哪里 | 服务注册、waterfall 与作用域 | 返回值、共享对象或命令消息 |
| 谁清理资源 | fiber、effect、Agent scope | dispose 是否必达、是否等待 |
| 恢复依据是什么 | Session 事件与投影 | 日志版本、请求重建与副作用 |
| 执行受谁限制 | 管线策略与底层执行世界 | 工具权限是否覆盖插件代码 |

Pi、Hermes、Codex CLI 的具体行为应读各自分册的固定版本，不用本表猜测。共同词汇不等于共同语义，尤其“插件”“Hook”“会话恢复”“沙箱”这些词最容易让不同层的概念混在一起。

## 18.2 更新前保存的不是只有版本号

一份可比较基线包括 commit、依赖锁、最终 profile 配置、原创样例和结果摘要。只记录 package 版本，遇到同版本源码快照、平台构建差异或本地补丁，仍然难以解释变化。本文固定完整提交，就是为了让每条源码结论有落点。

升级时先跑组件实验，再跑最小完整任务，再扩大到项目。组件实验能快速发现 inject、waterfall、effect 的契约变化；完整任务检查模型协议、工具与会话；项目任务才暴露更复杂的工作流。跳过前两层直接跑一项大任务，失败时难以定位。

## 18.3 对结果做语义比较

日志里的时间、随机 id 与绝对目录不适合逐字比较。可以先提取事件顺序、依赖状态、调用与结果配对、资源关闭次数，以及最终文件内容。保留原始证据用于诊断，再提交脱敏摘要用于版本对照。

但归一化也不能太宽。把所有错误文本都删掉，就看不见某次 deny 变成了执行器错误；把所有顺序都排序，就看不见 around middleware 的嵌套语义变了。应该先决定哪些字段允许漂移，哪些属于契约，而不是为了让 diff 干净不断忽略差异。

本册原七项组件实验的断言就是一份最小语义基线：缺依赖时不执行、provider 消失后依赖者停用、失败回收受管资源、正常 waterfall 保留结果、veto 不执行主体、重复 next 被拒绝、父清理等待子资源。它们没有覆盖所有 dsh 功能，升级报告应继续保留这个边界。

## 18.4 可替换架构也有成本

把每个部分都做成插件，能把变化局限在能力边界，也会增加配置与生命周期的理解成本。一个服务什么时候可用、当前 realm 属于谁、哪个注册需要在停止后继续保留到排空，这些问题在单体程序里可能被隐藏，在插件系统里必须显式处理。

因此不要为了“可扩展”把一段永远不独立变化的代码拆成公共服务。抽象应该对应真实替换需求、所有权或测试边界。真正值得借鉴的是让契约清楚、失败有归属、资源可撤销，而不是复制所有目录层级。

## 18.5 这本书结束之后

如果你只想使用 dsh，留下第 1 章的身份地图、第 7 章的日志判断和第 15 章的权限分层就够用。准备写插件，把 review-lab 的十三项场景留在身边，先给一项可逆能力写清楚如何开始、失败和停止。准备设计自己的 Harness，则从业务任务反推循环与持久事实，别先追求一个包罗万象的插件 API。

“一切皆插件”只有在卸载、失败和恢复也被认真设计时才有工程价值。把这三种情况跑过，再回头看正常路径，很多看似繁琐的类型、事件与句柄就会有具体用途。

## 18.6 把升级差异落到具体断言

连续实例增加的十三项检查使比较更细。依赖从两个变成一个就激活，会破坏第一项；重复工具失败时删掉旧条目，会破坏冲突场景；parallel 改成提前拒绝，会破坏受控等待断言。每项失败都对应某条可观察契约，而不是笼统地说新版“不兼容”。

有些变化是修复旧行为，需要更新书稿与断言；有些是回归；还有些是配置迁移导致测试没有加载同一组合。先检查固定来源与启动条件，再看实际结果，最后讨论是否接受变化。不能为了让测试恢复绿色，先删掉与新结果不符的断言。

对事件语义尤其如此。serial 的零值终止不是偶然输出，它来自 isBailed 的明确条件。若改版后零不再终止，应检查源码契约是否改变，并评估哪些插件用零表示有效结论。这个影响可能远大于一个测试的返回值差异。

## 18.7 从样例里带走三种具体设计

第一种是精确撤销：保存本次 entry 或 handle，清理时只撤自己的资源。第二种是停止收敛：先关入口，再通知活动工作，最后等待完成。第三种是把确定事实与推断分开：日志记下阶段，消费者根据自己所需视图推导状态。它们分别出现在 register 的 remove、plugin disposer 和 Journal 投影里。

这些设计可以迁到普通服务程序，不要求采用 Cordis。一个 HTTP 路由注册器也需要精确移除，一个任务队列也需要停止接纳与排空，一个账单系统也需要区分已提交与结果未知。迁移时保留问题与保证，不必复制本书的包名和目录。

反过来，不该照搬的内容也很明确：内存 Journal 没有耐久性，平面参数冻结不等于任意深层安全，教学 ReviewTools 没有官方审批与结果管线。看到例子小而易懂，可以借它理解协议；交付真实能力时仍要补齐承担的边界。

## 18.8 怎样判断一本源码教材是否还能使用

先看写作提交和当前软件版本，再检查关键入口是否仍存在；随后运行无需模型的组件实验，最后检查实际部署路径。若基础生命周期已经变化，后续章节的函数名即使还在，解释也可能过期。固定实验给读者一个比出版日期更直接的判断方法。

书稿中的来源链接、示例摘要和实验结果不是装饰。它们让一条结论可追溯到代码与输入，也允许后来的人指出具体错误。更新时留下旧记录，说明新版本从哪里开始不同，比把所有历史都改成“最新支持”更诚实，也更方便维护。

读到这里，可以从 review_text 做一次真正的小改动：例如增加空白行计数，同时更新返回契约、正常断言和展示内容。再运行卸载与失败场景，确认业务变化没有破坏资源管理。能完成这种修改，并解释每条记录为什么出现，就已经越过了只会复制插件模板的阶段。

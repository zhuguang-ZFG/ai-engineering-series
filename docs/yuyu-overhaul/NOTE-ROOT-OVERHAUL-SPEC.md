# 关于仓根 `OVERHAUL-SPEC.md` 的说明（M0 Step 3）

仓根有两个 SPEC，主题不同，**不要混着执行**：

| 文件 | 主题 | product | 里程碑 | 执行者该不该打开 |
|------|------|---------|--------|------------------|
| `docs/YUYU-OVERHAUL-SPEC.md` | 《御舆：解码 Agent Harness》主分册彻底改造 | `book` | M0–M9 | 做御舆时看这份 |
| `OVERHAUL-SPEC.md`（仓根） | 《Omp 从入门到精通》第二分册改造 | `omp` | M0–M8 | 做 omp 时看这份 |
| `omp/OVERHAUL-SPEC.md` | 同上，分册目录内的正本 | `omp` | M0–M8 | 与仓根那份同源 |

M0 那一刻记的是「两份字节完全相同（各 29,194 bytes）」，且 Goal / Architecture / Tech Stack 写的是 `omp`
与 `yuyu-omp-*`。**那个 29,194 今天对不上任何口径**（既不是索引 blob 的 30,391，也不是仓根工作树的 31,138），
只能当成「当时手抄、无法复核」的数字看待。

能复核的证据更硬：`git ls-files -s` 显示两个路径**共享同一个 blob**
（`100644 d648401f3e1cb2f5c308050c39a1dda56fe57dfc`，blob 尺寸 30,391 B / LF 口径）——
这说明它们进索引那一刻确实一字不差。两份都在索引里（不是未跟踪）：

| 路径 | 状态 | 工作树字节 | 行数 | 说明 |
|------|------|-----------|------|------|
| `OVERHAUL-SPEC.md`（仓根） | `A ` | 31,138 | 747 | 30,391 + 747 个 CR：与 blob 同内容，只差 CRLF |
| `omp/OVERHAUL-SPEC.md` | `AM` | 35,233 | 788 | LF 口径 34,445，比 blob 多 4,054 B —— add 之后被回写过 |

能复核的还有主题归属：仓根这份标题就是《Omp 从入门到精通》彻底改造 SPEC，
Goal / Architecture / Tech Stack 全篇是 `omp` 与 `yuyu-omp-*`；全文 `omp` 命中 152 行、
`御舆` 命中 29 行，而那 29 行逐条看过去全是「不伤御舆 / 与御舆对照 / 御舆契约冻结」这类**约束与反回归条款**，
没有一条是御舆的执行任务。所以**仓根这份不是御舆 SPEC**，只是被放在了仓根，容易让执行者误读为「主分册改造计划」。

> **2026-11-04 复核：两份工作树已分叉**（`diff` 实测 79 个差异行，其中 **38 行是复选框** = 19 对
> `- [ ]` ↔ `- [x]`）：omp 侧回写了 19 个已勾项、未勾 43；仓根这份未勾 62、已勾 0。
> 工作树相差 4,095 B，但**索引里那份 blob 仍是同一个**（见上表），所以分叉只发生在磁盘上、还没进过索引。
> **omp 侧以 `omp/OVERHAUL-SPEC.md` 为准**，仓根那份只作历史快照，别再改它（分布与泄漏面见
> `omp/overhaul/BASELINE.md`）。

## 本步不删除（M0 明确约定）

未提交状态下删改名有误伤风险，故此处只记录说明。三份文件的去留（尤其仓根副本是否删）
留给用户在「提交推送」窗口决定。建议：

- 保留 `omp/OVERHAUL-SPEC.md` 为 omp 唯一正本；
- 仓根副本改为一个指路文件，或直接删除；
- 御舆正本保持在 `docs/YUYU-OVERHAUL-SPEC.md`。

## 与御舆 SPEC 的互相约束（易踩坑处）

- 御舆 SPEC 全局约束 3「不伤 `make book`」与 omp SPEC 全局约束 7「不破坏御舆」是同一件事的两面：
  任何一次改动后，`--product book` 与 `--product omp` 都要各自构建通过。
- 御舆 SPEC 全局约束 7 与 omp SPEC 全局约束 5：交叉引用只用「参见 omp 分册第 M 章」/
  「参见御舆第 N 章」，**不互相贴对方的命令表或专有数字**。
- 两份 SPEC 都禁止在本次执行期内 `git commit` / `git push` / 开 PR。

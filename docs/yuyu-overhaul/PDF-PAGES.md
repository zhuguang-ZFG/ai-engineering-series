1. **「半截文件」这个解释不成立——那两个数是另一次构建的完成态产物。**

   （这两轮当时的构建日志没留，所以证据只能是文件自身的闭合，不是 `OK` 那行）；
   `5,781,074` 则是今天 09:29 那条 `book --lang zh`（不带 `--pdf`）smoke 的完成尺寸，那次日志在、exit 0
   （`logs/smoke-both-after-xref.log`）。
   也就是说，它们与 dist 的 5,781,712 之差**从来就不是写一半**，而是「另一次命令、另一组 flag」——
   差多少见第 3 条。我无法再回溯当时那两次读数指的到底是哪个路径（没记 `ls -l` 的完整行），
   所以这里只能说：用「半截文件」解释它们是不必要的，用「命令不同」解释它们是逐字对得上的。
   **仍然保留的纪律**：引用任何尺寸前先确认日志打了 `OK` 且退出码 0；
   再补一条更实用的——**同时也要确认命令的 flag 组合**（`--lang` 与 `--pdf` 都会改字节数）。
   上一版 zh PDF 那 1 B（记 25,057,827、盘上 25,057,826）仍**未归因**：
   两份都是完成态，1 B 落在 PDF 交叉引用表/时间串这类固定长度字段里，回查不到成因；
   它不动页数、不动书签，读者侧无差异，所以只标注为「未归因的 ±1 B」，不写成「已知噪声」。
2. **HTML 的字节数跟着「这一次跑了几种语言」变，不只跟书稿变。** 这一点本轮实测出来了：
   `deco.py:34` 的 `_WHEEL_N` 是模块级计数器、**跨语言不重置**，每枚车纹章（wheel）要用它给
   SVG 的 `spoke` id 去重（`deco.py:41`）。同一份 en 书稿：
   `--lang both` 跑出来的 en 文档里 id 是 `spoke10`…`spoke18`（两位），
   `--lang en` 单独跑则是 `spoke1`…`spoke9`（一位）。每枚车纹有 25 处引用、全书 9 枚 = 225 处，
   差一位就是 **225 B**。
   这也解释了为什么 zh 侧没有这一项：`both` 是 **zh 先渲染**，zh 拿到的是 1–9（今天单独复跑 zh
   也是 1–9，两边 id 位宽一致），en 才是被推到 10–18 的那个。
3. **`--pdf` 会把主题索引的页码填进 HTML，非 `--pdf` 构建留空槽。** 这是本轮为解释 zh 那 638 B
   才找出来的机制，比前两条都大：索引行里 238 个 `<span class="page-ref idx-ref" data-ref="…">`
   在 `--pdf` 构建里带上页码数字，HTML-only 构建里是空 span。实测两份 zh 产物那一行
   56,067 B ↔ 55,429 B，**差正好 638 B**，而 238 处页码的数字字符加起来**正好 638 个**；
   除这一行外两份文件 13,766 行**逐行相同**。

把三条机制合起来，上一版遗留的「余数」现在都归零了：

| 比较 | 字节差 | 分解 | 余数 |
|------|--------|------|------|
| zh：dist（both + `--pdf`）5,781,712 ↔ smoke（zh only，无 `--pdf`）5,781,074 | 638 | 页码 638 + 车纹 0（zh 的 id 两边都是 1–9） | **0** |
| en：dist（both + `--pdf`）5,909,019 ↔ smoke（en only，无 `--pdf`）5,908,483 | 536 | 车纹 225 + 页码 311（116 处页码，实测数字字符 311） | **0** |

`225 + 311 = 536`、`638 + 0 = 638`，两个方向都是精确闭合，不再需要「~30–60 B 未归因」这类措辞。
（这一对 en 数字今天重跑复现：`--lang en` 单独构建仍是 5,908,483、spoke 1–9、页码 0 处——
可复现性本身就是这条分解的可信度来源。）

对读者无影响（id 只在文档内唯一即可；页码只有在打 PDF 时才用得上），
但它让「产物字节数」这种指标不能跨命令比：`--lang` 决定车纹 id 位宽，`--pdf` 决定索引页码填不填。
要修的话 `_WHEEL_N` 是一行的事（改成每份文档渲染前重置）；`--pdf` 填页码是设计行为，不该「修」。

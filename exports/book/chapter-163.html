上下文工程导论

你早先说过“活动地点待确认”，几轮之后，回答却填出了具体地点。先查这次请求：那条限制还在输入里吗？它被摘要丢掉了吗？如果原文还在，模型有没有正确使用？这些问题需要分别检查。

本章讲应用怎样选择、组装和维护本次输入。先读 L01 分词与提示词回查，再用 L07 通知核验、L09 检索观察实际进入输入的材料。

0. 引言：聊着聊着，它就忘事，还越来越贵的原理

长对话出现错误，可能是历史没有重新发送、窗口策略删了关键条件、摘要失真，或模型没有正确利用仍在输入里的信息。产品还可能自动检索历史或恢复会话，不能仅凭聊天界面判断模型收到了什么。

费用也不能只看轮数。输入长度、输出长度、缓存计费、工具调用和模型版本都会影响总额。留下实际请求、用量和结果，才能定位这次问题。

1. “上下文工程”定义

本章用这个词指应用为一次模型调用组织信息的工作：带上任务、规则、相关资料、必要历史与工具回执，留出输出预算，记录来源和版本，并检查删改后有没有失去完成任务所需的条件。

它与提示词设计有重叠，也涉及外部存储、检索和流程控制。组织得更清楚有助于检查，不保证模型稳定完成所有任务。

2. 从"血泪教训"说起：Manus 团队踩过的坑

Manus 的公开文章由 Yichao “Peak” Ji 发布于 2025-07-18，描述团队在构建 Agent 时调整上下文的经验，包括缓存前缀、外部文件、任务清单和错误记录。

这是该团队对自身系统的经验说明，不是本课程复现实验，也不代表 DeepSeek V4.1 Flash 或 Kimi K3 的内部实现。

2.1 四次重构教会我们什么

原文确实说团队重构过四次，但没有逐次列出问题、想法和结果，不能据此补造四阶段故事。可以从原文提取需要在自己任务上验证的问题：前缀是否稳定、资料能否从外部找回、任务状态是否仍可见、失败是否被如实保留。

例如把“地点待确认”存入任务状态，再检查每次组装是否带上它。这是本课的人工练习，不是 Manus 的效果数据。

2.2 AI 的"记性"到底像什么

先分清四个位置：模型参数、当前输入、推理缓存、应用外部保存的资料。参数通过训练更新；当前输入提供本次可处理的信息；KV 缓存复用某些计算；外部存储可以持久保存记录，但内容通常要被选取并放进输入，模型才能在这次任务中据此回答。

电脑内存（RAM）和硬盘也不是同一类存储，不能把“传统电脑内存＝硬盘”作为类比。关掉页面是否丢记录，取决于应用保存机制，不能归结为模型必然失忆。

3. 第一步：认识成本 - 你的每一分钱花在哪

3.1 先看成本的动机

先分开记录未命中缓存的输入、命中缓存的输入、输出、工具及存储等项目。若服务按每百万 token 分别计费，一种简化的核算式是：

模型费用 = (未缓存输入 token × 对应单价
          + 缓存输入 token × 对应单价
          + 输出 token × 对应单价) / 1,000,000
任务总费用 = 模型费用 + 其他实际计费项目

这是核算结构，不是通用报价。不同服务可能另收缓存写入、保留、工具或其他费用，按实际账单项目补齐。没有用量和版本依据时，不能把“70% 重复读取、20% 新内容、10% 输出”写成典型比例。

3.2 KV Cache概述

在常见因果注意力解码中，KV Cache 保存前面位置已经算出的键和值，后续生成位置可以复用，减少重复计算。它不是原文摘要、长期记忆或新增参数，也不会让模型停止计算后续输出。具体窗口、压缩或混合架构另看相应实现。

跨请求的前缀缓存还需要服务支持：如何匹配、何时写入、保留多久、是否命中及怎样计费，都由接口规定。不能把一次解码过程的 K/V 复用和云服务跨请求缓存当成同一项承诺。进一步说明见缓存附录。

3.3 "背课文" vs "现查现用"的价格差

“背课文”容易让人误以为缓存后不占输入或模型学会了资料。实际上缓存内容仍属于本次输入的一部分，仍受接口长度约束；命中是否更便宜以及便宜多少，按所选服务版本报价与用量核对。

以 DeepSeek 当前缓存文档为例，它描述按已持久化前缀单元匹配，并以尽力而为方式提供缓存；输入里有相同文字并不保证命中。文档提供命中与未命中 token 的用量字段用于检查。本课未发 API 请求，不填实际命中率或省钱比例；Kimi K3 也不能套用另一服务的规则。

3.4 避坑指南：别让时间戳毁了你的“缓存”

对于按相同前缀匹配的缓存，前部变化可能缩短可复用范围。只有任务需要时才带精细时间，稳定规则与动态数据分开组织，再核对实际命中用量。不能为提高命中率省略会影响答案的最新时间或有效版本。

错误示范：把动态信息放前面

请求 A：当前秒数 12:00:01 + 稳定规则 + 问题 A
请求 B：当前秒数 12:00:02 + 稳定规则 + 问题 B

前部时间不同，会影响按前缀匹配的复用机会。这里没有量出“99% 失效”或延迟增加多少，实际结果还受服务的缓存单元、写入和保留策略影响。

正确姿势：动静分离

稳定部分：任务规则、工具定义等；只有仍然有效才保留。
动态部分：当前问题、日期、获准使用的最新资料和回执。
检查：发送的真实序列、输入用量、缓存命中及结果是否正确。

这是输入组织思路，不是所有接口的固定消息模板。需要更正规则时应及时更正，不能为了缓存永久保留错误规则。

4. 第二步：滑动窗口 - 当"记性"变成"成本"

应用可以保留最近若干消息，也可以按 token 预算取历史。它们是组装策略；模型结构里的滑动窗口注意力是另一层机制。超长输入可能被接口拒绝、由应用删减或由产品压缩，不能默认模型自动按最旧消息丢弃。

4.1 “先进先出”会出问题的原理

假设较早的需求写着“保留旧接口 v1”，最近的消息只说“继续修改”。若组装时只取最近几轮，把兼容要求丢掉，模型本次就没有这条依据。具体第几轮超出，取决于长度和策略，不能说聊到第 20 句必然失去首句。

删除历史时还要保留工具调用与对应结果的配对关系，以及未完成任务的必要状态；不能截成孤立回执，再让模型猜它对应哪个请求。保留轮数不能代替长度检查。

4.2 "中间失忆症"：关键信息丢失的成因

Lost in the Middle报告了所测模型在多文档问答和键值检索中受到相关信息位置的影响。它提醒我们：可接收长输入，不等于每处信息都会正确使用；不能把那组历史实验的 U 形曲线写成所有当前模型的固定表现。

把来源清楚的任务约束与当前问题组织在容易识别的位置，再用目标任务测试。外部资料无论放在哪里都仍是资料，不应因为“放开头更重要”就升级成系统指令。

5. 第三步：选择性保留 - 关键信息锚定方法

保留什么要看任务。当前目标、有效约束、关键依据与尚未解决的问题通常需要可追溯；已完成的重复寒暄可以考虑删减。用户曾说过的信息也不都适合永久保存。

5.1 给信息分等级的动机

信息 保留办法 需要检查
当前目标和约束 维护任务状态，按需带入 是否已被用户更正或撤销
正在使用的证据 保留原句、编号、版本 是否适用、是否相互冲突
较早对话 原始记录外存，选择必要部分 摘要是否漏掉否定和条件
可重新读取的文档 外部保存并检索 权限、版本、定位是否可用

这些做法没有固定的成本加成或“90% 信息保留率”。保留率必须先定义要保留哪些事实，再用实际样本检查。

5.2 "钉钉子"策略

“钉住”指应用在后续请求中继续选入必要信息，不是模型获得永久记忆或保证遵守。任务更正时，要更新状态并保留来源；外部原句继续作为资料，不能为了保留而提升它的指令权限。

没有必要把每项任务状态都写入系统角色。具体消息层次按接口支持安排，再检查实际输入里是否含有当前有效的约束。

6. 第四步：RAG - 当"记性"需要"图书馆"

检索把外部记录中的一部分带回本次输入。它不会自动扩大上下文窗口，也不等于把资料训练进参数。原文足够短时，可以先比较完整给材料的简单方案。

6.1 “小黑板”不够用的原理

完整文档可能超过输入预算，也可能包含很多无关内容。检索可以缩小范围，但若漏掉例外条款、选中旧版或压掉冲突证据，也会让答案失去依据。总成本和耗时要包含解析、索引、检索与模型输出，不能凭流程图断言省 99%。

6.2 "查资料"的最佳实践

保存文档编号、标题、日期和原文位置；先按用户权限限定范围，再检索。块长、取回条数和阈值由资料与任务评估，不存在适用于所有模型的“500–1000 字、3–5 条、相似度 >0.7”。

到 L09 实际改变查询、切块和条数，看输入变化；它是字符重叠教学检索，不是语义模型性能展示。更多边界见 RAG 回查。

7. 第五步：压缩 - 上下文紧凑编码方法

摘要和结构化摘取改变了输入，可能省 token，也可能丢事实。模型看到的是处理后的内容，因此需要能回到原文核对，不能把压缩当成无损缩写。

7.1 什么时候需要"缩写"

当输入预算、延迟或阅读用途确实需要删减时再压缩；先找无关和重复内容，不按“超过 2000 字”或“历史占 80%”一刀切。对于否定、例外、金额和版本，省掉一个词可能改变结论。

7.2 "缩写"的三种境界

方式 可以保留什么 常见损失
总结 主要问题和进度 细节、来源和限定可能消失
要点 未解决事项及相关依据 关系与适用范围可能被拆散
表格 字段、单位、原句编号 空值、否定和跨行条件可能丢失

纸上做一次：原句“周六开放，节假日除外，地点待确认。”若压成“周六在社区阅览室开放”，既漏了例外又补造地点。较忠实的记录是“周六开放；节假日除外；地点未知”，并保留原文编号。token 数和费用要实际计算，不能由表格形式推算节省比例。

8. 系统整合：打造 AI 的“记忆宫殿”

把“保存”和“本次提供”分开实现，再记录来源、状态和取舍理由。存储中有一份文件，不代表模型本次已看到；缓存命中，也不代表它已核对文件真假。

8.1 像盖房子一样组装上下文

对于使用共享上下文上限的接口，一次简化预算是 输入用量 + 预留输出 ≤ 窗口上限。例如人工设定上限 4096、预留输出 512，输入预算就是 3584 token。实际产品还可能有独立输入/输出上限，以及工具定义、模板、图像或推理用量的特别规则，应按接口核算。

输入预算应覆盖任务、规则、历史、检索资料、工具定义与回执、当前问题和消息封装等。先用所选 tokenizer 或服务用量估算；超限时说明缩减、检索或拆分的取舍，不默默删除关键条件。

8.2 这样设计最强的原理

没有一种分层顺序能保证“最强”。合理设计应让你能查清三个问题：有效约束有没有进入输入、证据来源是什么、删减后是否仍能完成验收。缓存用于复用计算，检索用于选资料，摘要用于改变表示，它们解决的问题不同。

8.3 实战效果

本课没有 Manus 系统日志或两个实际模型的成本、时延实测。比较方案时，先定义任务和验收，再保存输入/输出用量、缓存命中、工具次数、首 token 延迟、总时长和错误案例；保持模型版本与任务集合可比。不要把某次改善写成所有任务都更准。

📝 拿来即用的实战设计

当前目标：要交付什么，怎样检查？
有效约束：谁提出、何时更正、哪些仍有效？
资料：来源编号、版本、原句位置和可读范围。
状态：已完成事项及回执、未完成事项、未知或冲突。
本次选入：问题需要的内容；记录删减和输出预留。

场景 1：全栈工程师 Agent（长程记忆型）

人工任务：修改支付模块，同时保留旧 API v1。把兼容要求和验收保存在任务状态；选入当前代码及相关接口约定，记录读取的版本和实际测试结果。历史再长，也不能只凭摘要里的“修改完成”判断已通过测试。

规则：遵守当前仓库约定，只在已授权范围修改。
目标：调整支付模块，保留 API v1 行为。
依据：接口约定版本、相关代码位置、当前失败现象。
状态：已改文件、已运行检查与结果、尚未验证的部分。
交付：改动理由、验证证据、未完成项。

这是一份输入设计，不是已经运行的开发 Agent。按轮数截取历史前，检查需求与工具调用/结果配对是否仍完整；不能把代码库检索结果当成系统规则。

场景 2：智能客服 Agent（精准问答型）

先确认问题涉及的产品、有效政策与用户可读资料，再取相关条款。与身份、订单有关的信息要由应用按授权范围查询，不能从用户描述或相似案例补出订单状态。

任务：解释当前政策对这个问题是否适用。
材料：获准使用的政策原句、版本和适用条件。
输出：有依据的答复、引用、未知与冲突项。
缺资料：说明需要哪条信息；需要人工接手时说明未处理部分。
执行：未收到真实退款或修改回执，不说“已完成”。

“只依据资料回答”有助于说明任务边界，但不能保证模型不犯错；仍要逐项核验。上下文保存多久由产品需求与实际保存规则决定，不统一规定三轮或十轮。

10. 名词对照表

名词 这里的含义与边界
Context Window 单次处理容量；输入、输出和其他用量限制按具体接口核算
Token 编码单位，不能固定换算成多少汉字；见 L01 的实际快照
KV Cache 复用已计算的键和值等状态；跨请求缓存另受服务规则约束
RAG 选取外部资料加入回答过程，不保证取回完整或正确证据
Sliding Window 本章主要指应用按预算选择历史，区别于模型注意力结构
Lost in the Middle 指定历史实验中的位置效应，不是所有当前模型的固定曲线
System Prompt 接口中的一类指令消息，不能由外部资料自行提升权限
Few-shot 在当前输入提供少量示例，普通推理不据此更新参数
Chain of Thought 中间推理步骤的相关方法，效果依模型与任务验证
Hallucination 生成了无依据、错误或虚构的内容；语气自信不是必要条件
Embedding 把输入映射为向量表示，相近不等于事实一致
Vector DB 向量存储与检索的一类实现，不是 RAG 的必要条件
Temperature 影响采样分布；低温不保证事实更正确
TTFT 请求到首 token 的时间，受排队、输入处理和服务实现等影响

总结：上下文工程的本质

先看模型本次实际收到什么，再查它怎样使用。外部存储、缓存、上下文和参数各有作用；任何取舍都要用来源、预算和结果核验。资料够用就先完整给材料，确有缺口再增加检索、摘要或状态管理，保留能回查的路径。
